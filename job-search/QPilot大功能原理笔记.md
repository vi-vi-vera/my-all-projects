## 1. 预览状态机与竞态（案例 3）

### 是什么

用户写完代码后，界面要决定：现在该转圈等、该启动服务、该渲染 iframe、还是该报错。这个判断就是预览状态机。

### 实现原理

**两层结构：后端算决策，前端执行 + 渲染。**

- 后端状态接口每次都返回一个显式的决策对象 `{ action, reason, message }`——**把「我为什么这么判」一起回传**，排障时不用猜。
- 前端把「后端状态 + 本地上下文（是否在对话、来源、是否已尝试自动启动）」喂给一个**纯函数**，得到一个动作，再一次性更新状态。
- 状态共 9 个：`init` / `sandbox-booting` / `no-sandbox` / `no-files` / `waiting-chat` / `auto-starting` / `manual-starting` / `running` / `error`。
- 真正启动服务走一条**独立的临时会话流**（不占主聊天）。

**后端判断的四个条件：**

| 条件 | 怎么取 |
|---|---|
| 对话是否还在输出 | 扫内存活跃流 + 会话状态 |
| 启动流是否在跑 | 查注册的临时流 |
| 沙箱是否存活 / 在哪个阶段 | 只读缓存判断（不触发冷启动） |
| 有没有可预览的项目 | 列文件并匹配入口文件，排除运行时目录 |
| 端口是否健康 | 沙箱内 HTTP 探测，**连探两次**（间隔 1 秒，任一次成功即健康），避免热重载抖动误判 |

### 面试怎么讲

**一句洞察（开场用）：**

> 竞态的根因不是时序，是**决策点分散**——四个异步源（轮询、聊天流、启动流、沙箱阶段）各自在改状态，谁晚到谁覆盖谁。

**修法：** 把散落各处的判断收敛成一个纯函数，单点决策 + 显式原因；再针对「旧结果覆盖新结果」用**本轮的启动时间**区分这是上一轮的失败还是这一轮的失败。

**八个修复串成的故事线（讲 3 个就够，其余备用）：**

| 现象 | 原因 | 修法 |
|---|---|---|
| 重试时「启动中 ↔ 失败」来回跳 | 上一轮的失败和这一轮的启动混在一起 | 用本轮启动时间区分 |
| 初始化时 loading 跳变 | 多处各自改状态 | 收敛到单点决策函数 |
| 生成结束后卡住不启动 | 阶段推进条件缺失 | 补上自动启动条件 |
| 初始化项目时预览闪一下空态 | 空态渲染早于数据就绪 | 调整渲染时机 |
| 导入仓库后一直等对话完成 | 等错了条件 | 导入场景不等对话 |
| 端口被占导致服务起不来 | 把出站连接误判成端口占用 | 只查处于监听状态的端口 |
| 沙箱回收后判成「没有项目」 | 只看沙箱不看快照 | 同时读版本快照 |
| 残留文件判成 no-files | 沙箱回收后残留 | 清理残留文件再判断 |

### 不能夸大

- 「缺文件场景 60 秒 → 约 6 秒」只针对**这一个复现场景**，不是线上整体预览耗时。
- 没有做全量耗时对比，只有往返次数和场景复现时间可以作为证据。

## 2. 部署链路（案例 4）

### 是什么

把沙箱里的项目变成一个能通过域名访问的站点。

### 实现原理

**完整链路：**

```
点部署 → 域名预检 → 存储预检 → 发起部署（SSE 流式回传进度）
   → 后端分流：静态项目 → 对象存储；沙箱项目 → 构建镜像 → K8s
   → 写部署记录（一次部署一行，含域名标识）
   → 网关按域名分流到对应实例
   → https://{标识}.域名
```

**域名分配三级优先级：**

1. 用户/前端指定了名字 → 用指定的（做重名处理）
2. 没指定 → 复用这个项目**历史上成功部署过的自定义标识**
3. 都没有 → 用部署 ID 做哈希生成兜底标识

另外：**平台保留的一级子域（自己的入口）不能被部署占用**，前后端都做了拦截。

### 面试怎么讲：两个最值得讲的决策

**① 部署从「模型手写 curl」改成「受控 MCP 工具」**

> 原来的做法是让模型自己拼一个 curl 调部署接口，等于把接口和凭证暴露给模型。改成接入受控的 MCP 工具：令牌和**本次操作**绑定，模型只能调这个工具，不能自己发请求。

（这条和案例 2 的 Git 受控令牌是同一个思路，两个案例互相印证。）

**② 存储预检：只在数据可能丢失时才弹确认**

> 容器重建会把数据带走。但不是每次部署都会丢——只有数据真的会随容器丢失时，才弹确认框并**说明原因**，否则每次都弹等于没弹。

**③ 双环境隔离（Preview / Production，2026-10 新功能）**

> 之前项目只有一套环境，改配置会直接影响预览。新增了 Preview / Production 双环境：环境变量文件分开、数据库策略可选，老项目给轻量迁移提示，启用后自动让 Agent 适配并重启预览。

**补充（追问用）：** 子域名部署白屏——部署时强制把构建的 base 路径改成根路径。

### 不能夸大

- 部署规模、成功率数字都没有，只讲设计和修复。
- 双环境是「最小隔离」，不是完整的环境管理体系。

## 3. 沙箱 Git 受控令牌（案例 2）

### 原理

- **原来的风险**：给沙箱一把仓库凭证，模型被注入就能往任意仓库写。
- **做法**：后端签发**短期有效（30 分钟）、带签名和载荷哈希**的令牌；模型只能拿令牌调后端接口；后端先做冲突和分叉检查再执行；凭证始终不出后端。
- **配套**：冲突处理（含 AI 辅助解决冲突）、按需 AI 生成提交信息、推送前预检和远程领先预警；清理预览产生的临时文件；修 untracked 文件触发的假冲突。

### 性能那段（换沙箱之后）

- 换到新的沙箱方案后，**每条命令都是一次独立网络往返**。
- 原来查一次状态要十几次往返（仓库根、分支、提交号、远程、未提交文件、跟踪分支、本地超前、远程超前……）。
- 修法：把同一接口要的命令合成一段脚本，**一次往返拿完**，后端按标记切开。
- 结果：状态检查十多次 → 1 次；提交推送 6 → 1；拉取前检查 5 → 1；与远程 diff 4 → 1；分支列表 4 → 1。

### 面试怎么讲

> git 本身没变，变的是「发一条命令要付的路费」。所以修法不是换回旧方案（已经不能选），而是把同一个接口要问的这些合成一次请求。

### 不能夸大

- 收益是**往返次数**，没有做前后耗时对比，不说「快了百分之多少」。
- 旧沙箱方案现在只剩注释，不能说「还能切回去」。

## 4. 会话与协作（案例 5）

### 三个功能点

1. **编辑后重发**：新增截断接口，删掉最后一条用户消息及其后的回复；**同时清理模型侧的会话上下文**（只删一边会导致两边历史不一致）；正在输出时拒绝截断，顺序是「先取消 → 再截断 → 再当作新消息发出」。
2. **输出期间排队输入**：模型还在输出时用户可以继续输入，前后端都做了，队列持久化。
3. **历史会话按需迁移**：多线程模型上线前的老项目打开是空白（约 3500 个会话受影响）。方案是后端返回「需要迁移」的信号，前端据此迁移一次；只读协作者也能看到历史。
4. **多实例下的导入状态**：导入完成的通知只在执行任务的那台机器上广播，导致页面卡在「导入中」。改成读数据库里的导入状态，完成后同步一次文件树。

### 面试怎么讲

重点讲**第 3 个**（方案设计）：为什么不做全量迁移、怎么保证幂等、失败怎么兜底。

### 不能夸大

- 3500 是「受影响会话数」的估算，不是你修复的数量证明。

## 5. 上传与身份（备用）

- **上传统一**：统一上传接口，单文件上限 1GB；聊天附件统一转存对象存储。
- **门禁**：来源校验（Origin 白名单）放在**解析请求体之前**——先校验再收数据。
- **身份统一**：接入公司统一认证，预览和部署共用一套身份方案，**密钥不进沙箱**；废弃了旧的 Cookie 方案。
- **员工信息**：`/auth/me` 返回完整员工信息（中文名、部门、账号、头像）。
- **预览身份透传**：网关负责注入身份，让预览里的应用能拿到登录态。

### 面试怎么讲

一句话版本：「把散在各处的上传收成一个入口，来源校验前置；身份统一到公司方案，密钥不进沙箱。」

## 7. 统一登录态接入（案例 6）

### 背景（这是钩子的来源）

平台原来获取登录态靠调用一个**第三方安全接口**。这个接口因为安全问题要被下线，我们提供的登录能力会直接失效。讨论后决定：**把预览和部署的域名整体迁到公司统一认证上**，顺便把身份获取方式统一。

### 做了四件事

**① 部署域名的泛域名接入统一认证**

- 只需要登录、不读用户信息时，统一认证会在访问时自动拉起登录，业务服务不用改代码。
- **副作用**：切过去之后，某个业务平台（报告平台）的对外接口登录态失效。
- 处理：当天上午**先回滚**，下午确定方案再恢复，形成 P0 / P1 / P2 三级：
  - P0：对该业务域名单独接入 + 约定路径白名单豁免登录，**用户侧零改造**；
  - P1：重新调整 OA Skill 适配新鉴权（统一认证自带的 skill 不能直接搬，要改造）；
  - P2：等新 OA Skill 出来后业务按需改造，或维持 P0。
- 踩到的限制：泛域名**不支持**整体配置免登录路径，只能「先接子域名再接泛域名，在子域名上配免登录」；内部早期文档写「不支持泛域名接入」，实际已支持。

**② 打通前后端统一身份获取**

- 旧方案走那个被下线的第三方接口，拿不到身份。
- 升级后的方式：前后端携带凭证请求平台统一身份接口，拿到用户基础信息（中文名、部门、账号、头像）。
- 冲突点：**预览域名是动态分配的**，原来那套「路径白名单豁免」在预览环境不适用，必须业务改造 + 预览域名也接入统一认证。
- 后端对接时要绕开证书校验，且返回字段名有变更。

**③ 对外服务的免登录路径**

- 用户部署的项目要对外开放接口时，直接请求会被统一认证拦截返回 302。
- 平台下项目是动态的，逐个域名加白不可行。
- 落地：**约定固定免登录前缀**（形如 `/api/no-auth/xxx`），业务把要开放的接口挂到这个前缀下，平台侧统一加白。两个站点已生效。

**④ 预览环境的接入（最难的一次定位）**

- 现象：预览环境不在认证网关后面，前端调标准身份接口会打到**自己**的服务上返回 404，被识别成「游客」只读。
- 初查：预览域名和测试部署域名解析到同一个负载均衡 IP，一度怀疑是转发规则把流量送错了地方。
- **根因（我定位的）**：接入时**回源端口配错**——负载均衡上预览的转发监听器只配了 443，实际流量走 80 打到了后台服务。改成强制 HTTPS、按 443 回源后解决。
- 方案收敛：不再区分预览和部署两套鉴权——前端沿用标准身份接口，后台服务解密请求头里的身份信息。
- 稳妥处理：开发测试阶段**不整体接入预览泛域名**，先单域名接入，避免影响正式环境。

### 面试怎么讲

**钩子：**

> 平台原来靠一个第三方接口拿登录态，这个接口因为安全问题要下线，我们的登录能力会直接失效。所以要把预览和部署的域名整体迁到公司的统一认证上。

**60 秒标准版：**

> 平台原来通过一个第三方安全接口拿登录态，这个接口要被下线，我们的登录能力会失效，所以决定把部署和预览的域名整体迁到公司统一认证上。
>
> 我负责的是对接和落地这一段。迁的过程中产生了连带问题：某个业务平台的对外接口登录态失效了，我们先回滚止血，再拆成三级方案——先给这个业务单独接入并加路径白名单，保证用户侧零改造；再改造内部的身份 Skill 适配新鉴权。
>
> 最难的是预览环境。它不在认证网关后面，前端调标准身份接口会打到自己的服务上返回 404，被当成游客。一开始怀疑是转发规则送错了流量，我最后定位到是**接入时回源端口配错**：负载均衡上只配了 443，流量实际走 80 打到了后台服务。改成强制 HTTPS 回源之后解决。现在预览和部署共用一套鉴权。

**追问 1：为什么先回滚再恢复？**
> 对外接口是别的业务在用，影响面不可控。先回滚止血，再拆成 P0/P1/P2，让「保证现有业务可用」和「长期方案」分开推进。

**追问 2：泛域名免登录怎么解决？**
> 平台不支持对泛域名统一配免登录路径，只能逐个域名加，但我们的项目是动态创建的，加不过来。所以约定了一个固定的免登录前缀，业务把要开放的接口挂到这个前缀下，平台侧统一加白。

**追问 3：如果重做？**
> 两件事：一是迁移前先把「预览域名是动态分配的」这个约束列出来，白名单方案就不会白做一次；二是接入前先确认回源端口和协议，80/443 这个坑其实配的时候就能发现。

### 分工表述（必须说清）

- 与同事一起推进：**同事负责复现样例和接入操作**，**根因是我定位的**（回源端口只配 443、实际走 80）。
- 不要说「我主导了这次接入」。

### 不能夸大

- 「泛域名不支持免登录」是平台限制，不是你解决的，你做的是**绕开它的约定方案**。
- 预览环境**开发测试阶段只做了单域名接入**，泛域名整体接入没做，别讲成「预览全部接完了」。
- AI 调用场景（如 MCP）的内网登录授权**还没做**，属于待研究。

### 脱敏对照

| 内部说法 | 面试说法 |
|---|---|
| 太湖 / TOF | 公司统一认证 |
| CLB | 负载均衡 |
| 具体域名、泛域名 | 部署域名 / 预览域名 |
| 业务平台代号（qdata） | 某个业务平台 |
| 标准接口路径、请求头名 | 标准身份接口 / 请求头里的身份信息 |
| 同事姓名 | 另一位同事 |

## 8. 监控（加分，不单独练）

- **伽利略结构化上报**：部署、Git 提交与推送、首页核心接口（P0 / P1 分级）。
- **Langfuse（两个项目）**：
  - QPilot：修了上报的环境标识缺失（导致全部落到 default）和重复观测（同一批调用被记两份），在导出阶段按规则丢弃重复项，业务埋点代码不动、可随时回退。
  - QQ OKR：从 0 接入（见 qq-okr 材料）。

**讲法：** 两个项目都碰过 AI 调用链上报——一边是从 0 建，一边是修质量。说清楚哪边是建、哪边是修，不要混。
