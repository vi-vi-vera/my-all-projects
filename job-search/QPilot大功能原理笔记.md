## 1. 预览状态机与竞态（案例 3）

### 是什么

用户写完代码后，界面要决定：现在该转圈等、该启动服务、该渲染 iframe、还是该报错。这个判断就是预览状态机。

### 实现原理

**两层结构：后端算决策，前端执行 + 渲染。**

- 后端状态接口每次都返回一个显式的决策对象 `{ action, reason, message }`——**把「我为什么这么判」一起回传**，排障时不用猜。
- 前端把「后端状态 + 本地上下文（是否在对话、来源、是否已尝试自动启动）」喂给一个**纯函数**，得到一个动作，再一次性更新状态。
- 状态共 9 个：`init` / `sandbox-booting` / `no-sandbox` / `no-files` / `waiting-chat` / `auto-starting` / `manual-starting` / `running` / `error`。
- 真正启动服务走一条**独立的临时会话流**（不占主聊天）。

**后端判断的四个条件：**

| 条件 | 怎么取 |
|---|---|
| 对话是否还在输出 | 扫内存活跃流 + 会话状态 |
| 启动流是否在跑 | 查注册的临时流 |
| 沙箱是否存活 / 在哪个阶段 | 只读缓存判断（不触发冷启动） |
| 有没有可预览的项目 | 列文件并匹配入口文件，排除运行时目录 |
| 端口是否健康 | 沙箱内 HTTP 探测，**连探两次**（间隔 1 秒，任一次成功即健康），避免热重载抖动误判 |

### 面试怎么讲

**一句洞察（开场用）：**

> 竞态的根因不是时序，是**决策点分散**——四个异步源（轮询、聊天流、启动流、沙箱阶段）各自在改状态，谁晚到谁覆盖谁。

**修法：** 把散落各处的判断收敛成一个纯函数，单点决策 + 显式原因；再针对「旧结果覆盖新结果」用**本轮的启动时间**区分这是上一轮的失败还是这一轮的失败。

**八个修复串成的故事线（讲 3 个就够，其余备用）：**

| 现象 | 原因 | 修法 |
|---|---|---|
| 重试时「启动中 ↔ 失败」来回跳 | 上一轮的失败和这一轮的启动混在一起 | 用本轮启动时间区分 |
| 初始化时 loading 跳变 | 多处各自改状态 | 收敛到单点决策函数 |
| 生成结束后卡住不启动 | 阶段推进条件缺失 | 补上自动启动条件 |
| 初始化项目时预览闪一下空态 | 空态渲染早于数据就绪 | 调整渲染时机 |
| 导入仓库后一直等对话完成 | 等错了条件 | 导入场景不等对话 |
| 端口被占导致服务起不来 | 把出站连接误判成端口占用 | 只查处于监听状态的端口 |
| 沙箱回收后判成「没有项目」 | 只看沙箱不看快照 | 同时读版本快照 |
| 残留文件判成 no-files | 沙箱回收后残留 | 清理残留文件再判断 |

### 不能夸大

- 「缺文件场景 60 秒 → 约 6 秒」只针对**这一个复现场景**，不是线上整体预览耗时。
- 没有做全量耗时对比，只有往返次数和场景复现时间可以作为证据。

## 2. 部署链路（案例 4）

### 是什么

把沙箱里的项目变成一个能通过域名访问的站点。

### 实现原理

**完整链路：**

```
点部署 → 域名预检 → 存储预检 → 发起部署（SSE 流式回传进度）
   → 后端分流：静态项目 → 对象存储；沙箱项目 → 构建镜像 → K8s
   → 写部署记录（一次部署一行，含域名标识）
   → 网关按域名分流到对应实例
   → https://{标识}.域名
```

**域名分配三级优先级：**

1. 用户/前端指定了名字 → 用指定的（做重名处理）
2. 没指定 → 复用这个项目**历史上成功部署过的自定义标识**
3. 都没有 → 用部署 ID 做哈希生成兜底标识

另外：**平台保留的一级子域（自己的入口）不能被部署占用**，前后端都做了拦截。

### 面试怎么讲：两个最值得讲的决策

**① 部署从「模型手写 curl」改成「受控 MCP 工具」**

> 原来的做法是让模型自己拼一个 curl 调部署接口，等于把接口和凭证暴露给模型。改成接入受控的 MCP 工具：令牌和**本次操作**绑定，模型只能调这个工具，不能自己发请求。

（这条和案例 2 的 Git 受控令牌是同一个思路，两个案例互相印证。）

**② 存储预检：只在数据可能丢失时才弹确认**

> 容器重建会把数据带走。但不是每次部署都会丢——只有数据真的会随容器丢失时，才弹确认框并**说明原因**，否则每次都弹等于没弹。

**判断方式（代码核对）**：读项目下 `.qpilotcode` 清单里的 `deploy.isEphemeralStorage` 标记 + `ephemeralReason`。

- 曾经考虑过的两种方案都否掉了：**扫项目文件去猜**不准（误报漏报多），**让模型判断**太重（每次部署都要跑一次推理）。
- 最终是**让生成项目的模型在收尾时自己声明**：预检只读这个标记，不贵也准。
- **标记由模型写入**（`src/config/system-prompt.ts`）：提示词强制要求模型在声明完成前做持久性自检——不允许把业务数据写到容器本地目录/SQLite/内存数组，要改用平台数据库或上传接口；自检完再把结果写进 `.qpilotcode` 的 `isEphemeralStorage`，为 `true` 时还要写一句中文的 `ephemeralReason`。所以它既是**生成阶段的约束**，也是自检结果，不是部署时扫出来的。
- 三态：`true` = 弹确认；`false` = 数据不随容器丢失，不管；`null/undefined` = 老项目，不拦截。
- **读取失败时按「需要确认」处理**（`readError=true`）——读不到不代表没风险，静默放行会漏掉真正有风险的项目。

**③ 双环境隔离（Preview / Production，2026-10 新功能）**

> 之前项目只有一套环境，改配置会直接影响预览。新增了 Preview / Production 双环境：环境变量文件分开、数据库策略可选，老项目给轻量迁移提示，启用后自动让 Agent 适配并重启预览。

**补充（追问用）：** 子域名部署白屏——部署时强制把构建的 base 路径改成根路径。

### 不能夸大

- 部署规模、成功率数字都没有，只讲设计和修复。
- 双环境是「最小隔离」，不是完整的环境管理体系。

## 3. 沙箱 Git 受控令牌（案例 2）

### 原理

- **原来的风险**：给沙箱一把仓库凭证，模型被注入就能往任意仓库写。
- **做法**：后端签发**短期有效（30 分钟）、带签名和载荷哈希**的令牌；模型只能拿令牌调后端接口；后端先做冲突和分叉检查再执行；凭证始终不出后端。
- **配套**：冲突处理（含 AI 辅助解决冲突）、按需 AI 生成提交信息、推送前预检和远程领先预警；清理预览产生的临时文件；修 untracked 文件触发的假冲突。

### 性能那段（换沙箱之后）

- 换到新的沙箱方案后，**每条命令都是一次独立网络往返**。
- 原来查一次状态要十几次往返（仓库根、分支、提交号、远程、未提交文件、跟踪分支、本地超前、远程超前……）。
- 修法：把同一接口要的命令合成一段脚本，**一次往返拿完**，后端按标记切开。
- 结果：状态检查十多次 → 1 次；提交推送 6 → 1；拉取前检查 5 → 1；与远程 diff 4 → 1；分支列表 4 → 1。

### 面试怎么讲

> git 本身没变，变的是「发一条命令要付的路费」。所以修法不是换回旧方案（已经不能选），而是把同一个接口要问的这些合成一次请求。

### 不能夸大

- 收益是**往返次数**，没有做前后耗时对比，不说「快了百分之多少」。
- 旧沙箱方案现在只剩注释，不能说「还能切回去」。

## 4. 会话与协作（案例 5）

### 三个功能点

1. **编辑后重发**：新增截断接口，删掉最后一条用户消息及其后的回复；**同时清理模型侧的会话上下文**（只删一边会导致两边历史不一致）；正在输出时拒绝截断，顺序是「先取消 → 再截断 → 再当作新消息发出」。
2. **输出期间消息队列**：原来模型输出时直接禁用输入框，效率低；现在模型输出时用户可继续发消息，进入排队队列，支持编辑 / 删除 / 置顶，前一条结束后自动发送队列第一条，队列持久化。
3. **重发时避免误删**：消息发出后若出错，此时消息**还没落库**；若照样走 truncate，会误删上一条历史消息。判定：**有会话标识（已落库）才 truncate，没有就跳过**。
3. **历史会话按需迁移**：多线程模型上线前的老项目打开是空白（约 3500 个会话受影响）。方案是后端返回「需要迁移」的信号，前端据此迁移一次；只读协作者也能看到历史。
4. **多实例下的导入状态**：导入完成的通知只在执行任务的那台机器上广播，导致页面卡在「导入中」。改成读数据库里的导入状态，完成后同步一次文件树。

### 面试怎么讲

重点讲**第 3 个**（方案设计）：为什么不做全量迁移、怎么保证幂等、失败怎么兜底。

### 不能夸大

- 3500 是「受影响会话数」的估算，不是你修复的数量证明。

## 5. 上传与身份（备用）

- **上传统一**：统一上传接口，单文件上限 1GB；聊天附件统一转存对象存储。
- **门禁**：来源校验（Origin 白名单）放在**解析请求体之前**——先校验再收数据。
- **身份统一**：接入公司统一认证，预览和部署共用一套身份方案，**密钥不进沙箱**；废弃了旧的 Cookie 方案。
- **员工信息**：`/auth/me` 返回完整员工信息（中文名、部门、账号、头像）。
- **预览身份透传**：网关负责注入身份，让预览里的应用能拿到登录态。

### 面试怎么讲

一句话版本：「把散在各处的上传收成一个入口，来源校验前置；身份统一到公司方案，密钥不进沙箱。」

## 7. 统一登录态接入（案例 6）

### 背景（这是钩子的来源）

平台原来获取登录态靠调用一个**第三方安全接口**。这个接口因为安全问题要被下线，我们提供的登录能力会直接失效。讨论后决定：**把预览和部署的域名整体迁到公司统一认证上**，顺便把身份获取方式统一。

### 做了四件事

**① 部署域名的泛域名接入统一认证**

- 只需要登录、不读用户信息时，统一认证会在访问时自动拉起登录，业务服务不用改代码。
- **副作用**：切过去之后，某个业务平台（报告平台）的对外接口登录态失效。
- 处理：当天上午**先回滚**——**回滚的是刚配好的泛域名接入配置**（把接入删掉），下午确定方案再恢复接入，形成 P0 / P1 / P2 三级：
  - P0：对该业务域名单独接入 + 约定路径白名单豁免登录，**用户侧零改造**；
  - P1：重新调整 OA Skill 适配新鉴权（统一认证自带的 skill 不能直接搬，要改造）；
  - P2：等新 OA Skill 出来后业务按需改造，或维持 P0。
- 踩到的限制：泛域名**不支持**整体配置免登录路径，只能「先接子域名再接泛域名，在子域名上配免登录」；内部早期文档写「不支持泛域名接入」，实际已支持。

**② 打通前后端统一身份获取**

- 旧方案走那个被下线的第三方接口，拿不到身份。
- 升级后的方式：前后端携带凭证请求平台统一身份接口，拿到用户基础信息（中文名、部门、账号、头像）。
- 冲突点：**预览域名是动态分配的**，原来那套「路径白名单豁免」在预览环境不适用，必须业务改造 + 预览域名也接入统一认证。
- 后端对接时要绕开证书校验，且返回字段名有变更。

**③ 对外服务的免登录路径**

- 用户部署的项目要对外开放接口时，直接请求会被统一认证拦截返回 302。
- 平台下项目是动态的，逐个域名加白不可行。
- 落地：**约定固定免登录前缀**（形如 `/api/no-auth/xxx`），业务把要开放的接口挂到这个前缀下，平台侧统一加白。两个站点已生效。

**④ 预览环境的接入（最难的一次定位）**

- 现象：预览环境不在认证网关后面，前端调标准身份接口会打到**自己**的服务上返回 404，被识别成「游客」只读。
- 初查：预览域名和测试部署域名解析到同一个负载均衡 IP，一度怀疑是转发规则把流量送错了地方。
- **根因（我定位的）**：接入时**回源端口配错**——负载均衡上预览的转发监听器只配了 443，实际流量走 80 打到了后台服务。改成强制 HTTPS、按 443 回源后解决。
- 方案收敛：不再区分预览和部署两套鉴权——前端沿用标准身份接口，后台服务解密请求头里的身份信息。
- 稳妥处理：开发测试阶段**不整体接入预览泛域名**，先单域名接入，避免影响正式环境。

### 关键事实（代码与设计文档核对）

- **接口**：平台统一提供 `GET /api/auth/me`（Skill 里写明：前端自动带 headers/cookies，后端请求时**只剔除 hop-by-hop headers，其余原样转发**）。平台侧用令牌解密请求头里的身份信息后返回。**密钥始终在平台侧，不进沙箱**。
- **前后端都可直调**（SKILL.md 已明确）：前端请求自动携带 headers/cookies；后端请求时**只剔除 hop-by-hop headers，其余原样转发**。身份判断必须以接口返回为准，不得信任客户端提交的用户名。
- （旧的分岔方案属于未上线的尝试，面试不提。）
- **预览链路**：认证网关 → 回源 443 → 负载均衡 → 预览网关（**透明反代，不剥离任何请求头**，所以加密身份头能原样进沙箱）→ 沙箱入口 → 沙箱内服务。
- **80/443 那个坑的准确机理**：回源配成 `http:80` 时，流量落到集群里真实存在的部署网关服务（它只认三个部署域名），看到预览域名就返回「请用部署域名访问」的错误 JSON；改成回源 `https:443` 后，流量才走到预览网关进沙箱。
- **两个域名解析到同一个入口 IP**，靠域名区分走哪条链路——这是配错端口会互相串的根源。
- 纯静态、没有后端的项目保留一个可选直连接口（只返回中文名、部门等展示信息，不给工号）。

### 面试怎么讲

**钩子：**

> 平台原来靠一个第三方接口拿登录态，这个接口因为安全问题要下线，我们的登录能力会直接失效。所以要把预览和部署的域名整体迁到公司的统一认证上。

**60 秒标准版：**

> 平台原来通过一个第三方安全接口拿登录态，这个接口要被下线，我们的登录能力会失效，所以决定把部署和预览的域名整体迁到公司统一认证上。
>
> 我负责的是对接和落地这一段。迁的过程中产生了连带问题：某个业务平台的对外接口登录态失效了，我们先回滚止血，再拆成三级方案——先给这个业务单独接入并加路径白名单，保证用户侧零改造；再改造内部的身份 Skill 适配新鉴权。
>
> 最难的是预览环境。它不在认证网关后面，前端调标准身份接口会打到自己的服务上返回 404，被当成游客。一开始怀疑是转发规则送错了流量，我最后定位到是**接入时回源端口配错**：负载均衡上只配了 443，流量实际走 80 打到了后台服务。改成强制 HTTPS 回源之后解决。现在预览和部署共用一套鉴权。

**追问 1：为什么先回滚再恢复？**
> 对外接口是别的业务在用，影响面不可控。先回滚止血，再拆成 P0/P1/P2，让「保证现有业务可用」和「长期方案」分开推进。

**追问 2：泛域名免登录怎么解决？**
> 平台不支持对泛域名统一配免登录路径，只能逐个域名加，但我们的项目是动态创建的，加不过来。所以约定了一个固定的免登录前缀，业务把要开放的接口挂到这个前缀下，平台侧统一加白。

**追问 3：如果重做？**
> 两件事：一是迁移前先把「预览域名是动态分配的」这个约束列出来，白名单方案就不会白做一次；二是接入前先确认回源端口和协议，80/443 这个坑其实配的时候就能发现。

### 分工表述（必须说清）

### 概念备注：负载均衡 vs Ingress（别说串）

- **负载均衡（CLB）**：云资源，在集群**外**，把外部流量送到集群节点的某个端口（或 Ingress 入口）。四层（TCP）+ 七层（HTTP/HTTPS）都能做。
- **Ingress**：K8s 概念，在集群**内**，按域名 / 路径把 HTTP 流量路由到具体服务；需要 Ingress Controller 实现，且前面通常要有负载均衡把流量送进来。
- 两者是**串联的两层**：负载均衡送流量进门，集群内网关按域名路由。看起来像（都在转发请求），但位置和职责不同。
- 本项目的三条入口：**测试部署域名**与**预览域名**共用一个负载均衡（转发规则分监听器配：预览的规则只在 443 监听器下，测试部署的规则在 80 回源能命中的监听器下）；**正式部署域名**走集群 Ingress 入口（host 规则 → 后台服务）；预览还有一层自带的预览网关（透明反代）再进沙箱入口。
- 面试口径：**「负载均衡在集群外送流量进门，集群内网关按域名路由——两层，串联。」** 沙箱方案里那个名字带 ingress 的组件，统一说「沙箱方案的入口网关」，不要展开标准 Ingress 资源细节。

### 概念备注：K8s 是什么（被问到时怎么答）

- K8s（Kubernetes）是**容器编排系统**：管的是「容器在哪台机器上跑、跑几个、挂了怎么办、怎么被访问到」。没有它，这些都要手工做。
- 结合本项目记住几个概念就够：
  - **Pod**：最小单位，装一个或多个容器。用户部署出来的项目、沙箱，各自都是一个 Pod。**Pod 是「正在跑的那个实例」，挂了就没了**。
  - **Deployment / StatefulSet**：不是实例，是**「说明书 + 管理者」**——声明「我要跑几个什么样的 Pod」，并保证实际跑着的符合声明（少了补、挂了重建）。
    - **Deployment**：无状态，Pod 之间完全等价，随便换一个都一样 → 用户部署出来的应用用这个。
    - **StatefulSet**：有状态，每个 Pod 有固定序号、稳定名字和自己的存储卷，按顺序启停 → **沙箱用这个**（StatefulSetPlus），因为每个沙箱是某个用户的开发环境，有自己的文件、端口和身份，不能被替换成一个全新的空实例。
    - 一句话区分：**Pod 是干活的，Deployment / StatefulSet 是保证「一直有合适数量的 Pod 在干活」的。**
  - **Service**：给一组 Pod 一个稳定的访问入口。**NodePort** 是把服务暴露到节点的某个端口（预览网关的 30881 就是）。
  - **Ingress**：按域名 / 路径把 HTTP 路由到 Service（正式部署域名走这个）。
- **我在项目里实际用到的**：构建镜像 → 推到镜像仓库 → 在集群里起实例 → 等它就绪 → 通过域名访问；以及预览这条链里，沙箱也在集群内，由预览网关转发进去。
- **口径**：「我用 K8s 部署过应用，知道 Pod / Service / Ingress 的基本概念和一条完整的部署链路；集群运维不是我的范围。」**不要说精通、不要说搭过集群、不要说写过 Operator**。被追问就诚实界定边界——你的定位是 AI 应用工程，不是基础设施。

## 9. 技术栈地图（概念理清用，面试不主动讲）

> 目的：把接触过的这些组件放到同一张图里，知道各自在哪一层、解决什么问题。面试不主动展开，但心里有底讲的时候不会慌。

### 9.1 一条请求的完整链路

```
① DNS          域名 → IP（决定流量去哪个门）
      ↓
② 认证网关      校验登录，注入身份头（横切能力）
      ↓
③ 引流层        把外部流量送进集群
   ├─ CLB       云的负载均衡，四层 + 七层都行
   ├─ IAS       内部的类 Nginx 网关，七层，带服务发现
   └─ NodePort  直接开在节点上的端口
      ↓
④ 集群内路由    按域名 / 路径找到服务
   ├─ Ingress   K8s 机制，host/path → Service
   └─ Service   集群内稳定入口，后面挂一组 Pod
      ↓
⑤ 运行层
   ├─ K8s       编排系统（调度、重启、扩缩容）
   ├─ TKE       腾讯云的 K8s 服务（公有云）
   ├─ TKEX      公司内部的 K8s 平台（原 STKE，按 BG 分：CSIG/TEG/PCG/WXG/IEG）
   └─ Pod       实际跑的容器；由 Deployment（无状态）/ StatefulSet（有状态）管着
```

### 9.2 按「解决什么问题」分类

| 类别 | 组件 | 解决什么 |
|---|---|---|
| 寻址 | DNS | 域名换 IP |
| 安全 | 认证网关 | 登录校验、身份注入 |
| 引流（进门） | CLB、IAS、NodePort | 把外部流量送进集群 |
| 路由（进门后） | Ingress、Service | 按域名找到服务 |
| 服务发现 | 北极星、K8s Service/DNS | 后端 IP 老变，怎么找到它 |
| 运行 | K8s、TKE、TKEX | 容器在哪跑、挂了怎么办 |
| 实例 | Pod、Deployment、StatefulSet | 真正干活的 |

### 9.3 三个最容易混的点

1. **CLB 和 IAS 是同类，不是上下游**：都在做引流 + 域名转发。CLB 是云产品（能做四层），IAS 是内部平台（类 Nginx，只七层，配北极星做服务发现）。不同团队/时期选了不同的，所以会同时存在。
2. **IAS 和 Ingress 也是同类，但层级不同**：Ingress 是 K8s 内部的机制（规则在集群里、跟应用走）；IAS 是独立网关平台（规则在平台上配，通过北极星寻址，可跨集群）。
3. **TKEX 和 TKE 是同一类东西的两个供应商**：都是 K8s 容器平台，TKEX 是内部的、TKE 是腾讯云的。前端从 TKEX 迁到 TKE，本质是**换了个跑容器的地方**，架构没变。

### 9.4 一句话记住每个

- **CLB**：云的门，四层七层都能转
- **IAS**：内部的类 Nginx 门，带服务发现
- **Ingress**：门里面的路由表（K8s 原生）
- **北极星**：通讯录，服务名 → 实际地址
- **Service**：集群内稳定入口，挡住 Pod IP 的变化
- **K8s**：编排系统本身
- **TKE / TKEX**：跑 K8s 的地方（云上 / 内部）
- **Pod**：真干活的容器；**Deployment / StatefulSet** 是保证它一直有的管理者
- **有状态 vs 无状态**：删掉重建会不会丢东西——会丢就是有状态（数据库、沙箱），不丢就是无状态（前后端服务大多都是）
