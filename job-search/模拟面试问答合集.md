## 模型一边生成一边显示，断线和改一句重发怎么处理

问：模型一段一段往外吐字时，前端怎么接？输出到一半失败了，用户看到什么？用户改一句再重发，模型侧的旧上下文怎么清掉？只讲 QPilot 里真实的实现。

答：按一次真实请求的顺序看。代码里只有四次动作：发送、持续往下写、断线后去取剩下的、改句子之前先删干净。

**发送。** 浏览器对聊天接口发一个普通请求，请求头里带着登录态。同时它记住另一条地址：`/api/agent/chat/会话编号;线程编号/stream`。页面刷新或连接断开时，不重新问模型，而是去这条地址把还没写完的内容要回来。会话编号还没准备好时，这条恢复请求不会发。

**持续往下写。** 服务器先不结束这个响应。模型每产出一小段文字，就写成一帧：

```text
data: {"type":"text-delta","id":"...","delta":"好"}

```

空行表示这一帧结束。浏览器读到一帧，就把 `delta` 接在当前这条回复后面。

同一帧写进当前这个响应，写完立刻刷出，避免字停在服务器或反向代理的缓冲里。

**Redis 做什么。** Redis 不保存这轮对话的正文。正文写在消息表里。它只帮断线后的下一次请求找到还没写完的那条流。生成开始时写两笔记录。

第一笔是自己的索引。键是「这个会话的这个线程」，值是一个流编号，一小时后自动过期。新请求进来时，靠这笔记知道该恢复哪一条，而不是在所有正在输出的流里猜。

第二笔由可恢复流那一层写入：已经推给浏览器的那些帧暂存在这里。产生这些帧的那个进程同时在 Redis 上等着新连接来问「你还在写吗」。

**断线后去取。** 浏览器带着登录态访问上面那条恢复地址。服务器先读第一笔，拿到流编号，再拿这个编号去读第二笔，响应头和发送时一样。

原来的进程还在，它就会应答。已经暂存的帧先补上，之后新产生的帧继续写给这个新连接。页面上已有的字不用重头生成。

进程已经重启，就没有人应答，结果是等待应答超时。这时 Redis 里的流编号可能还在，但那条正在写的流接不回来。恢复接口返回 `204`，浏览器改为加载消息表里已经存下的内容，不会因为 Redis 里还有一个编号就再叫一次模型。Redis 里没有这个编号时，同样返回 `204`，表示这回合已经结束，或者根本没在输出。

**改一句再发送。** 这一步要动两处记录，只删一处会让两边看到的历史不一致。

消息表里删的是这个对话最后一条用户消息，以及它后面的全部回复。页面上的消息编号和数据库里的编号不是同一套，所以截断请求不带页面上的编号，由服务器自己找最后一条用户消息。

模型侧另有一份会话记录，下次发送会拿它接着写。所以截断之后还要删掉这份记录，并清掉「下次从旧会话继续」的指针。下次发送会用删完之后的消息重新开会话。

对话状态还是「正在输出」时，截断会直接拒绝。否则一边删记录，一边还有字写到页面上。顺序是：先取消当前这回合，等状态不再是正在输出，再截断，最后把改过的句子当作一条新消息发出去。
