# 2026-11-04 模拟面试 · 一面（AI 应用 / Agent 全栈）

> 面试官设定：组内资深工程师（未来同事），一面 60–90 分钟。
> 评分四维：结论先行 / 案例支撑 / 边界诚实 / 可被追问的深度，各 1–5 分。
> 结果：**66 / 140（2.4 分均），按 28–32K 目标，一面止步水平。**
> 题目来源：[`../面试问答合集/待补答案-面试官视角.md`](../面试问答合集/待补答案-面试官视角.md) 的 12 道满分题。

## 总评

| 题 | 内容 | 分 | 主要问题 |
|---|---|---|---|
| Q1 | 一分钟自我介绍 | 11 / 20 | 零机制零数字，把最硬的成果说成了功能清单 |
| Q2 | 架构归属与边界 | 7 / 20 | 前后矛盾（「跑通」→「毛坯」），「重构了很多」是废话 |
| Q3 | 预览九态与竞态 | 12 / 20 | 最强项，旧失败过滤那句逻辑是崩的 |
| Q4 | 用一个概念概括你做的层 | 12 / 20 | harness 概念对，但没和自己的六块对上 |
| Q5 | Git 令牌的威胁模型 | 9 / 20 | 最强的一块，答成 30 秒版本 |
| Q6 | 评估与回归集 | 13 / 20 | 诚实满分，方法全丢，还把自己有的 demo 说没了 |
| Q7 | 系统设计：Chat + tool call + diff + preview | 2 / 20 | 没有骨架，直接冻结 |

## 三个模式（比单题分数重要）

1. **在讲「我做了什么」，不在讲「我为什么这么做」。** 七题里六题缺「放弃了什么」。招的是能判断的人，不是能执行的人。
2. **强项收缩得太厉害。** Git 令牌、预览状态机答出了简历上一行字的长度。强项答浅比弱项答浅致命——它直接说明没想过威胁模型和设计取舍。
3. **有货，但没内化。** 五份答案文档齐全，一开火就说「不清楚」。读过 ≠ 能讲，中间差的是一次一次张嘴。

## Q1 · 一分钟自我介绍

**问**：一分钟以内，说清我是谁、做过最硬的一件事、为什么坐在这个岗位前面。

**我的回答（原文）**

> 面试官号，我是刘奕晨，毕业于中国传媒大学软件工程专业，工作时长 5 年，前三年在华侨城做园区业务相关的 web、桌面端、小程序，后面在腾娱先做了 QQ 频道的 h5、小程序、web、运营后台，近一年由于组织架构调整，开始接手全栈 agent 开发，目前主要人力在一个司内的 agent 编程平台上，我接手这个平台时主流程大致跑通，不过稳定性不太好，所以前期我主要是修这些稳定性的问题，并补充相关 agent 能力，主要包括支持从 git 导入仓库、支持 skills、优化等待时长等。我的技术栈主要是 TypeScript、React 和 Node.js

**评分**：11 / 20（结论 3 · 案例 2 · 边界 4 · 深度 2）

**问题**

- **「近一年」会被抓。** 2026 年 3 月转全栈，现在 11 月，八个月。面试官一算就对不上。
- **「接手时主流程跑通、我去修稳定性」最伤。** 把自己定位成「来修 bug 的」，还主动递刀把子：「那架构是谁设计的？你是维护还是重建？」
- **三个「能力」全说成功能清单。** git 导入、skills、优化等待时长——一个数字都没有。手里明明有「Git 两条链路的权限边界」「7 接口合并一次往返、状态检查十多次→1」「缺文件 60 秒→6 秒」。

**标准答法**

> 面试官好，我是刘奕晨，中传软件工程本科，五年经验，前端出身，现在做 AI 应用的全栈开发。
>
> 前三年在华侨城做园区业务的 Web、桌面端和小程序；2024 年 7 月到腾娱，先做 QQ 频道的多端前端和运营后台，其中技术债治理后台是我从空仓库独立做到上线的。
>
> 2026 年 3 月转全栈，现在是企业内部 AI 编程平台 QPilot Code 的两名主力开发之一，和另一位同事平级分工。我负责沙箱里的 Git、预览、部署，以及上传、身份、Skills 和会话这几块，前后端都写。
>
> 最能说明我做的事是把「模型能碰什么」讲清楚：Git 有两条实际在用的路——面板上的提交推送走后端接口，先做冲突和分叉检查；聊天里让 AI 提交，是模型在沙箱里用原生 git 命令做的，仓库配置里带着凭证，所以也能推成功，这条靠提示词约束不主动提交。另外我设计并实现过一套短期令牌、后端代执行的 AI 受控写入方案，但当时没从界面接进去。部署那条是真正落地的：从模型手写 curl 改成受控的 MCP 工具。另外把沙箱里 7 个 Git 接口的多条命令合并成一次往返，状态检查从十多次降到 1 次。
>
> 技术栈是 TypeScript、React、Node.js；AI 这层主要是 Claude Agent SDK、MCP 和沙箱执行。

差别在三点：**说清定位（两名主力之一）、说清机制（令牌、受控工具）、给一个数字（十多次→1）**。

## Q2 · 架构归属与边界

**问**：你说接手时主流程跑通、你去修稳定性。那这个平台的架构不是你设计的是什么？你是在别人的架构上打补丁，还是把某一块重做了？边界在哪？

**我的回答（原文）**

> 大的框架不是我设计的，不过我接手的时候基本上是个毛坯状态，所以后续慢慢重构了喝多功能

**评分**：7 / 20（结论 2 · 案例 1 · 边界 3 · 深度 1）

**问题**

- **前后矛盾。** Q1 说「主流程跑通」，Q2 说「毛坯」，隔了不到两分钟，会被判定为「往自己有利的方向调措辞」。
- **「慢慢重构了很多功能」是废话。** 「慢慢」「很多」两个词同时说明：说不清做了什么，也说不清范围。
- 正确切分是：**框架和主链路是别人的，「把每个模块从能跑推到可控」是我的。**

**标准答法**

> 框架不是我的。主链路——对话、沙箱执行、预览、Git、部署——是之前同事搭的，我 3 月加入时它能跑，但每个环节都不可靠。
>
> 我做的不是重写框架，是把其中三块从「能跑」推到「可控」：
>
> 一是**模型写 Git**。我先把两条链路理清楚：面板上的提交推送走后端接口，先做冲突和分叉检查；聊天里让 AI 提交，是模型在沙箱里用原生 git 命令做的，凭证在仓库配置里，靠提示词约束不主动提交。另外我设计并实现过一套 30 分钟令牌、后端代执行的 AI 受控写入方案，不过没从界面接进去。这条边界我会主动说清，不会讲成「凭证不进沙箱」。
>
> 二是**部署**。原来让模型手写 curl 调接口，改成受控的 MCP 工具，令牌和这一次操作绑定。
>
> 三是**预览**。原来轮询、聊天流、启动流、沙箱阶段四个源各自改状态，界面反复横跳。我收敛成一个纯函数做单点决策，再用本轮启动时间过滤掉上一轮的失败。
>
> 所以边界是：框架和主链路是别人的，这三个模块的方案、实现、上线是我的。

三段骨架一致：**原来怎么做 → 问题是什么 → 我改成了什么**。后面每题都能套。

## Q3 · 预览九态与竞态

**问**：①四个异步源分别是什么、为什么结论不一致？②单点决策纯函数的输入输出是什么？③重试时上一轮的失败晚到，怎么判断新旧？

**我的回答（原文）**

> 当用户在跟 llm 沟通时，会有一个 is_chat 的状态记录当前是否在会话状态，然后启动预览服务时，也会有一个预览的状态，而预览是跑在沙箱里面，沙箱也会维护一个状态，而前端的预览窗口展示什么就由这几个状态来决定，这些判断原来是各自散落在代码里面，很容易产生竞态导致在启动服务阶段，启动流程会反复闪动，或上一轮启动失败了，重启时不展示启动流程反正展示失败状态，我吧这些状态收归到了一个纯函数里面，预览窗口当前的状态有这几个变量统一计算，并新增了一个失败时间记录，如果这个记录小于当前时间，说明是过期态，就不做计算

**评分**：12 / 20（结论 3 · 案例 3 · 边界 4 · 深度 2）

**加分**：直接报了 `is_chat` 这类真实字段名，可信度远高于「有个会话状态」。以后每题带一两个真名。

**必须修的逻辑错误**

> 「如果这个记录小于当前时间，说明是过期态」——**任何过去的时间都小于当前时间**，按字面等于「所有失败都算过期」。

正确说法：每次启动记一个**本轮启动时间**；失败结果自带它**属于哪一轮**的时间；判断时若失败的归属时间**早于本轮启动时间**，才是上一轮迟到的结果。比的是「失败的归属时间」和「本轮启动时间」，不是和「当前时间」。

加分延伸：时间戳方案有隐患——同毫秒、时钟回拨会误判；更稳的是每次启动发递增的 `runId`，比 id 不比时间。

**另两个漏掉的点**

- 纯函数的输入输出没交代：输入 = 后端状态 + 判断原因 + 前端本地上下文，输出 = 九态之一 + 该做什么。
- 状态其实是两层算的：后端综合沙箱存活、文件与版本快照、启动流、探两次间隔一秒的 LISTEN 端口检查，算出九态并把**原因**一起回传；前端纯函数只做本地上下文合并。

**标准答法**

> 四个源：轮询、聊天流、启动流、沙箱阶段。它们各自在不同时间点通知前端，谁晚到谁覆盖，所以出现两个症状——启动阶段流程反复闪动，以及上一轮失败的结果晚到，把这一轮的「启动中」盖成「失败」。
>
> 我拆成两层。后端综合四件事算状态：沙箱是否存活、文件与版本快照是否存在、启动流有没有致命错误、以及探两次间隔一秒的 LISTEN 端口检查——只查 LISTEN，因为原来把模型网关的出站连接也当成端口占用，服务就起不来了。后端输出九态之一，并把判断原因一起回传，排障不用猜。
>
> 前端只有一个纯函数：输入是后端状态 + 原因 + 本地上下文（聊天还在输出、用户有没有点重试），输出是当前该做什么。所有异步源只提供输入，不再自己改状态。
>
> 旧失败靠本轮启动时间过滤：失败结果带着自己归属的那一轮时间，早于本轮启动时间的一律丢弃。这个方案有局限——同毫秒和时钟回拨会误判，更稳的是用递增的 runId。

## Q4 · 用一个概念概括你做的层

**问**：你做的模块挺散（Git、预览、部署、上传与身份、Skills、会话、前端工作台）。用一个概念概括「我在做哪一层」，为什么？

**我的回答（原文）**

> 这些其实都是 harness 这块的概念，如果只是调用 sdk 的话其实只能根据输入给出一段回答，而且没有状态，但是我们实际使用中需要模型可以直接接触我们的生产资料、需要记忆历史的对话、需要规划工作流程，且一些授权的信息也需要对模型进行隔离，这就需要我们去给模型提供工具调用、做记忆能力、状态管理、错误处理这些

**评分**：12 / 20（结论 4 · 案例 2 · 边界 3 · 深度 3）

**好的地方**：概念抓住了，而且从「为什么」切入——「只调 SDK 只能给一段回答、没有状态」，比背定义强。

**只答了一半**：讲成了教科书解释，没讲成「这个词就是我」。缺的动作是**把 harness 六块和自己的六块一一对上**。

**两处越界**

- **「记忆历史对话」** → 实际做的是截断、输入队列、历史会话按需迁移，属于**上下文管理**，不是记忆系统。追问「长期记忆怎么存、怎么召回」就崩。
- **「规划工作流程」** → 规划是模型侧的事，没做 planner，也没做工作流编排（单 Agent + Skills）。这句等于主动邀请问多 Agent。

**三句要补**

① 六块对六块：

> 我做的正好是六块里的五块：控制循环与状态收敛——预览九态单点决策；工具执行——部署改受控 MCP 工具；上下文管理——Skills 渐进式加载、截断两边都删；权限与沙箱——Git 面板预检、AI 受控写入方案（未接入界面）、身份密钥不出平台；可观测——AI 调用链的 trace、token 与成本口径。缺的是流程编排那块，我们是单 Agent + Skills。

② 三层区分（高频追问）：

> harness 是拥有循环、状态、工具、权限和恢复的那一层；framework 是帮你把这些拼起来的工具箱；MCP 是工具怎么接进来的协议。harness 管整体，framework 是零件，MCP 是插头。

③ 收尾：

> 所以我做的不是「对接模型」，是模型之外那一层——循环、工具、权限和状态收敛。

## Q5 · Git 令牌的威胁模型（针对设计实现过的 AI 受控写入方案）

> ⚠️ 前提先说清：这套 `git-write` 工作流后端实现过、但**没从界面接进去**。答威胁模型时按「设计方案」讲，别当成线上所有 Git 操作的现状；线上两条链路见案例 2。

**问**：①模型拿令牌能做什么，能推任意分支、写别的仓库吗？②载荷哈希防什么，不加会怎样？③令牌泄漏的损失边界在哪？

**我的回答（原文）**

> 模型只能拿这个令牌调后端接口，由后端去做git操作，这个令牌如果泄露了风险也是可控的，一方面有效时长只有30min

**评分**：9 / 20（结论 3 · 案例 2 · 边界 3 · 深度 1）

**重话**：令牌设计是这份材料里最能体现安全判断的一块，答出了最浅的版本。强项答浅比弱项答浅更亏——面试官会判定「只是照方案实现了，没想过威胁模型」。

而且「风险可控，因为只有 30 分钟」把主动权递出去了：30 分钟够不够把该干的事干完？够，clone 一个仓库、推脏代码 30 秒都不用。

**标准答法**

> 只能对**这一个会话、这一类操作**发起请求，而且必须过签名校验。作用域写在签名里，不是写在请求参数里——令牌载荷里根本没有仓库地址和分支，想改仓库、改分支，签名直接对不上。
>
> 载荷哈希防篡改和重放：签名覆盖「这次请求的完整内容」，哈希一变签名就失效。没有哈希，令牌等于一张 30 分钟的万能通行证，可以拿它发任意 body；有了哈希，令牌和这次操作是**一对一绑定**的，换内容就作废。
>
> 泄露的损失边界分三层：作用域——只能调固定接口、只能动这一个会话的操作；凭证隔离——工蜂凭证不在令牌里，令牌换不出更高权限（**注意这是该方案的隔离；线上对话链路里凭证在沙箱仓库配置里**）；执行侧兜底——后端仍做冲突和分叉检查，操作留痕可审计。最坏情况是 30 分钟内、对这一个会话做这一类操作，且每次都被记录。
>
> 但要说清局限：30 分钟对自动化攻击不算短，时间不是主防线，作用域收窄和载荷哈希才是；而且这套方案没有从界面接进去，讲的时候要主动划清。再进一步，令牌应该绑到具体 commit 或 diff 哈希上，并且一次性使用。

## Q6 · 评估与回归集

**问**：怎么判断一个 AI 功能变好还是变坏？有没有回归集，每次改 prompt、换模型后跑一遍？没有就直接说没有，然后讲你会怎么建。

**我的回答（原文）**

> 我没做过

**评分**：13 / 20（结论 5 · 案例 1 · 边界 5 · 深度 2）

**判断**：诚实这关过得干净，但只值三个字。这题本来不是指望你有，是想看有没有把这事**想过**。答完「没做过」等于把最容易拿的分推回去。

**不精确**：个人 demo 里做过 10 条 golden cases（提纲有记），说「完全没做过」把自己有的也说没了。

**标准答法**

> 业务上没有。这点我不绕：我们没有回归集，改完 prompt 基本靠人工看几个 case。
>
> 个人 demo 里我做过一小套，10 条，覆盖「必须出现的内容」和「不能出现的内容」，但不是生产规模。
>
> 如果让我建，三步：
>
> **收集**——从真实 bad case 和历史事故里挑，再加人工构造的边界场景，保证覆盖真实分布，不能只挑好做的。
>
> **判定**——格式类用脚本校验（schema、必填字段）；语义类按 rubric 打分，再抽样人工复核。模型判分只能当辅助。
>
> **落地**——每次改 prompt、换模型、改工具都跑全量，盯格式合规率和语义达标率；退化了先分格式退化还是语义退化，再往上定位到 prompt、上下文、工具还是模型。
>
> 它的价值是把「看起来能跑」和「稳定」分开——没有这套，prompt 改完只能靠感觉。

## Q7 · 系统设计：Chat + tool call + file diff + preview

**问**：两分钟只讲骨架和取舍：数据模型怎么切、状态机怎么定、哪两处放弃了什么。

**我的回答（原文）**

> 不清楚

**评分**：2 / 20

**判断**：说「不清楚」比硬编强，但正确动作是接一句「我按结构试着讲一下，讲不完整你打断我」，然后从数据模型开始。**空着交卷拿 0 分，搭一半至少拿 8 分。**

卡住的不是知识（这套系统自己做过，`待补答案-系统设计.md` 里有完整稿），是**没有骨架**——一旦没有结构，脑子就去找「标准答案」，然后就空了。

**骨架三段**

- **数据模型**：message 挂 tool_call（名字、参数、状态、结果）；一轮对话关联 file_change（文件、前后版本）；再关联 preview_state。文件要有**版本快照**——沙箱会被回收，状态不能只活在沙箱里。
- **状态机**：tool_call 三态（执行中/成功/失败）；chat 三态（输出中/完成/取消）；preview 九态，由纯函数算出并带原因。
- **两个取舍**：① 预览读**版本快照**，不依赖运行中的沙箱——放弃「只信实时状态」，换来沙箱回收后界面不崩；② 对话还在输出时预览**先等待**——放弃「实时跟随」，换来不出现起来一半又被改动的中间态。
