## 3.1-1 发布链路 · 60 秒标准说法

> 我们内部的发布分两类、一个例外。
>
> 常规业务服务走「测试自动、正式留人」：测试分支一推送，Orange CI 跑完自动更新测试环境；正式分支推送只构建镜像，通知到人、确认之后才发到 TKE。正式环境永远不自动发。
>
> 2026 年 7 月到 8 月的资源整合迁移把这套规矩带到了 9 个服务上。这批服务跨 4 条业务线，原来散在旧项目组的工作区，发布是构建完直接更镜像，没有管控。我们收拢到统一工作区之后，发布改走审批流。我和另一位同事分工，我负责交付链路这一段——仓库迁移、流水线迁移、配置和环境变量重新关联。两周完成，正式环境逐项确认，切换动作本身没有出事故。
>
> 例外是 QPilot Code 自己：它走自己的 stream CI，构建完自动更新负载，没接审批流——内部工具、用户是内部员工、迭代快，是权衡后留的口子。
>
> 发出去之后靠伽利略做监控上报：部署、Git 提交推送、首页核心接口这些 P0/P1 链路都有结构化数据，出问题能看到。

### 最容易被追问的 3 个点

**① 「正式环境为什么不自动发？人工确认到底在卡什么？」**

> 卡的不是代码，是放行动作。代码质量靠 MR 评审和测试环境的自动验证；人工那一步只回答一个问题——这次正式变更现在要不要上。这类后台是内部运营在用，数据改动影响面大，自动发布省下的几分钟，抵不上一次误发的代价。

**② 「QPilot 没接审批流，出了事怎么办？是不是不规范？」**

> 这是权衡，不是疏忽。QPilot 迭代快，接审批会把一天多发拖成一天一发；它的用户是内部员工，影响面可控，所以用「快发布 + 监控 + 快回退」换掉了「慢审批」。真要承接外部用户或更重的业务，接审批流是第一件要补的事。

**③ 「审批流会不会拖慢发布？测试和正式的镜像怎么保证是一回事？」**

> 慢的只有正式那一下，测试环境照常全自动，日常迭代不受影响——迁移那两周，9 个服务逐项确认也没超期。镜像一致性靠分支模型：正式环境上线的镜像一定出自正式分支那次构建，测试跑通、人工放行之后才发，不存在「测试验了一个、正式发了另一个」。

## 3.1-2 灰度与回滚

### 先如实交代（约 30 秒）

> 灰度这块我如实说：我们没有建正式的灰度体系——没有按比例放量，也没有灰度控制台。实际在用的是三个替代手段：一是测试环境全量先跑、正式环境人工逐项确认；二是 QPilot 做了双环境的最小隔离，一个项目分预览和正式，环境变量文件分开、数据库可选隔离；三是真出问题就回滚止血——统一登录接入那次，用户项目的对外接口被认证拦住不可用，我们先把刚配好的接入整体撤掉，让业务先恢复，之后再分三步重新接回去。

### 如果要做，我会这么设计（三档，成本从低到高）

一句原则：灰度不是「分几批发」，是把爆炸半径从一次发布里切出来。

**第一档：按功能开关。** 新功能合进去默认关，开关放配置中心（七彩石），先对白名单开，稳定了再全量。代码发布和功能释放解耦，出问题关开关就行，不用回滚镜像——QPilot 这种迭代快的平台最适合先做这档。代价是开关债务：每个开关要有下线计划，且新旧两条代码路径并存，测试组合翻倍。

**第二档：按用户。** 在网关或登录态那层识别用户，内部员工先走新版本。QPilot 天然适合：用户本来就全是内部员工，「自己先吃狗粮」就是第一批灰度。代价是同一个用户得稳定落在新版上，否则体验割裂。

**第三档：按实例。** TKE 上新旧版本各起一组实例，入口按比例分流量，从小比例起步，盯伽利略的错误率和耗时，正常再放大。这一档救的是开关救不了的场景，比如带数据库变更的发布。代价最重：旧版本要一直活着，资源翻倍；两个版本同时写库，表结构只能加字段不能删改。

### 回滚的三条路径与代价

前提：回滚的前提是知道「发过什么」。QPilot 的部署记录里存了 `sourceVersionId`，版本历史能看到每个已发布版本——没有版本记录，回滚就是空话。

| 路径 | 速度 | 代价 / 限制 |
|---|---|---|
| 配置 / 开关回退 | 秒级 | 只对功能级问题有效；已经写进库的数据不会跟着回去 |
| 镜像 / 版本回退 | 分钟级 | 全体用户同时回旧版；若这次带表结构变更，旧镜像可能跑不起来 |
| 入口 / 流量回退 | 最快止血 | 粒度最粗，不动服务只切流量；重放要重来一遍，之前配的工作可能作废 |

### 边界（防临场说过头）

- 三档灰度是设计方案，我没有在生产上跑过；能讲的实战只有登录接入那次入口回滚，和双环境最小隔离。
- 双环境是「最小隔离」，不叫灰度：它分开的是预览和正式的环境变量，不是新旧版本的流量比例。

## 3.2 排查 · 排查顺序（说流程，不堆名词）

| 问题 | 排查顺序 | 能挂什么 |
|---|---|---|
| 页面打不开 | ①先分清是「打不开」还是「打得开但白屏」：超时/DNS/证书 → 看请求有没有到；②看状态码：502/504 是后端或网关，404 是路由或回源规则，401/403 是身份；③看入口层：负载均衡监听器、回源端口、转发规则；④最后才是前端资源与路由 | 案例 6：预览域名 404，根因是转发规则只配在 443 监听器下，回源配成 80 就走了默认后端 |
| AI 一直转圈 | ①先确定是「模型没回」还是「状态没更新」：看有没有流式帧到达；②看后端状态机当前处于哪一态、判断原因是什么（我们的状态是带原因回传的）；③看端口/进程：预览类问题查端口占用与 LISTEN 状态；④看代理是否缓冲 | 案例 3：端口泄漏、出站连接被误判成端口占用、沙箱回收后判成无项目 |
| SSE 断线 | ①看前端是否收到最后一帧与结束标记；②看恢复接口返回：有内容说明原进程还在，`204` 说明这轮已结束或进程重启；③看中间层读超时与心跳；④看网关/代理是否缓冲 | 模拟问答合集（断线恢复链路完整） |
| 线上报错定位到具体请求 | ①先有 trace_id 贯穿：入口生成、逐层透传、日志与上报都带上；②按 trace_id 串起网关日志、服务日志、调用链；③区分是「请求级错误」还是「语义级错误」（业务拦截不该算错误率） | 案例 6：同 trace_id 双发；`Abandoned → WARNING` 的修正 |
| 依赖服务连不通 | ①先分层：DNS → TCP → TLS → 应用层，逐层确认卡在哪；②再确认是不是网络策略（跨环境 ACL、白名单）；③对比同环境其他服务是否也连不通，判断是单点还是网段；④临时方案与长期方案分开讲 | 案例 8：ClickHouse 被 ACL 拦，权衡白名单 / 复用 / 自建后选自建 |

## 3.3 监控 · 三题

**trace / metrics / log 分别解决什么**

> 三者不是替代关系，是三种提问方式。metrics 回答「有没有异常、量级多大」——错误率、耗时、QPS，用来告警；trace 回答「这一次请求慢在哪、错在哪一环」——跨服务、跨工具调用串起来看；log 回答「当时到底发生了什么」——细节和上下文。我的做法是先用 metrics 发现，再用 trace 定位到某一次请求，最后用 log 看现场。

**你们报了哪些、怎么分级**

> QPilot 里把部署、Git 提交推送、首页核心接口接入伽利略结构化上报，按 P0/P1 分级——P0 是影响主链路可用性的，P1 是影响体验但可降级的。分级的意义不是排名，是决定告警给谁、要不要半夜叫人。

**AI 应用的监控和普通服务有什么不同**

> 三点。第一，除了错误率和耗时，还要看 token 与成本——同样是 200，成本可能差十倍；第二，一次请求内部有工具调用树，要看每一层工具的耗时和失败，而不是只看最外层；第三，错误率的语义变了：业务主动拦截（取消发布、用户追问）不是故障，如果按普通服务的异常口径上报，整条 trace 会被标红，大盘就失真。这一条我实际改过——把 `ERROR + Abandoned` 改成 `UNSET + WARNING` 加业务标记。

## 3.4 性能 · 两题

### 3.4-1 首屏慢怎么定位

**口述版**

> 我按「拿不到、拿太多、算太久」三层排。第一层看网络：DevTools 的瀑布图，TTFB 高就是服务端或链路慢，资源串行等待就是依赖顺序有问题，这时候优化前端没用。第二层看体积：首屏是不是打进了不该进的包，路由级有没有做懒加载，第三方库有没有按需引入，这一步用构建产物分析看，不靠猜。第三层看渲染：LCP 元素是什么，主线程有没有长任务，首屏是不是被同步计算或者大列表一次性渲染卡住。顺序上先排除前两层，因为它们往往一次改动收益最大；第三层才轮到具体组件优化。

**追问备用**

- 怎么证明是前端的问题？——在弱网和本地各测一次，如果本地也慢就是渲染或计算问题；如果只有弱网慢，就是资源体积或请求数问题。
- 首屏优化有哪些常见手段？——路由懒加载与代码分割、关键资源预加载、图片按需、减少首屏请求数、把非关键逻辑延后到空闲时间。

**边界句**

诚实说法：我没有做过完整的首屏性能专项，上面是排查顺序；我实际做过的是与首屏相关的工程侧改动（前端 API 地址改环境变量、正式环境 CI 迁到 TKE），不是性能调优成果。

### 3.4-2 输入卡顿怎么排查

**口述版**

> 输入卡顿通常是三个原因之一。第一，输入框的值被提升到了大组件的顶层状态，每敲一个字整棵消息树重渲染——解法是把输入状态和列表状态隔离，输入值不要上浮。第二，每次输入都在同步做重计算，比如搜索、高亮、代码块解析——这类要延后或放到 worker，用低优先级更新。第三，被高频流式更新抢了主线程——流式帧要合并批量更新，不能一帧一次强制同步渲染。我在会话模块里做过相关的一件事：模型输出期间原来直接禁用输入框，用户只能干等；改成前后端持久化的输入队列之后，输出时用户照样能打字、排队、编辑，输入框的更新不依赖消息流的节奏。

**追问备用**

- 怎么确认是重渲染？——React DevTools Profiler 录制输入过程，看每次按键触发了哪些组件、耗时多少。
- 队列持久化为什么放后端？——刷新或换设备后队列还在，不会因为页面重载丢掉用户输入。

**边界句**

诚实说法：输入队列是产品与状态设计上的改动，我没有做过输入性能的量化优化（没有 profile 数据），不当性能成果讲。
