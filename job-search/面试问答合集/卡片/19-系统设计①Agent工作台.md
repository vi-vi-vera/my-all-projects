# 卡 19 · 系统设计① AI Agent 工作台（8 分钟）

> 定级：L2→L3（口述稿成型，抗追问已过两层）｜ 2026-11-22（D6）
> 用法：面试前读一遍骨架，别看全文。**所有"现状"都按下面口径说，不许升级也不许降级。**

## 五步结构（8 分钟分配）

| 步 | 用时 | 内容 |

## 第 1 步：澄清（问完必须自己兜底）

四个维度：**目标用户 / 规模 / 核心场景 / 哪些先不做**。

面试官说"你定"时立刻接：

> "那我按**内部工具**假设：用户是研发和运营两类、权限不同；日活会话百级；**单任务可能跑几十分钟**，不是一问一答；不做多 Agent 编排，也不做训练和微调。"

## 第 2 步：六层 + 切分理由

| 层 | 职责 | 现状口径 |
|---|---|---|
| 接入层 | 鉴权、协议适配（SSE）、入口 | web + 企微 bot **两条入口独立并存** |
| 会话与任务层 | 消息树、流、取消、断线重放、编辑重发 | 流式 + `streamId` 重放**已实现**；**chat 长任务转异步没做** |
| 编排层 | ReAct 循环、上下文组装、工具调用 | Claude Agent SDK、单 Agent + Skills；**摘要压缩没做** |
| 能力层 | 工具/MCP、Skills 按需加载、权限、沙箱 | 有；沙箱跑在 **OpenSandbox**（k8s 容器池，2C4G + DIND sidecar）；git-write 受控令牌**已实现未接前端** |
| 状态层 | 消息存储、记忆、文件产物 | 消息 **append-only**；长期记忆 **dev 分支做完一版、未合主干** |
| 平台支撑层 | 模型接入、可观测、成本、**评测** | OTel `gen_ai.*` 有生产实战；cache token 单列；**评测只有个人 Demo 10 条** |

**必说的切分理由（这是结构感的分）：**

> "**会话层和编排层必须分开**：会话管'这段历史能不能恢复'，编排管'这一次模型怎么想'。混在一起，断线重放和任务恢复会互相污染——我们的痛点恰好在这条缝上。"

## 第 3 步：一条主流程

> 用户发一句话 → 接入层建 `streamId`、回 SSE → 会话层挂到消息树、按**四级优先级**组装上下文（系统提示 / 技能 / 历史 / 当前输入）→ 编排层走 ReAct → 模型返回 `tool_use` → 能力层**在沙箱里**执行 → 结果回灌 → 流式吐回、落库、打 trace → 断线用 `streamId` **全量重放**。

一句话收：**"一条消息穿过六层，每层只做一件事，失败点各自独立。"**

## 第 4 步：三个设计点

### ① 会话恢复 vs 任务恢复（含金量最高）

> "这是两个问题。
> **会话恢复做了**：第三方库生成 stream 观测对象，里面有 `streamId`；每来一个 chunk 就按 `streamId` 落一条。用户回来重放，前端**全量覆盖渲染**，之后继续接流式。
> **任务恢复没做**：Claude Code SDK 不能单点重发，只能清上下文重建。代价两条——重建的上下文和原来那份**有出入**；前缀一变**命中不了缓存**，直接变贵。所以选择不做，改成探活 + 失败返回 + 用户重试。"

### ② 为什么 chat 不转异步

> "**没做**。两条入口独立，不能互转。如果能重来，会在会话层把'同步等还是异步跑'做成一个字段，上层不感知。代价是取消、进度、部分结果全要重做。"

### ③ 沙箱：安全 vs 能力

> "沙箱用的是 **OpenSandbox**：k8s 上从**预热池**分配容器沙箱（2C4G，带 **DIND sidecar**，所以沙箱里能 docker build/push），命令和文件操作走沙箱内的 **execd 守护进程**。选容器而不是更轻的方案，是因为要真能跑构建和部署；代价是每个沙箱 2C4G 的资源成本，以及 DIND 把 docker daemon 放进了沙箱、放大了攻击面。"

## 第 5 步：收口

> "两个瓶颈：**恢复语义**（会话能重放、任务不能续跑）、**评测**（只有 10 条 golden cases，改动靠人肉回归）。下一步先补评测——没有回归集，不敢动架构。"

## 抗追问（这两层今天被追过，记答案）

| 追问 | 答法 |
|---|---|
| `streamId` 谁生成、换设备怎么知道？ | **恢复入口是 `sessionId`，不是 streamId**。前端 `useChat(resume)` 请求 `GET /api/agent/chat/{sessionId;<suffix>}/stream`，`sessionId` 是持久化会话 id（路由/会话记录里，跨设备可拿）；后端按 `streamKey = sessionId[:scope]` 去 Redis 反查 streamId。`<suffix>` 区分主 chat / `thread:` 子线程 / `start-service` 临时流 |
| Redis 存什么？ | **只存 streamId 元数据**（JSON：streamId / conversationId / stage / lastProgressAt / registeredAt，TTL 3600s）。**真正的 chunk 流在进程内存里**（`resumable-stream` 库）。服务重启 → 内存流丢失、Redis 里 streamId 还在 → `resumeExistingStream` 抛 "Timeout waiting for ack" → 返回 204，前端走正常重载 |
| TTL 到期但任务还在跑？ | TTL 固定 3600s、**没有续期** → 超 1h 的长任务 key 会过期，resume 反查不到（但流还在内存里）。这是现状，主动说是局限 |
| 探活误杀怎么办？ | **看护不是杀进程，是把 RUNNING 的 conversation 标记 failed**（`conversation-running-recovery`，每 60s sweep）。两层判据：① `max(createdAt, updatedAt)` 的 grace（普通 30s / 临时 5min）② `probeActiveStream` 里 `lastProgressAt` + 5min stale，再实际 resume 验证内存流。`lastProgressAt` **只在注册时设一次、无逐 chunk 刷新** → 等价总时长，长任务会被误判；修法 = 写 chunk 即刷新 |
| 进程只是慢、没死呢？ | 同上——这正是"没有心跳"的直接后果，主动说出来 |

## 口径红线（说错即硬伤）

- **任务恢复：没做**，不要说"在做/部分做"
- 长期记忆：**dev 分支做完一版、未合主干**
- 评测：**只有个人 Demo 的 10 条**，业务上没建正式回归集
- 单 Agent + Skills，**没有多 Agent 编排**
- 沙箱是 **OpenSandbox 容器沙箱**（k8s 预热池 + DIND sidecar），**不是进程隔离**，也不是自研隔离
