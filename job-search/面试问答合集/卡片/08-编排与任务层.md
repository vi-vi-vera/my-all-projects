# 卡 08 · Agent 编排（提纲 1.4）

> 定级：L2（概念 + 任务层有实战）｜ 2026-11-17
> 口径：任务层实现都在 **`dev/wecom-bot-dispatch` 分支**（第 2/3/5A 步）；显式 Plan 层、chat 转异步**都没做**。

## 3 句骨架

1. **编排分两层：循环层归模型，任务层归工程。** 循环层是「每一步做什么」（ReAct / Plan）；任务层是「一次运行怎么排队、并发、失败、卡死」。我做的是**任务层**——这层跟模型无关，任何长任务系统都需要它。
2. **判断 ReAct 还是 Plan，看「那个 while 循环是谁写的」。** 自己写 = 你实现 ReAct；SDK 帮你转 = 你在配置 ReAct。Plan 不是替换 ReAct，是**套在它外面的一层壳**。
3. **Plan 的价值不是「更聪明」，是「计划变成可产物」**——可展示、可审批、可回放、可评测。ReAct 的推理是隐式的，只能评结果。

## 一、三层架构（先画边界，再讲能力）

```
① 模型循环层   SDK 的 tool loop（ReAct）        ← 两条链路共用
② 交互层       chat panel：SSE / 取消 / 断线续传 / 九态状态机 / 竞态收敛
③ 任务层       dispatch：队列 / 串并行 / 重试 / 卡死看护 / 定时调度
```

**② 和 ③ 共用同一个执行内核和同一套受控工具，差别只在外壳的可靠性要求。**

| | 交互层（chat） | 任务层（dispatch） |
|---|---|---|
| 用户 | **在线等** | **不在场** |
| 时长 | 秒～分钟 | 分钟～几十分钟 |
| 失败 | **报给用户，他自己再发** | **系统自愈** |
| 中断 | 用户主动取消 | 系统判死（看护）|
| 难点 | **竞态收敛** | **并发与自愈** |
| 指标 | TTFT、流不中断 | 成功率、重试率、卡死率 |

> **判据一句话：用户在场就让他自己重试，用户不在场系统必须自愈。**
> 所以 ② 最难的词是「取消」（把控制权还给用户），③ 最难的词是「自愈」（从用户手里接管）。

## 二、循环层

**演进**：单次工具调用（不会自己决定下一步）→ ReAct（Thought/Action/Observation 循环）→ Plan-and-Execute（先出图纸）→ **混合（外层粗 Plan + 内层每步 ReAct + 失败只重规划该段）**

| | ReAct | Plan-and-Execute |
|---|---|---|
| 决策时机 | 每一步 | 开头一次（后可重规划）|
| 灵活 | 高，边走边改 | 低，遇错要重规划 |
| 步数成本 | **不可控** | 可控，可并行 |
| 可观测 | 差（推理隐式）| 好（计划显式）|
| 可审批 | 做不到 | **危险动作执行前可拦** |
| 适合 | 探索型（排查、找 bug）| 流程明确、有高危动作 |

> 演进的一句话：**2023 年比谁更聪明，2026 年比谁更可控；可控的前提是把隐式推理变成显式产物。**

**五步 ReAct 骨架（被问“你怎么实现 ReAct”就写这个）**
```ts
const messages = [{ role: 'user', content: task }]
for (let step = 0; step < MAX_STEPS; step++) {
  const res = await llm(messages, { tools })
  messages.push(res)
  const calls = res.toolCalls ?? []
  if (calls.length === 0) return res.content      // 没有工具调用 = 说完
  for (const c of calls) {
    const out = await execTool(c)
    messages.push({ role: 'tool', content: out })  // 结果回灌
  }
}
```

**现状口径**：没有显式 planner，规划交给模型，工程侧做的是**约束工具面 + 状态收敛**——严格说是 ReAct 形态，但把活动范围收窄了。若要加 Plan，加在 `agent.run()` 外面：一次调用出 steps[] → 逐步 run → 失败只重规划当段，成本很低。

## 三、Cursor 三个模式（产品层的对照，别当术语用）

| 模式 | 范式 | 差别 |
|---|---|---|
| Ask | **不是 ReAct**（无 Action） | 只读，无副作用 |
| Craft | **ReAct（tool loop）** | 可写，默认信任 |
| Plan | **Plan-and-Execute + 人工闸门** | 危险动作执行前要签字 |

> **范式解决「它怎么想」，档位解决「敢不敢让它做」。** 产品要三个档，是因为这是两个不同的问题。

## 四、任务层：五个部件

**① 并发：按副作用边界分**
判据不是「读/写」，是：**这个操作会不会改变别的任务也依赖的共享状态？**
- 会 → 串行（两个任务同时改同一项目 → 后者覆盖前者）
- **一方在写，另一方在读 → 也不安全**（读到一半状态变了）
- 代价：串行吞吐 = 最慢那个，且一个卡住堵一排 → **所以串行必须配超时和看护**（看护不是补丁，是串行设计的配套）

**② 重试：能重试 ≠ 该重试**
> **判据：同样输入再跑一次，结果会不会不同？** 会不同 = 环境性，可重试；一定一样 = 确定性，别重试。

| 可重试 | 不该重试 |
|---|---|
| 超时、5xx、连接错误、423 占用、服务重启、卡死 | prompt 校验失败、参数非法、权限不足、业务规则拒绝 |

三个必备细节：**上限**（防放大故障）+ **退避**（等环境恢复）+ **复用原 DB 行**（否则分不清「一个任务试三次」和「三个任务」）
**Agent 独有**：重跑时把失败原因注入 prompt —— `[自动重试 第N次] 上次失败原因：X，请检查项目状态并规避`。**普通服务是原样重放，Agent 可以带着教训重来。**
风险：重试前要确认幂等（上次已推镜像，重试会推第二次）。

**③ 卡死看护：超时 ≠ 卡死**
单次调用超时管不了「整体卡在第 12 步反复重试」。实现：5 分钟一轮 sweep，`running` 且 `updated_at < now() - 30min` → 清僵尸会话 → 标失败 → 走重试链。
**为什么先清僵尸会话**：不清的话重试请求会被同一 session 的 **423 锁**挡在门外，然后空等——看起来像「重试了但没效果」。这是真踩的坑。

**④ 定时调度：核心不是准时，是幂等**
多实例同时扫表会重复触发 → **抢占式推进 `next_run_at`**（`UPDATE ... WHERE next_run_at = 本次周期`，影响行数 = 1 才算抢到），本质是乐观锁。
> **调度系统第一指标是幂等。晚 10 秒没人发现，重复跑一次可能删两次数据。**

**⑤ 三个只有真做过才知道的坑**
- **时区**：应用侧 `Date` 与 DB 会话时区（PRC）差 8 小时 → 漏行。**凡拿时间和 DB 比，一律 SQL 端 `now()`**
- **宽限基准**：恢复器按「当前时间往前推 N 分钟」算，导致重启后刚创建几秒的任务被漏 → 改成以**进程启动时刻**为基准
- **状态外化**：企微通知区分「正在重试 🔄」与「终态失败 ❌」，发 `session_task_retrying` 事件让面板实时刷新 —— **自动重试最怕用户以为它挂了**

## 五、语义 / 机制 / 有效语义（今天最大的收获）

| 层 | 内容 |
|---|---|
| **设计语义** | 想抓什么（如「无进展」）|
| **实现机制** | 用什么代理指标（如 `updated_at`）|
| **有效语义** | 机制实际判的是什么（**总时长**——因为运行期没有心跳，时间戳不动）|

**三层的差额 = 代理指标失效。** 追问法：
> 「你怎么知道它没进展？」→「看最后更新时间。」→ **「那它跑的时候会不会更新这个时间？」** → 到底。

**安全话术**：
> 「我用的是『最后更新时间超 30 分钟』。但运行期没做心跳，`updated_at` 只在状态跃迁时更新，所以实际是**总时长兜底**，不是真正的无进展检测。代价是可能误杀本来就要跑很久的任务——要改就得让执行过程按步上报心跳。」

三种改法的优先级：**心跳（正解，让语义和实现对齐）＞ 拆步骤（治本但成本高）＞ 调高阈值（最差，只是推迟误杀）**。

## 六、三档口径（讲自己系统时的固定框架）

| 档 | 1.4 里对应什么 |

> 大多数候选人只会说「做了 / 没做」。能说「做了一半、缺哪一段、为什么缺」，层次立刻不同。

## 我的理解（原话 · 2026-11-17）

**并发的判据**
> 「区分两个任务能不能并行，主要看它们是否依赖同一个资源、且某一方还会改动它；如果有写任务在改资源，就不该有其它任务跟它并行。」

**不该重试的**
> 「权限问题、工具参数不合规，这种就不该重试。」

**卡死阈值误杀的三种改法**
> 「一种调高阈值，但真卡死时用户等待成本更高；一种让任务主动上报心跳；还有一种把长步骤拆成多个小任务。」

**chat 的状态收敛**
> 「chat 状态和预览状态是独立维护的，但展示时会联动，而且预览启动实际也调 chat 接口，所以启动和会话流互斥。最终把这个判断收归到同一个函数里，两边各自维护状态，函数里综合算展示态。」

**最有价值的一次质疑**（说明真在读代码）
> 「不是说定位的是超长时间**没有进度**的任务吗，为什么看原理还是按整体耗时算的？」
> → 这一问问出了「语义 ≠ 实现」，是本科目最值钱的发现。

## 最容易被追死的一问

> **「你怎么知道任务卡住了？」**
> → 看 `updated_at` 超 30 分钟。**追问「运行期会不会更新它」** → 会暴露：没有心跳，实际是总时长兜底。**主动说这个局限**，并给出改法（按步上报心跳）。
