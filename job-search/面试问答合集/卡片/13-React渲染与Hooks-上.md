# 卡 13 · React 渲染与 Hooks（上）

> 定级：L2+（S1 已过，机制能推演；待 S2 补 hooks 全量）｜ 2026-11-18
> 本卡覆盖：渲染模型与两阶段、setState 与批处理、Fiber、hooks 顺序、useEffect、stale closure、useMemo/useCallback、key
> **待补**（S2）：useRef 三用途、useReducer、forwardRef / useImperativeHandle、自定义 hook 设计原则

## 3 句骨架

1. **组件就是函数，渲染就是调用它一次**——由此推出：每次渲染局部变量全新、state 是快照、闭包会过期、hooks 必须按固定顺序调用。
2. **hooks 靠「调用顺序」识别身份，不靠名字**，所以不能进 if/for；同理 `key` 靠值识别列表项身份，所以不能随便用 index。**凡靠位置识别 identity 的地方，位置一变就全错。**
3. **React 的性能问题 99% 不是「算得慢」，是「引用不稳导致比较失效」**——`memo`/依赖数组都只做 `===` 比较，不去比内容。

## 一、渲染模型（一切推论的源头）

```
state 变化 → 重新执行组件函数 → 得到新的 UI 描述 → diff → 只改差异
```

**三个推论**

| 推论 | 表现 |
|---|---|
| 每次渲染函数体重跑 | 局部变量、props 全是新的 |
| state 是**那一次渲染的快照** | 不是"会变的变量"；下次渲染是新的一份 |
| 闭包捕获的是**引用**不是值 | effect 用 `[]` 会永远读到第一次的值 |

**这不是 React 发明的，是 JS 的引用语义**：
```js
{a:1} === {a:1}   // false —— 内容一样，不是同一个对象
```

## 二、hooks 靠顺序识别（为什么不能进 if）

**函数组件没有记忆**——调用完局部变量全丢。所以记忆必须存在组件外部，**hook 就是访问那块存储的接口**。

简化实现（这就是"为什么靠顺序"）：
```js
let hooks = [], cursor = 0
function useState(init) {
  const i = cursor++
  if (hooks[i] === undefined) hooks[i] = init
  return [hooks[i], v => { hooks[i] = v; rerender() }]
}
```

**写在 if 里的后果**：某次渲染跳过了一个 hook → 后续所有 hook 的索引整体前移 → **读到别人的状态**（不是报错，是静默错乱）。

**规则**：`if (x) { useState() }` ❌ ／ `const [v] = useState(); if (x) {...}` ✅
**一句话**：**hook 的「调用」不能被条件包住，hook 的「内部逻辑」可以有条件。**

**自定义 hook** = 自己写的、以 `use` 开头的函数，内部调用别的 hook。可以放自定义 hook（因为它每次渲染都被调用，顺序不变）。
**为什么必须 `use` 开头**：给 ESLint 插件识别用，命名不规范保护就失效。

## 三、useEffect

**为什么需要它**：渲染阶段必须纯净（可能被多次执行/中断重放）；副作用（请求、订阅、定时器）要单独放。

| 写法 | 时机 |
|---|---|
| `useEffect(fn)` | **每次渲染后**都执行 |
| `useEffect(fn, [])` | 只在挂载后一次 |
| `useEffect(fn, [a])` | 挂载后 + `a` 变化后 |

**依赖比较是 `Object.is`（引用比较），不是深比较。**

**cleanup 跑在两个时机**：① 下一次 effect 执行**之前** ② 组件卸载时。目的：保证任一时刻只有一份副作用在工作。

**漏 cleanup 的具体后果**：定时器叠加（请求翻倍）、监听累积（回调触发 N 次）、SSE/WS 连接泄漏 + 往已卸载组件 setState。

**StrictMode 开发环境会故意「挂载→卸载→再挂载」**，专门用来逼出没清理干净的副作用。

## 四、两个独立问题（**最容易答错，重点记**）

> ⚠️ 这两件事**不是**一个四象限——它们互不影响，必须分开判断。

### 表 A：依赖里「写没写」→ 决定**对不对**

| | 依赖没写（`[]`） | 依赖写了（`[x]`） |
|---|---|---|
| **x 的语义不会变** | ✅ 正常 | ✅ 正常（可能多跑，但值对）|
| **x 的语义会变** | ❌ **stale**：永远用旧值（静默错误）| ✅ 变了就重建 |

> `[]` 是在断言「它永远不变」。**断言错了就静默出错**，而且不报任何错。

### 表 B：依赖写了之后，引用「稳不稳」→ 决定**跑几次**

| | 引用稳定（useCallback / ref） | 引用不稳定（每次新建） |
|---|---|---|
| 结果 | 只在语义真变时重跑 ✅ | **每次渲染都重跑**（白跑）|

**两个失败模式是不同性质的**

| 模式 | 真实症状 |
|---|---|
| **stale**（表 A 左下）| 定时器还在往**上一个会话**发消息；回调读到旧 state |
| **反复重跑**（表 B 右侧）| 定时器**叠加**（cleanup 缺失时）、请求风暴、订阅重复 |

> **依赖数组只回答「什么时候该重新执行」；引用稳定只回答「会不会被误判成变了」。**
> 前者管正确性，后者管跑几次——**两个问题，两张表，别合并。**

**两种解法**
```jsx
// A. latest ref（定时器只建一次，且永远拿最新值）
const onSendRef = useRef(onSend)
onSendRef.current = onSend
useEffect(() => { const id = setInterval(() => onSendRef.current(), 1000); return () => clearInterval(id) }, [])

// B. 父组件 useCallback 稳住 + 子组件写进依赖（真需要"变了就重建"时用）
```

**顺带**：`setState(prev => prev + 1)` 也是同一思路——**不读外部变量，让 React 给你最新值**。

## 五、闭包（不是 return 造成的）

```jsx
useEffect(() => {
  setInterval(() => onSend(), 1000)   // 这个回调引用了外层 onSend → 它就是闭包
}, [])
```
**只要有函数引用了外层变量就是闭包，和 `return`（cleanup）无关。** `return () => clearInterval(id)` 只是在"返回清理函数"，恰好也是函数而已。

⚠️ **父组件传函数用 props，React 没有 `emit`（那是 Vue）**。

## 六、useMemo / useCallback

**先记住它解决什么**：每次渲染，函数体里的对象/函数都是新的 → 传给 `memo` 子组件时浅比较判定"变了" → 子组件白渲染。

**三个真实场景（不在里面就别包）**

| 场景 | 写法 |
|---|---|
| 对象/数组当 prop 传给 `memo` 子组件 | `const config = useMemo(() => ({...}), [])` |
| **Context 的 value** | `useMemo(() => ({...}), [所有字段])` |
| 对象/函数要进别的 hook 依赖 | `const filters = useMemo(...); useEffect(..., [filters])` |

`useCallback(fn, deps)` ≡ `useMemo(() => fn, deps)`，函数版。

**判据一句话：有没有人拿它的引用做 `===` 比较？没有就别包。**

**四种白搭的情况**：计算很便宜／依赖每次都变／**子组件没被 `memo` 包**／依赖数组写错（缓存了过期值，比不缓存更糟）。

**优化顺序**：减少 state → 拆组件 → 状态下沉 → 最后才 memo。

## 七、Context 的 value 必须 useMemo

Context 的 value **按引用比较**：每次 Provider 渲染新建对象 → **所有 consumer 全部重渲染**，哪怕它们用到的字段没变。

```tsx
const value = useMemo(() => ({ a, b, c }), [a, b, c])   // ✅ 依赖要覆盖每个字段
```
> 这也是「Context 该不该拆」的由来：**依赖数组太长本身就是维护风险**，所以有时直接拆成多个 Context。

## 八、key 与 hook 是同一个原理

| | 身份靠什么 | 位置变了会怎样 |
|---|---|---|
| hooks | 调用顺序 | 状态串位 |
| 列表 key | key 的值 | 用 index 时删中间项 → 后续 key 全变 → 复用错、**输入框内容跑到别的行** |

## 九、S1：两阶段与更新机制（2026-11-18）

### 机器总图（六层）

```
【0】组件函数 + hooks
      ↓ JSX → React.createElement
【1】React 元素（普通对象，一次性"图纸"）
      ↓ reconcile
【2】Fiber 树（长期存活的"施工档案"，可中断的工作单元）
      ↓ Scheduler 决定何时跑、跑多久让出
【3】render 阶段（Reconciler）—— 只算、不碰 DOM、可中断
      ↓ workInProgress 树 + 副作用标记
【4】commit 阶段（Renderer）—— 真改 DOM、同步、不可中断
【5】浏览器绘制
【6】useEffect 异步执行（绘制之后）
```

### React 元素 ≠ Fiber

| | React 元素 | Fiber |
|---|---|---|
| 是什么 | `{type, props}` 普通对象 | 长期存在的节点对象 |
| 生命周期 | **每次渲染新建**，用完即弃 | **跨渲染存活**，被复用更新 |
| 存什么 | 只描述长什么样 | 状态、DOM 引用、父子兄弟指针、优先级、副作用标记 |

> 元素是"这一版的设计图"，Fiber 是"这间房的工程档案"。**每次渲染是拿新图纸更新旧档案，不是推倒重建。**

### render 阶段做三件事

```
① 执行组件函数 → 拿到新的子元素
② 和旧子 Fiber 对比 → diff（key 在这里决定复用）
③ 打标记 → 插入 / 更新 / 删除
```
**完全不碰 DOM** → 所以能被打断、丢弃重来。

### commit 阶段三个子阶段

| 子阶段 | 干什么 |
|---|---|
| before mutation | 读 DOM（`getSnapshotBeforeUpdate`） |
| **mutation** | **真正改 DOM** |
| layout | 同步跑 `useLayoutEffect` / `componentDidMount` |

**同步、不可中断**——不能让用户看到改了一半的界面。结束后切换 current ↔ workInProgress（**双缓冲**）→ 浏览器绘制 → 最后才跑 `useEffect`。

### setState 三问（分三层答，别一句"异步"）

| 问 | 答 |
|---|---|
| 调用本身同步吗 | **是**，代码继续往下走 |
| 能立刻读到新值吗 | **不能**，当前渲染里的 state 是快照 |
| 渲染是立刻的吗 | **不是**，攒批后统一渲染 |

```jsx
setN(n + 1); setN(n + 1); setN(n + 1)   // 点一次 → 1，不是 3（三次都用同一个旧 n）
console.log(n)                           // 0（旧快照）
console.log(dom.textContent)             // 0（还在事件处理里，commit 没到）
```
要累加必须 **函数式更新** `setN(p => p + 1)`（每次基于上一次结果）。

### 批处理：18 的关键变化

| 版本 | 范围 |
|---|---|
| 17 及之前 | **只在 React 事件处理里**批；setTimeout / Promise / 原生事件不批 |
| **18** | **自动批处理扩展到所有场景** |

**边界是「同步执行块 / 微任务」**：`await` 让出后，flush 微任务已经跑完，恢复时的 `setState` 开新一批 → 渲染两次。
`flushSync(() => setN(1))` 可强制同步刷新（需要"先更新 DOM 再读"的场景）。

### Fiber 解决什么（不要说"性能更好"）

**问题**：老架构递归遍历，一旦开始必须跑完 → 树大就长时间占用主线程 → 交互和动画掉帧。
**解法**：树改成**链表**（`child` / `sibling` / `return`），处理完一个节点检查是否该让出，**记下下一个该处理的节点**，空闲再续。
**结论**：**把「不可中断的递归」改造成「可中断、可恢复的遍历」**，于是才有了优先级调度（用户输入可打断低优先级渲染）。

### useLayoutEffect vs useEffect（用"第几步"记）

| | 位置 | 代价 |
|---|---|---|
| `useLayoutEffect` | **commit 的 layout 子阶段（绘制前）** | 阻塞绘制，但**没有中间态闪动** |
| `useEffect` | **绘制之后** | 不阻塞，但用户可能先看到中间态 |

### 知识点定位表（零件在机器的哪里）

| 知识点 | 位置 |
|---|---|
| 组件是函数、state 是快照 | 第 3 层：render 每次重新执行函数 |
| hooks 靠顺序 | 第 1 层：Fiber 上挂着 hooks 链表 |
| 副作用不能写在渲染里 | 第 3 层可中断/可重放 → 挪到 commit 后 |
| memo / useMemo / useCallback | 第 3 层：决定该节点要不要重新执行 |
| **key** | **第 3 层 diff**：决定新旧子节点怎么配对复用 |
| Context value 要 useMemo | 第 3 层：value 变 → 所有 consumer 重渲染 |
| 批处理 | 第 ③–⑤ 步：攒批 + 微任务 flush |
| Fiber 可中断 | 第 2–3 层：链表 + 时间片 |
| useLayoutEffect / useEffect | 第 ⑨ 步 / 第 ⑫ 步 |
| 双缓冲 | 第 ⑩ 步：算完再切 |
| 错误边界 | 第 3 层（渲染期）能接；事件/异步接不住 |

## 我的理解（原话 · 2026-11-18）

> 「因为 React 的组件实际是个函数，每次状态更新都会用最新状态重新计算一次组件，拿到虚拟 DOM，所以说 useState 返回的不是变量，而是最新状态的快照。」

> 「memo 只会进行浅比对，两个一样内容的对象会因为地址不一致而 false，对应父组件重新渲染传值这种情况。如果内容不变不需要渲染，就用 useMemo 把对象包一层，这样就会一直保持这个引用。」

**答对但需要修的一处**
| 当时说的 | 修正 |
|---|---|
| 「父组件只是重渲染，引用变化 → 造成不必要的副作用执行」 | 这只在**依赖里写了它**时成立；依赖是 `[]` 时**什么都不会发生，而是静默失效** |

**踩过的坑**
- 以为闭包是 `return` 造成的（实际：引用外层变量就是闭包）
- 以为 React 有 `emit`（那是 Vue；React 一律函数当 prop）
