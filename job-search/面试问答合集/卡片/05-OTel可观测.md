# 卡 05 · OTel 可观测（提纲 3.3，JD 点名 + 差异化武器）

> 定级：L2 → 待盲测｜ 2026-11-16
> 定位：**这是你唯一有生产实战的 JD 高频考点，要主动往这引。**

## 3 句骨架

1. **任务 = trace，LLM 调用 / 工具调用 = 子 span**，父子关系还原完整轨迹。一个 trace 就是一次任务的完整轨迹——**它就是评测的数据底座**（先有可观测，才谈得上评过程）。
2. **AI 监控和普通服务的根本差异是监控对象变了**：输出非确定（要记 prompt 版本 + 模型版本才能复现）／成功不能看状态码（要挂质量信号）／成本是运行时变量（token 就是钱）／延迟要拆 TTFT 与总时长。
3. **成本与信噪比靠策略，不靠堆存储**：metrics 全量计数、traces 分层采样（异常且贵的全留）／脱敏在写入前做／冷热分层 + TTL 按用途定。

## trace 结构

```
trace: agent_task            task_id / user_id / conversation_id / status / 总耗时
├─ span: llm_call #1         model, input/output/cache tokens, finish_reason
├─ span: tool_call           tool.name, 入参(脱敏), 返回摘要, 耗时, status
│    └─ span: http_request   下游接口
├─ span: llm_call #2
└─ span: llm_call #3 (final)
```

`gen_ai.*` 关键字段：`gen_ai.request.model`、`gen_ai.usage.input_tokens / output_tokens / cache_read_input_tokens`、`gen_ai.response.finish_reason`、`gen_ai.tool.name`

## 「AI 一直转圈」的四种可能（排查顺序）

| 现象 | 病因 | 查哪 |
|---|---|---|
| **连 trace 都没有** | 请求没进来 | 网关 / 入参校验 / 鉴权（**最先确认**）|
| 最后一个 span 未结束、耗时异常 | 卡在这个调用 | llm → 流式连接/上游超时；tool → 下游接口/沙箱进程 |
| 同类 span 反复出现 | 循环空转，不是卡 | 同参数重复 N 次 → 熔断 + 上报 |
| **trace 已结束但页面还转** | 状态流转 / 前端 | 状态机、消息回传（案例 3 的九态）|

## AI 监控 vs 普通服务（三条差异 + 对应动作）

| 差异 | 所以要多做什么 |
|---|---|
| 输出非确定，日志无法复现 | 每次调用打 prompt 版本号 + 模型版本 |
| 200 也可能是错答案 | 用户反馈 / 人工评分 / 评测分挂到 trace 上 |
| 成本随输入输出浮动 | 按调用计量 token 与成本，按功能/用户/模型聚合 |
| （加分）用户感知是首字延迟 | 拆 TTFT 与总时长，别只看总耗时 |

## 采样 / 脱敏 / 存储

**关键区分**：**metrics 全量计数，traces 采样**——「这周花了多少 token」必须走计数器，不能靠采样估。

| 采样 | 说明 |
|---|---|
| 头部 | 进请求即按比例，简单但漏长尾 |
| 尾部 | trace 结束按规则决定，精准保留异常，但需缓冲全量 |
| **分层（推荐）** | 正常请求 1–5%，**失败/超时/超 token 预算 100% 留** |

**脱敏**：写入前做（不是查询时）／工具入参出参是重灾区／**保留结构不保留内容**（`"password":"***"` 或只存 hash）／高敏场景只存元信息不存正文
**成本**：冷热分层（近 7 天全字段，远期只留聚合）／TTL 按用途定／超长 prompt 截断 + 存 hash

## 两个真坑（故事，比理论值钱）

**坑 1｜trace 表 1 天 TTL + 100G 专用盘 → 磁盘写满，上报静默失效**
> 「可观测系统本身也必须被监控——上报失败率、丢弃条数、磁盘水位。**数据静默丢失比没有数据更危险，因为你会以为一切正常。**」

**坑 2｜业务拦截原标 ERROR + Abandoned，告警全是噪音 → 改 UNSET + WARNING**
> 「span status = ERROR 只该用于真正的故障。用户取消、业务规则拦截属于正常路径，标 UNSET 用 attribute 区分。否则告警一多，真故障就被埋了。」

## Trade-off

- **全量采集 vs 采样**：全量能查任何个案，但存储与写入成本线性涨 → 分层采样 + metrics 全量计数
- **存正文 vs 只存元信息**：正文能复盘 prompt 问题，但敏感且占空间 → 脱敏后存，高敏场景只存元信息
- **TTL 短 vs 长**：短省钱但看不到趋势，长能回溯但成本高 → 排障窗口 7 天 + 聚合表长期

## 我的理解（原话 · 2026-11-16）

**排查路径（真实工作方式）**
> 「在 Langfuse 根据用户 id 和 prompt 找到对应的 trace，看任务是否结束。如果结束了，说明是后台的状态流转有问题；如果任务还在进行，就进一步查看卡在哪个步骤。」

> 这句里最值钱的是**「结束了 → 说明是状态流转问题」**——把故障定位到“不是模型层”。补两点就完整了：
> ① 先确认**有没有 trace**（没有 = 请求没进来，去查网关）
> ② 中间态要看**最后一个 span 是否结束**（未结束 = 卡在它）+ 有没有**同类 span 反复出现**（有 = 循环空转，不是卡）
