## 一、prompt 六块（背下来）

| # | 块 | 回答什么 | 写坏的典型 |
|---|---|---|---|
| 1 | **角色** | 它是谁、在什么场景工作 | “你是资深工程师”——只是语气，不是约束 |
| 2 | **上下文** | 项目结构、已有约定、约束 | 整份 README 塞进去 |
| 3 | **任务** | 做什么 + **做到什么程度算完成** | 只说“优化代码”，无完成标准 |
| 4 | **格式** | 输出长什么样（schema/模板） | 只说“用 JSON”，不说字段 |
| 5 | **示例** | 一两个正例，必要时反例 | 示例分布和真实任务不一致 |
| 6 | **兜底** | 做不了/不知道/**不能做什么** | “请谨慎操作” |

**改法对照**：

```
✗ 你是一个专业的程序员
✓ 你在内部 Agent 平台工作，Node + TS，遵循仓库约定，不引入新依赖

✗ 请谨慎地修改代码
✓ 修改前先读文件；只改与需求相关的行；不动测试文件

✗ 确保代码质量，输出结果
✓ 完成标准：类型检查通过、相关单测通过
  输出格式：先一句话说明改了什么，再给 diff
```

**三条铁律**：

1. **写成可执行规则，不写形容词**（“谨慎”→“改前先读文件”）
2. **任务块必须写完成标准**（否则模型提前收工或过度发挥）
3. **安全不能靠提示词**：提示词会被忽略、被注入绕过；**真正不能做的从工具和权限上拿掉**，提示词只负责“别尝试、碰到了怎么说”

**项目实战挂点**：
- 硬规则「不要把业务数据写到容器本地」
- 收尾自检并把结果写进标记（标记由模型写，后端读）
- Skills 从「手工塞进 prompt」改成 SDK 原生**渐进式加载**（只放名单、正文按需读）

**追问：prompt 改完怎么验证没退化** → 跑回归集：硬标准 gate → 逐条 diff（成功→失败）→ 目标项升、非目标项不降。（接卡 24）

## 二、tool calling 完整流程（六步）

```
① 模型输出 tool_use（结构化 JSON：工具名 + 参数），不是自然语言
② harness 拦截 → schema 校验（类型/必填/枚举）
③ harness 做权限与边界校验（工具白名单、路径越界）
④ harness 执行（MCP / 沙箱）
⑤ 结果序列化 + 瘦身 → 以 tool_result 回灌消息历史
⑥ 模型基于结果继续决策（再调工具 或 给最终答复）
```

**最关键的一句**：

> **模型只产出调用意图，真正发请求的是 harness。** 只有这样工具调用才能被**校验、拒绝、记录、中断**——模型能直接调，这四件都做不了。

**循环终止三条件**：模型不再输出 tool_use / 达最大轮次 / 用户中断或超时。

## 三、参数不合法：分三层处理

| 层 | 例子 | 处理 |
|---|---|---|
| 语法/类型 | 少必填、类型错、拼错字段 | **回给模型重试** |
| 边界/权限 | 路径越界、调白名单外工具 | **直接拒，不回给模型**（重试=帮它试绕过） |
| 业务 | 文件不存在、分支没有 | 回给模型，但错误信息要**可操作** |

**错误信息写法**（越具体，返工越少，直接省钱）：

```
✗ { error: "invalid params" }
✓ { error: "path 必须是相对仓库根的路径；你传了 /etc/passwd。示例：src/a.ts" }
```

**重试两约束**：次数上限（3 次）+ **幂等**（写文件/推代码这类有副作用的，重试前先判断是否已成功）。

## 四、ACP（一句话）

> **MCP = Agent ↔ 工具**的接入协议（工具/资源/prompt 三类原语）。
> **ACP = Agent ↔ 客户端 / Agent ↔ Agent** 的通信协议（会话生命周期、中断、消息格式）。
> **MCP 管“能调什么工具”，ACP 管“谁在跟 Agent 对话、怎么打断它”。**

## 五、好工具的设计（有 MCP 实战，别只答流程）

- **description 最关键**：写清「什么时候该用、什么时候不该用」，这是模型判断的唯一依据
- **粒度**：一个工具做一件完整的事。太大参数易填错，太小题数爆炸、上下文被撑满
- **参数**：**能由后端决定的不要交给模型填**（减少出错面和注入面）
- **返回**：只回必要字段，大结果落盘给引用
- **失败**：错误信息要让模型能自我纠正
