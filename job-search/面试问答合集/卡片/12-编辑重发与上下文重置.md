# 卡 12 · 编辑重发与上下文重置（只讲 Claude 链路）

> 定级：L3（有实做，2026-11-18 核对代码）｜ 归属：提纲 1.5「用户改一句重发，模型侧旧上下文怎么清」
> 口径：统一走 `claude_agent_sdk`，OpenAI 那条链路只作兼容历史，不在主线里讲。

## 3 句骨架

1. **「编辑重发」= 截断消息 + 让模型侧的 transcript 失效**，不是删会话、不是新建会话。
2. **清上下文的手法不是「删缓存」，是「让续接失效，逼它走重建」**——把上下文的真相来源从 SDK 的 transcript 换回自己的 messages 表。
3. **代价必须主动说**：续接失效 → 前缀全变 → **prompt cache 失效**（cache 读约正常价 10%，之后几轮都要重新热）；用户会感知到 **AI 失忆**；从消息表重建可能丢工具轨迹 → 行为漂移。

## 完整链路（五步）

```
① truncate 接口
② 校验：归属 403 / RUNNING 409（先尝试恢复僵尸会话）
③ 截断 messages（从最后一条 user 消息起）
④ 清 Claude 侧：删 transcript + 断两个指针
⑤ 下一轮 send：找不到 transcript → 从 messages 重建上下文
```

## ② 校验的两个守卫

```ts
conversation.userId !== userId   → 403
status === RUNNING               → 先 recoverStaleRunningConversation()
                                 → 仍 RUNNING 则 409
```
**为什么拒 RUNNING**：模型还在往旧上下文写，你这边已删 → 消息表与模型侧错位。
**为什么先 try 恢复**：这个 RUNNING 可能是进程崩溃留下的僵尸，恢复成功就放行。

## ③ 截断：两种模式

```
不传 messageId → deleteFromLastUserMessage   ← 编辑重发的默认语义
传 messageId   → deleteFromMessage           ← 为"编辑任意中间消息"预留
```
**`messageId` 是请求参数（从哪条开始删），不是"这条消息存不存在"的判断。**
连带删掉后面的 assistant 回复**不是误删，是语义**：问题改了，答案作废。

## ④ 清 Claude 侧三件事（`resetClaudeSession`）

```ts
ClaudeSessionEntryRepository.deleteByScope({ backagentProjectId, threadId })  // 1 真删 transcript
ChatThreadRepository.update(threadId, { providerThreadId: null })              // 2 断续接指针
ConversationRepository.update(conversationId, { agentSessionId: "" })          // 3 断会话指针
```

**为什么三件都要做**：transcript 是 Claude 自己的历史；`providerThreadId` 是"下次还续这个 session"的指针；`agentSessionId` 是 runner 拿去 resume 的 id。缺一个都能把旧上下文带回来。

**为什么要「整份失效」而不是「删一轮」**：Claude SDK 没有单轮删除能力，transcript 是整体。

**两个工程细节**
| 细节 | 原因 |
|---|---|
| `deleted === 0` 也执行清理 | **幂等**——重复调用/兜底路径都保证 provider 状态干净 |
| 清理 **best-effort**，失败只记日志不抛错 | 上下文没清干净 = 模型多记一点（可恢复）；接口报错 = 用户操作直接失败（不可接受） |

## ⑤ 下一轮 send：上下文来源的四级优先级（代码事实）

```ts
initialContextSource =
  !shouldCreateVersion        ? 'none'
  : isRequestNewConversation  ? 'fresh'            // ① 用户主动要新会话
  : canAttemptResume          ? 'claude_resume'     // ② 有 agentSessionId + 有主 transcript
  : canAttemptContinue        ? 'claude_continue'   // ③ 无指针但 transcript 还在
  : shouldStartInHistoryMode  ? 'thread_history'    // ④ 没有主 transcript
  : 'fresh'                                         // ⑤ 兜底
```

判定条件：
```ts
canAttemptResume   = 有 agentSessionId && hasClaudeStoreMainTranscript
canAttemptContinue = 无 agentSessionId && hasClaudeStoreMainTranscript
shouldStartInHistoryMode = !hasClaudeStoreMainTranscript && 有 thread && 有 latestThreadConversation
```

**关键开关是 `hasClaudeStoreMainTranscript`**：第 ④ 步已删 transcript → 它为 false → resume/continue 都不成立 → **必然落到 `thread_history`**。

**`thread_history` = 从 messages 表（已截断）读出历史 → 注水成 Claude 需要的上下文 → 按保留策略裁剪（轮数/字符数）。**

## 一句话总结（背这个）

> **「编辑重发」的本质是把上下文的真相来源，从 Claude 的 session store 换回我自己的消息表。**
> 截断 messages + 让 transcript 失效（删 scope、断指针），下一轮它就只能从我的消息表重建。

## 三个必被追问的点

**① 为什么不能只删一轮？** → SDK 的 transcript 是整体，没有单轮删除能力。

**② 代价是什么？**
- 前缀全变 → **prompt cache 失效**，之后几轮重新热（真金白银）
- 用户感知 **AI 失忆**
- 从消息表重建可能丢 tool call 轨迹 → 行为漂移

**③ 为什么不直接新开会话？** → 用户只改了一句，前面 20 轮上下文还要保留；删的是"这句之后"，不是全部。

## 我的理解（原话 · 2026-11-18）

> 「后台数据库会删掉重发的 conversationId 对应的数据，然后 push 新的 conversation 记录，同时由于每次调用模型都会在模型侧留下记录，所以模型这边也要清；但 SDK 没有提供单独删某一次会话的功能，所以只能全清，然后从数据库同步最近的 n 条历史对话。这里确实会造成一定程度的模型幻觉，因为会改变模型的历史上下文且会导致无法命中缓存。」

**记忆与代码的偏差（要改）**
| 记忆里 | 实际 |
|---|---|
| 删掉 conversationId 对应的数据 | **按消息截断**，conversation 保留 |
| push 新的 conversation 记录 | **没有新建**，截断后直接重发 |
| 造成「幻觉」 | 准确是**上下文不一致 → 行为漂移** |
| 全清 + 从 DB 同步 | ✅ 对，但路径是 `thread_history` 注水重建（按轮数/字符裁剪）|

## thread_history 的裁剪参数与算法（2026-11-18 核对）

**两道闸**（都可 env 覆盖）：
```ts
DEFAULT_MAX_USER_TURNS = 20        // SANDBOX_CHAT_HISTORY_MAX_USER_TURNS
DEFAULT_MAX_CHARS      = 60_000    // SANDBOX_CHAT_HISTORY_MAX_CHARS
```

**五步算法**
1. **筛会话**（先决定哪些对话算历史）：排除当前会话 / 只留 `status === 'completed'` / 只留 `kind === 'chat'` / 排除 `metadata.temporary` / 排除 `startServiceAccepted` 与 `workflowMode === 'service-start'`
2. **按 user turn 分组**：以 `role === 'user'` 为界，一个 turn = user + 其后的 assistant/tool/reasoning → **天然不会截半个 turn**
3. **先按轮数切**：`turns.slice(-20)` 取最后 20 轮
4. **再按字符从最老丢**：`while (length > 1 && chars > 60k) slice(1)` → **永远保留最后一轮**（哪怕它自己就超预算）
5. **字符估算**：role 长度 + 4 + 正文；**text 计入、reasoning 计 0、文件只计元信息**；消息间 +2

**两个设计判断（能讲出来是加分）**
- **先轮数后字符**：轮数是语义单位（一问一答的完整性），字符是成本单位 → **先保语义完整，再压成本**
- **用字符不用 token**：算真 token 要引 tokenizer，成本高且不同模型不同 → 字符估算是够用的近似（60k 字符 ≈ 15k–30k token）

> 口径：「最多 20 轮、6 万字符，先按 turn 分组所以不会截半个 turn，先轮数后字符、从最老往前丢、但永远保留最后一轮。」
