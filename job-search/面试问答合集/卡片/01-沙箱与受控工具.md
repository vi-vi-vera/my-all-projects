# 卡 01 · 沙箱安全执行与受控工具（提纲 1.9）

> 定级：L3（可主动输出）｜ 2026-11-16 练成

## 3 句骨架

1. **核心假设：模型行为不可信**——输出会错、提示词会被注入、工具会被误调。所以整套设计不是"让模型别做坏事"，而是**让它没有做坏事的落点**。
2. **最小权限四层**：能力收口（模型只能调受控工具，不能自己发请求）→ 身份约束（以当前用户身份执行，不是平台身份）→ 范围约束（只能碰该用户自己的项目）→ 审计（谁在何时调了什么，可回溯）。
3. **落地形态**：部署这类固定流程收成一个 MCP 工具，模型只看到 schema、看不到实现、拿不到凭证；真正的构建/推镜像/部署走后端**固定流水线**——模型就算想说错话，也没有可注入的参数入口。

## 挂的案例

- **案例 4（部署 MCP）**：两个理由——① 系统级数据（pod 秘钥、项目数据）不能开给 AI，泄漏 + 被拿去做预期外行为；② 部署前是固定检查 + 按项目类型分流，本来就该收口。
- **受控令牌**：30 分钟有效期、签名 + 载荷哈希、绑定用户与项目、只能调后端接口、后端验签 + 预检、本次 id 防重放。
- **案例 6（上传门禁）**：Origin 白名单校验放在解析请求体之前——先关门再收东西。
- **案例 3（端口清理）**：执行环境回收、LISTEN 检查。

## Trade-off（各一句）

- **收口 vs 灵活性**：固定流程做成受控工具，模型不能自由组合 → 换来确定性与安全性，代价是新场景要改工具，不能靠提示词糊。
- **令牌短时效 vs 可用性**：30 分钟够一次操作，但长任务要续签 → 换来确定性回收，代价是多一次刷新链路。

## 边界（必须诚实说）

- **git 口径分两条链路**：
  - 面板提交推送 → 后端代办（取当前用户凭证、冲突预检后执行），凭证不进沙箱
  - LLM 对话链路 → 模型在沙箱跑**原生 git**，clone 时凭证地址写入 remote，约束**主要靠提示词**
  - git-write 受控令牌 → **已实现未接前端，是方案不是现状**
- 收尾原话：「准确说不是我做了受控 git 工具，而是我做了一套受控令牌方案，并在面板链路上把凭证挡在了沙箱外。LLM 链路目前还是原生 git，靠提示词约束——这块我知道是弱项。」

## 最容易被追死的一问

> **「工具封装好了，模型照样能调它去部署不该部署的项目，你怎么挡？」**

答：令牌绑定用户+项目+参数哈希，对不上直接拒；重放靠本次 id；环境分级——生产要二次确认或根本不可调；再加幂等键防重复触发。

> 追问升级版：「凭证从哪来？」→ 后端维护 userId → 当前有效凭证映射，沙箱里只有不透明 token。

## 沙箱形态（2026-11-23 查代码定稿，覆盖此前「进程隔离」的错说法）

**结论：不是进程隔离，是 k8s 上的容器沙箱——阿里云 OpenSandbox。**

| 维度 | 事实 | 出处 |
|---|---|---|
| 平台 | `@alibaba-group/opensandbox`，内部域名 `code.qpilot.woa.com` | `src/config/env.ts`、`config/opensandbox-adapter-factory.ts` |
| 分配方式 | k8s **Pool CR 预热池**，`pool-dind-2c4g-...` | `env.ts` `OPENSANDBOX_POOL_REF` |
| 规格 | **2C4G**，带 **DIND sidecar**（沙箱内可 `docker build/push`） | `env.ts:116`、`build-preview/sandbox-deploy.helpers.ts:565` |
| 应用层预热 | 空白沙箱预热池，含 sandboxId / domain / envdAccessToken，统计命中率 | `sandbox-warm-pool.service.ts` |
| 执行入口 | 沙箱内 **execd 守护进程**（HTTP：/files、/files/upload、/files/download、/files/mv、/files/search） | `sandbox-execd-client.ts` |
| 生命周期 | 默认 **24 小时**（`SANDBOX_TIMEOUT_HOURS`），支持重连（只需 sandboxId） | `env.ts`、`sandbox-sessions` schema |
| 历史 | 早期用 **E2B**，已迁移到 OpenSandbox（旧字段保留兼容） | `schema/sandbox-sessions.ts:40-41` |

**面试口径（四维）**：

> "隔离级别是**容器级**——沙箱跑在 k8s 上，从预热池分配，2C4G，带一个 DIND sidecar，所以沙箱里能 docker build/push 做部署。命令和文件操作不直接在本机起子进程，而是打到沙箱里的 execd 守护进程。
> 资源是按池子规格给的，生命周期默认 24 小时，用完回收。
> 代价有三条：每个沙箱 2C4G 的资源成本；**DIND 把 docker daemon 放进了沙箱，攻击面比纯容器大**；容器仍共享内核，防不住内核级逃逸——所以敏感操作还要叠受控令牌。"

**还没核实、别乱说**：网络出口是否白名单、CPU/内存是 k8s limits 还是 rlimit、沙箱内是否 root（代码里有 `run_as_root docker build`，但那是部署链路）。
