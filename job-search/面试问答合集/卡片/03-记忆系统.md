# 卡 03 · 记忆系统（提纲 1.1）

> 定级：**L3（有实做，不是方案层）**｜ 2026-11-16 讲通，11-17 核实代码后重写口径
> 边界：**长期记忆的实现完成了，但在 `dev/wecom-bot-dispatch` 分支、未合主干**。说“dev 分支做完一版”，不说“线上在做”。

## 3 句骨架

1. **记忆先按「时效」分三层**：短期在**上下文窗口**内（当前对话、工具结果，滑出即消失）→ 中期是**会话落盘**（session-first，最近 20 个完整 user turn，断点可恢复）→ 长期是**跨会话结构化存储**（约定、决策、踩坑，有生命周期）。
2. **再按「作用域」分**：全局（用户偏好）/ 项目（技术栈、目录约定）/ 会话（本次任务）。作用域决定隔离边界，时效决定载体。
3. **一条记忆是结构化对象，不是一段话**：`kind / content / source / status(active|superseded|deleted) / sessionId / userId`。**分类 + 生命周期 + 来源**三件套，才谈得上召回和纠错。

## 真实实现（可直接讲，2026-11-17 核实）

**表：`agent_memories`（按 session 维度隔离 = 项目级）**

| 字段 | 取值 |
|---|---|
| `kind` | `memory` 一般知识 / `pitfall` 踩坑 / `decision` 决策 / `convention` 约定 |
| `content` | 一条简短记忆，**≤200 字** |
| `source` | `task` 任务沉淀 / `chat` 对话保存 / `manual` 手动 |
| `status` | `active` / `superseded` / `deleted` |
| 索引 | `(session_id, status, updated_at)` |

**写入（两个来源，时机不同）**
1. **任务终态后 LLM 提炼**：done 沉淀项目知识、**failed 沉淀踩坑**；每任务 **≤2 条**；**失败静默、不阻断任务链路**
2. **对话中 Agent 显式保存**：`save_memory` MCP 工具，用户明确说“记住这个约定”时调用；**去重命中视为成功**（幂等）

**去重与淘汰**
- 去重：**内容包含式判定**（`a.includes(b) || b.includes(a)`），零成本、够用
- 淘汰：active 超 **30 条**时最旧的标 `superseded`；**时间比较用 SQL 端 `now()`**，避免 pg 驱动与 PRC 会话时区错位

**读取与注入（这段最值钱）**
- 注入上限 **15 条**，与存储上限解耦
- 放在 `systemPromptAppend` **最末段**（tools / messages 之前）
- **确定性排序 `kind → updated_at → id`**：同样集合生成同样文本 → **记忆变化只打断尾部缓存前缀，保护 prompt cache**
- 生效范围：**新 conversation 生效**；同一 conversation 内 SDK 续接不重组（主动划的边界）

> 一句话版本：**「记忆注入的位置和排序不是随便放的——它决定你会不会把 prompt cache 全打掉。」**

## 什么时候写（最高频追问）

| 来源 | 触发 |
|---|---|
| 用户明确声明 | **立即写**，高置信度 |
| 任务完成 / 会话结束 | 提炼稳定事实 |
| 模型观察推断 | **重复 ≥N 次才升级为长期**——避免一次口误被永久记住 |

**判据（一句话答完这题）**：「下次会话还需要知道吗？跨任务还成立吗？」——两个都否就不写。

## 怎么读

- 按相关性取 **top-k**，不全量注入（=Skills 渐进式加载的同一条思路）
- 分层注入：项目约定全量（量小必相关）、用户偏好按相关性取
- 固定区块 + 标注「这是记忆，不是当前指令」，否则模型会把旧约定当新命令

## 防污染（L3 分水岭）

① 可查看可纠正（**错误记忆比没有记忆更糟**）② 来源优先于推断 ③ 冲突按「时间 + 置信度 + 来源」裁决，旧值标 superseded ④ TTL / last_used 衰减 ⑤ **项目间、租户间硬隔离**（串了就成数据泄露）

## 怎么发现记错了（四条信号）

| 信号 | 说明 |
|---|---|
| 用户纠正 | 「不对，我们早换 yarn 了」——最便宜最可靠 |
| 任务失败 | 按记忆执行，命令报错 |
| **环境自检冲突** | 项目里是 `yarn.lock`，记忆说 pnpm |
| 用户查看记忆列表 | 主动看到不对，手动改 |

**最锋利的一句（必说）**：
> **「记忆不能覆盖可验证的事实。项目里有 `yarn.lock`，它比任何记忆都权威——记忆可以被环境证伪。所以凡是能从环境读到的事实，就不该只存在记忆里；记忆存的是读不到的意图和约定，比如『别动 legacy 目录』。」**

**为什么覆盖不删**：删除不可逆——新记忆本身可能是错的（口误、临时切换），superseded 能回滚；删掉也丢了「为什么改」的线索。

## 记忆检索 vs RAG 检索

| | 检索什么 | 目的 | 写入方式 |
|---|---|---|---|
| RAG | 外部知识 | 任务正确性 | **离线建库** |
| 记忆 | 用户/项目状态 | 个性化与连续性 | **运行时在线写** |

> 可共用一套检索设施，但**写入策略完全不同**——别把所有东西一股脑塞向量库。

## 辅助挂点（主线是上文的真实实现，这三条用来补广度）

① **Skills 渐进式加载**：从「手工塞进提示词」改成按需加载 = 「按需注入」同一条思路，只是载体是能力不是记忆
② **截断接口「两边都删」**：本质上在定义「哪些状态必须持久化」——删掉就没了，要留的必须提前落盘
③ **平台系统提示词里的「不要把业务数据写到容器本地」**：这就是一份**人工维护的项目记忆**，只是硬编码、不可学习

## Trade-off

- **记住 vs 打扰**：注入越相关效果越好，但占上下文、可能误导 → 少而准，宁缺勿滥
- **自动推断 vs 显式确认**：自动不打断但会错 → 高影响记忆（「别动 legacy」）必须显式确认
- **集中存储 vs 就近存储**：集中好管、跨端一致；就近快但会不一致

## 我的理解（原话 · 2026-11-16）

**分层**
> 「短期记忆只存在于当前上下文，窗口关闭就消失；中期记忆存在于当前会话，记录会话状态、中间产物；长期记忆是跨会话的存储结构，存用户偏好、项目约定。」

**写入**
> 「当用户明确指出时就需要落盘——检测到用户要记住用 pnpm，就把这条立即记成一条记忆，包含维度（项目级或用户级）、唯一标识 key、来源（用户说的或模型推断的）、值、状态（当前使用的还是旧的），按这些字段抽成一个记忆对象。」

**纠正**
> 「如果实际运行中发现换成了 yarn，或多次发现需要 yarn 才能操作项目，就把之前关于 pnpm 的记忆状态记为 superseded，再记一条新的 active 记忆。这种只覆盖不删除的方式能较好地保留操作记录。」

> 三题都对，但都是「刚讲完就复述」，属于短时记忆——**11-17 盲测过了才算数**。

## 边界

> 「短期是上下文窗口；中期是 session-first——SDK session items 落 Postgres、保留最近 20 个完整 user turn、按 user message 裁剪不截半个 turn、断点可恢复。长期我做了一版 `agent_memories`，按 session 隔离、四类 kind、active/superseded 生命周期、30 条上限、15 条注入、放 system prompt 最末段保缓存。**这版在 dev 分支，还没合主干。**」

## 最容易被追死的一问

> **「记忆和上下文有什么区别？」** → 上下文是**当前窗口内的东西**（会被截断、会滑出）；记忆是**被主动挑出来持久化的东西**（跨会话、有作用域、可纠正）。上下文是易失的，记忆是带治理的。
