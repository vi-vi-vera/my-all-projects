# 卡 02 · 评测与回归集（提纲 1.8）

> 定级：L3（方案层，非实战层）｜ 2026-11-16 练成
> 定位：业务上没落地，讲的是「如果做我会怎么做」。**开场必须先声明这一点。**

## 3 句骨架

1. **回归集 = 一组固定的「输入 + 期望判据」，每次改动跑一遍，前后对比判断有没有退化。** 它解决的是「看起来能跑」和「稳定」之间的差距——没有它，prompt 改完只能靠感觉。
2. **判分分两层**：格式合规用脚本校验（schema / 必填 / 枚举），必须 100% 过；语义达标用断言优先，断言覆盖不了才上 LLM-as-judge，关键 case 人工抽检。**能用断言就别用 judge。**
3. **判断「变好」不看总分**——总分会被平均掉。看三件事：硬门禁 100%、目标类别通过率↑且非目标类别不↓、case 级 diff 逐条解释（谁退化了、谁修好了）。

## 一条 case 的四要素

输入（含上下文、**工具返回要 mock**） / 期望（必须包含什么·不能包含什么·格式要求） / 标签（类别·来源·难度） / 判法（断言 or judge）

> 期望不能写成「标准答案全文」——LLM 输出不唯一，精确匹配会制造假失败，要写成断言。

## case 来源（按价值排序）

线上 bad case > 真实分布采样 > 边界与对抗（空输入/超长/注入/多轮）> 契约类（格式必填）
**数量**：起步 10–30 条就成立，原则是「每条可判定 + 覆盖各类别」，不是多。

## LLM-as-judge 三条纪律

① 给 rubric 逐项打分，不打笼统 1–10 ② 判分模型 ≠ 被测模型 ③ 防位置偏差（A/B 换序跑两次）和长度偏差，关键 case 人工抽检

## 掉分归因树（**按离数据从近到远排，不是按重要性排**）

> 为什么这个顺序：越靠底层越容易验证、改造成本越低。**上来就怀疑模型是最贵的排查方式**，而大部分人恰恰这么干。

**第 0 步 · 先确认「过程对」是真的对**
工具选对了吗？参数对吗？顺序合理吗？有没有多余调用？——过程本身有瑕疵时，「结果错」只是下游表现，先修过程。

**第 1 层 · 工具返回对不对（最该先查）**

| 症状 | 处理 |
|---|---|
| 返回缺字段，模型没法判断 | 补返回字段 |
| 返回内容本身错（下游服务/数据问题）| 修工具实现 |
| 返回太大，被截断或压缩过头 | 只留必要字段，大结果落盘给引用 |
| 格式晦涩（嵌套太深、单位不明）| 改返回结构，或在 schema 里写清语义 |

**第 2 层 · 返回对，但模型没读到 / 读错**

| 症状 | 处理 |
|---|---|
| 结果被截断砍掉了 | 调截断策略，工具结果优先保留 |
| 多轮后早期结果被挤出窗口 | 摘要压缩 / 落盘 + 按需取回 |
| 误解返回格式 | 加 schema 说明，或让工具直接产出结论字段 |

**第 3 层 · 读到了，但推理错**

| 症状 | 处理 |
|---|---|
| 指令冲突、约束漏写 | 改 prompt |
| 少样本示例把模型带偏 | 换示例，或干脆不给示例 |
| 多步推理超出能力 | 拆步骤 / 换更强模型 / 把计算交给工具 |

**第 4 层 · 知识缺口（不是 bug，是边界）**
模型不知道业务规则 / 历史约定 / 领域知识。
处理两条路：**能工具化的固化进代码**（把判断交给工具，别求模型答对）；**不能工具化的上 RAG 或写进 prompt**。

**收尾（最值钱的一句）**
> 「四层都排除完还是错，说明这个任务本身不该交给模型——该把判断固化成工具或规则。这是我判断的终点，不是继续调 prompt。」

**手法**：失败 case 的完整输入 + 上下文 dump 出来看；要二分定位就「只改一处再跑」。

## 轨迹 vs 结果（JD 点名）

| 组合 | 判读 |
|---|---|
| 结果对 + 过程绕 | 能用但不稳、成本高，迟早出事 |
| **过程对 + 结果错** | **先 dump 工具返回**：返回不对→工具问题；返回对→解读问题（prompt/上下文/模型） |
| 两者都对 | 真过 |

## 挂的案例（唯一的实战连接点，必须主动说）

> 「轨迹评测的前提是能把轨迹存下来。我们做的 OTel 调用链上报——任务=trace、LLM/工具=子 span——就是它的数据底座。**先有可观测，才谈得上评过程。**」

辅助挂点：个人 Demo 的 10 条 golden cases（覆盖必须提到的类别 + 不能出现的内容）；案例 3「把判断原因一起回传」= 可解释的失败。

## Trade-off

- **断言 vs judge**：断言便宜稳定可解释，但只覆盖可枚举的正确性；judge 灵活但带偏差 → 高频强约束用断言，开放质量才用 judge。
- **覆盖度 vs 跑批成本**：case 越多越稳，但每次全量跑太贵 → 分层跑：门禁用小集秒级拦，全量集在合入前跑。
- **离线回归 vs 线上指标**：离线管已知且可复现，线上管未知与真实分布 → 互补，不能互相替代。

## 边界（每次都要带）

> 「回归集我的做法是这套闭环。业务上我们还没正式落地，只在个人 Demo 里做过 10 条 golden cases——但正因为做过，我知道没有它的痛点在哪。」

## 最容易被追死的一问

> **「分数怎么算出来的？」** → 两层：格式脚本校验（硬门禁）+ 语义断言/judge。
> **「总分涨了能上线吗？」** → 不能。总分会被平均掉，要看硬门禁、分项、case 级 diff。
