## 一、3.1 发布链路（60 秒，四块缺一不可）

```
① 两类 + 一个例外
   常规服务：测试自动、正式留人
     - 测试分支 push/merge → Orange CI → 构建、打包、推镜像 → 自动部署测试环境
     - 正式分支 merge → 只构建镜像推镜像库 → 统一发布平台接审批 → 通过才发 TKE
     - 正式环境永远不自动发
   例外：QPilot Code 走自己的 stream CI，构建完自动更新负载，没接审批流

② 迁移的角色边界
   9 个服务、跨 4 条业务线、两周完成、正式逐项确认、切换零事故
   我负责交付链路：仓库迁移 / 流水线（蓝盾）迁移 / 配置与环境变量重新关联

③ 为什么正式不自动发
   卡的不是代码，是放行动作。代码质量靠 MR 评审 + 测试环境自动验证；
   人工只回答「这次正式变更现在要不要上」。内部运营在用、数据影响面大，
   自动发布省下的几分钟抵不了一次误发

④ 发后怎么看
   伽利略结构化上报：部署、Git 提交推送、首页核心接口等 P0/P1 链路
```

**三个必被追问**：

| 追问 | 要点 |
|---|---|
| QPilot 不接审批是不是不规范？ | 权衡不是疏忽：迭代快、内部员工、影响面可控 → 用「快发布 + 监控 + 快回退」换「慢审批」；若承接外部用户，第一件要补审批 |
| 审批会不会拖慢？测试/正式镜像怎么保证一致？ | 只有正式那一下慢，测试照常全自动；镜像一定出自正式分支那次构建，不存在验一个发另一个 |
| 灰度做了吗？ | 见下 |

### ⚠️ 口径纠错（2026-11-28，D12 踩过一次）

> **没有做「按比例放量的灰度」，也没有灰度控制台。**

| 真实做过 | 叫什么 |
|---|---|
| 9 个服务：先更新**一批 pod**、验证、再全量覆盖 | **分批发布 / 滚动更新**（✅ 实战，可以讲） |
| 9 个服务接入统一发布平台的**审批流** | 审批流（✅ 实战） |
| QPilot：stream CI 构建完自动更新负载 | 自动发布（✅ 实战） |

**「按流量比例切给同时在线的新旧版本、盯指标再放大」= 灰度，没做。** 三档灰度（功能开关 / 按用户 / 按实例）是**设计方案**，别讲成生产现状。

**讲实战要分项目**：「QPilot 走 stream CI 自动发；另外 9 个服务走审批 + 分批」。面试官不介意某项目没做灰度，**介意把 A 项目的事安到 B 项目上**。

### 回滚三条路径

| 路径 | 速度 | 代价 |
|---|---|---|
| 配置/开关回退 | 秒级 | 只对功能级有效；已写进库的数据不跟着回去 |
| 镜像/版本回退 | 分钟级 | 全体同时回旧版；带表结构变更时旧镜像可能跑不起来 |
| 入口/流量回退 | 最快止血 | 粒度最粗，不动服务只切流量 |

前提：**部署记录里存了 `sourceVersionId`**，没有版本记录回滚就是空话。

## 二、3.4-1 首屏慢：三层，先排便宜的

| 层 | 叫什么 | 看什么 | 判据 |
|---|---|---|---|
| **① 拿不到** | 网络 | **Network 瀑布图** | TTFB 高 → 服务端/链路慢（**优化前端没用**）；串行阶梯 → 依赖顺序；排队 → 并发打满 |
| **② 拿太多** | 体积 | **构建产物分析**（不靠猜） | 首屏打进不该进的包？路由懒加载？第三方按需引入？ |
| **③ 算太久** | 渲染 | **Performance 火焰图** | LCP 元素、主线程长任务、同步大计算、大列表一次性渲染 |

**顺序理由**：前两层常一次改动就省几百 KB / 几百毫秒；第三层逐个组件抠，最费功夫收益最小。

### 瀑布图具体看什么（每根横条分几段）

```
[排队灰] [DNS/TCP/TLS 浅] [等待 TTFB 深] [下载 蓝]
```

| 表现 | 结论 |
|---|---|
| TTFB 段 1.5s、下载段 50ms | 服务器迟迟没回第一个字节 → 服务端慢 |
| 6 个请求排成一列、每根前有灰色排队段 | HTTP/1.1 同域约 6 连接打满 → 队头阻塞 |
| 横条呈阶梯，一根结束下一根才开始 | 依赖顺序问题（HTML→CSS/JS→接口瀑布） |
| 蓝色下载段特别长（弱网更明显） | 体积大 → 进第②层 |
| 几十个小请求密密麻麻 | 请求数过多 |

**TTFB = 请求发出到收到第一个字节。**

### 火焰图具体看什么（Main 轨道）

| 颜色 | 是什么 |
|---|---|
| 蓝 | Loading（解析 HTML） |
| **黄/橙** | **Scripting（JS 执行）** |
| 紫 | Rendering（样式计算/布局） |
| 绿 | Painting（绘制） |

| 表现 | 结论 |
|---|---|
| 一大片黄橙 + **>50ms 宽块（右上角红色小三角）** | 长任务：全量 JSON 解析、同步大计算、大列表一次性渲染 |
| 紫色 Layout 反复密集 | 强制同步重排（循环里读 `offsetHeight`） |
| 绿色 Paint 长 | 大面积重绘（阴影/滤镜） |
| 蓝色 Parse HTML 长 | HTML 太大 |
| Timings 的 **LCP 竖线之前**被什么占着 | 那就是首屏慢的直接原因 |

**定位具体代码**：点宽块 → Bottom-Up / Call Tree 看调用栈 → 找自己写的函数名。

### 三个工具别混

| 工具 | 看什么 |
|---|---|
| Network 瀑布图 | 时间花在**等什么资源** |
| Performance 火焰图 | 主线程**干了什么活** |
| React DevTools Profiler | **哪些组件重渲染** |

问「怎么确认是重渲染」答的是第三个。

### 3 分钟实操

```
1. Disable cache + Fast 3G，录 Network
2. TTFB 高 → 停，别在前端瞎优化
3. 看排队/阶梯 → 并发数与依赖顺序
4. 录 Performance，看 Main 长任务 + LCP 竖线之前
5. 关节流本地再测：本地也慢 → 渲染/计算；只有弱网慢 → 体积或请求数
```

**第 5 步 = 「怎么证明是前端的问题」的标准答案**：弱网和本地各测一次。

**边界句**：没做过完整首屏性能专项，上面是排查顺序；实际做的是工程侧改动（前端 API 地址改环境变量、正式 CI 迁 TKE），不是性能调优成果。

## 三、3.4-2 输入卡顿：三原因

1. **输入值上浮到大组件顶层** → 每敲一字整棵消息树重渲染 → 输入状态与列表状态隔离
2. **每次输入同步重计算**（搜索/高亮/代码块解析）→ 延后、worker、低优先级更新
3. **高频流式更新抢主线程** → 流式帧合并批量更新，别一帧一次强制同步

**挂的项目实战**：模型输出期间原来禁用输入框，改成**前后端持久化的输入队列**后，输出时用户照样能打字、排队、编辑；队列放后端是因为刷新/换设备不丢。

**边界句**：输入队列是产品与状态设计改动，**没做过量化性能优化（无 profile 数据）**，不当性能成果讲。
