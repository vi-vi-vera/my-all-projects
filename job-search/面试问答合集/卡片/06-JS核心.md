## 一、事件循环

### 三层优先级（背死）
```
同步代码（整段跑完） > 微任务队列（清空） > 宏任务（一次一个）
```

| 宏任务 | 微任务 |
|---|---|
| setTimeout / setInterval / setImmediate | **Promise.then / catch / finally** |
| I/O、事件回调、UI 渲染 | **queueMicrotask**、MutationObserver |
| | **await 之后的剩余部分（续体）** |

规则：**宏任务执行完 → 清空所有微任务（含新产生的）→ 渲染 → 下一个宏任务**

### await 的准确模型（三句）
1. `await X` **先同步求值 X**
2. 把函数**剩余部分**打包成续体，挂到 X 上
3. X **settle 之后**，续体进微任务队列
> 不是“下一轮就执行”——`await` 一个 pending 的 Promise，要等它到货。

### 高危坑（当天踩过）
| 坑 | 正解 |
|---|---|
| 以为“跑一行看一眼队列” | **同步是整段跑完**，`console.log('5')` 跟 `1` 挨着，不会排到微任务后面 |
| 以为 `await b()` = “b 稍后执行” | **b 当场同步执行**，只有 await 之后的代码延后 |
| 以为 `resolve()` 会中断执行 | `resolve` 只改状态存值，**后面的 `console.log('p2')` 照打** |
| 以为链式 then 一起排队 | `t2` 要等 `t1` 的回调返回、第一个 then 的 Promise 完成才入队 |

### 挂案例
> **案例 5「输出期间消息队列」**：SSE 分片逐条到达时不能每片都 setState，要在微任务/批次里缓冲合并，让“一次渲染”对应“一批数据”——事件循环不是用来背输出的，是用来决定**什么时候把状态变化推到渲染**。

## 二、原型链

### 两个概念
| | 属于谁 | 记法 |
|---|---|---|
| `Fn.prototype` | 函数 | 函数给儿子留的家产 |
| `obj.__proto__` | 对象 | 实例找爹的地址 |

`a.__proto__ === Fn.prototype`；`Fn.prototype.constructor === Fn`

### 改对象 vs 换对象（核心）
| 操作 | 实际动作 | 影响谁 |
|---|---|---|
| `Fn.prototype.x = 1` | 顺地址进去改对象 | **所有实例**（新老都变）|
| `Fn.prototype = {y:2}` | **换掉槽位里的地址** | **只有之后 new 的实例** |

> 类比：两人各拿一张写着房间号的纸条。你去 101 搬把椅子 → 他进 101 也看得到；你把自己纸条改成 202 → 他手上还是 101，什么都没变。
> **`new` 是“把当时的房间号抄一份给新对象”。**

### new 四步
1. 创建空对象
2. 空对象 `__proto__` 指向 `Fn.prototype`
3. 执行构造函数，`this` 绑到新对象
4. **返回结果是对象，就直接使用这个对象（this 丢弃）；返回的是原始值就忽略，返回 this**

| 构造函数返回 | new 的结果 |
|---|---|
| `{}` / `[]` / `function` | 返回它，**`this` 丢弃** |
| `1` / `'a'` / `true` / `undefined` / **`null`** | 忽略，返回 `this` |

### 手写 instanceof
```js
function myInstanceof(obj, Ctor) {
  if (obj === null || (typeof obj !== 'object' && typeof obj !== 'function')) return false
  let proto = Object.getPrototypeOf(obj)
  while (proto !== null) {
    if (proto === Ctor.prototype) return true
    proto = Object.getPrototypeOf(proto)
  }
  return false
}
```
三个加分点：① **必须先挡原始值**（否则 `getPrototypeOf(1)` 会装箱，`myInstanceof(1, Number)` 误判 true）② `typeof 'function'` 也要放过（函数也有原型链）③ 循环靠 `null` 终止

### getPrototypeOf vs `__proto__`
本质读同一个 `[[Prototype]]` 槽。区别：`__proto__` 是挂在 `Object.prototype` 上的**遗留访问器**（Annex B）、不是自有属性、会被同名属性遮蔽、`Object.create(null)` 的裸对象**没有**它。写代码用 `getPrototypeOf`。

### 挂案例
> **Error Boundary 的 `class Boundary extends React.Component`** 本质就是原型链继承，`setState`、生命周期都是顺着原型链找到的。

## 三、闭包

### 一条规则（所有题都从它推）
> **闭包捕获的是「变量（绑定）」，不是「值」。**
> - 变量被改 → 闭包看到新值（`var i` → 3 3 3）
> - 变量不再变（每次创建新的）→ 闭包永远看旧值（stale closure）

### 定义（人话）
函数找变量，看的是**它写在哪**，不是谁调用它。闭包 = 函数记着“我出生在哪”，能顺着那条路回去读那层的变量。

**每个写在函数里的函数都是闭包**（默认行为）。只有当它**活得比外层久**（被返回、被注册成回调），外层作用域才被迫保留。

### 高危坑
| 坑 | 正解 |
|---|---|
| 用“变量提升”解释 3 3 3 | 真因是 **`var` 只有 1 个绑定**，三个闭包读同一槽位 |
| 说“全局的 i” | `var` 是**函数作用域**，放函数里就是局部，仍然共享一个绑定 |
| 说“闭包导致内存泄漏” | 闭包不是病；**持有整个作用域**、忘了解绑才是病 |

### 三种改法（var 拿 0 1 2）
① IIFE 造新作用域 ② 函数工厂 `bind(k)` ③ 换 `let`（**for 循环里每轮一个新绑定，这才是 2 输出 0 1 2 的真因，不是“let 没提升”**）④ `Array.from` / `forEach` 每次回调自带参数

### stale closure（React，实战价值最高）
```js
const [count, setCount] = useState(0)
useEffect(() => {
  const id = setInterval(() => {
    console.log(count)      // 永远 0
    setCount(count + 1)     // 永远算 0+1=1，卡在 1
  }, 1000)
}, [])
```
机制：**每次渲染 = 重新执行一次 Chat = 新作用域新 `count`**；`setInterval` 的回调只在挂载时创建一次，**一直住在第 1 次渲染那个世界**，而那个 `count` 是 `const`，永不改变。

对照纯 JS 版（能正常涨）：`let count` 是**一个可变绑定**，`count = count + 1` 改的就是它。
> 差别不在闭包，在**变量**：一个槽位被改 vs 每次换新的一份。

三种改法：① `setCount(c => c + 1)`（首选，把“读最新值”交还 React）② `useRef` 存最新值（要读最新且不想重建副作用，如 SSE 回调）③ 把 count 加依赖（会重建 timer，容易叠）

### 挂案例
> **案例 5**：SSE 分片回调里 `setMessages([...messages, chunk])` 读到的是注册那刻的 messages → 看似丢消息。修法：`setMessages(prev => [...prev, chunk])` 或 ref 持有最新队列再批量 flush。
> **内存泄漏真事**：SSE 连接切走没 `close()`、监听没解绑、定时器没清——都是“闭包 + 忘了回收”。

## 四、类型判断

| 工具 | 能判 | 判不了 |
|---|---|---|
| `typeof` | 原始值、函数 | 所有对象都返回 `'object'` |
| `instanceof` | 对象属于哪个构造器 | 原始值全 false；**跨 iframe 失效** |
| `Object.prototype.toString.call()` | 一切，最可靠 | 略重 |

`typeof` 八个返回值：`undefined boolean number string symbol bigint function object`

**`typeof null === 'object'` 的由来**：早期用低 3 位做类型标签，对象是 `000`，`null` 是空指针、机器码全 0 → 被误判。改不了，会破坏老网站。

**为什么要 `.call`**：多数类型改写了自己的 `toString`（数组是 join、Date 是日期串），只有 `Object.prototype.toString` 老实报类型，`.call` 让它以目标对象为 this 执行。

**`1 instanceof Number` 为 false**：原始值没有原型链。`(1).toString()` 能用是因为**引擎临时装箱**——装箱是临时的，原型链是永久的。

### 选择顺序（这题真正想要的）
```
原始值 → typeof  ｜ null → === null ｜ 数组 → Array.isArray()
内置对象 → toString.call ｜ 自定义类 → instanceof
```

### 挂案例（比背清单值钱）
> **「运行时类型判断只该发生在系统边界」**——网络响应、localStorage、URL 参数（数据是 unknown）。内部一律靠 TS 类型，像预览九态、消息模型那样**用类型把状态收敛住**（案例 3、5），不靠运行时 typeof。

## 我的理解（原话 · 2026-11-16）

> 用法：背自己的话比背别人的话快。面试前扫这一栏，让表述回到“我讲得出口”的版本。

**事件循环（综合题推演，全对）**
> 「输出A → setTimeout 进宏任务队列 → 进入 run，输出 D，await 后面的进微任务队列 → 输出 G → 清空微任务队列，输出 E，setTimeout 进宏任务队列 → 进第一个宏任务，输出 B，产生一个微任务，立即执行微任务，输出 C → 再取一个宏任务，输出 F」

**原型链（一句问出来的真相，几乎全对）**
> 「new 出来的对象的 `__proto__` 指向 Fn 的 prototype，更新 prototype 的属性，对象对应的属性也会变；那把 prototype 整个更改为什么 `__proto__` 还是老的 prototype？因为 `__proto__` 实际存的是 prototype 的地址，而 `Fn.prototype = {...}` 实际是改变了地址，`__proto__` 的值一直是老地址。」

**闭包（自己总结的版本，精准）**
> 「只要是函数读取了他外部作用域的变量就算一个闭包。如果函数内部使用的变量因为某些原因需要一直保留，这个闭包就会一直持有**出生那层**的作用域变量；如果直接给这个变量赋值，后续能看到改动。而 React 持有的是 count 为 0 时的那个作用域变量，每次 set 是创建了一个新的 count，所以页面展示会变成 1，但每次执行时都是用的最初的 0 去 +1。」

**类型判断（三题全对）**
> 「`typeof null` 是 object，因为 JS 最初用 000 标识对象，null 的位也全是 0，被误认为 object。」
> 「判断数组用 `Array.isArray()`，它查内部槽，跨 realm 也准。」
> 「`toString.call` 用 call 把 this 绑到目标变量上。」

**当天答反过、后来修正的（说明“想当然”的惯性）**
| 当时答的 | 正确 |
|---|---|
| 换 `Fn.prototype` 后 `a.y` 能拿到 2、`a.x` 变 undefined | 反了：`a.y` 是 undefined，`a.x` 还是 1 |
| `new` 返回对象时仍能拿到 `this.a` | 反了：`this` 整个被丢弃 |
| 用“变量提升”解释 `3 3 3` | 真因是 `var` 只有**一个绑定** |
| 同步代码“跑一行看一眼队列”，漏掉 `5` | 同步是**整段跑完** |
