## 0. 优化前后速查（面试讲「为什么做这个优化」用）

> 依据两个仓库各分支的提交记录与提交说明整理；括号里的时间只帮你回忆，面试不用报日期。
> 用法：先讲「原来怎么做」把问题摆出来，再讲「为什么不行」，最后讲「改法 + 效果」。**效果栏写「现象」的，就是没有量化数据的，别硬编数字。**

| 功能 | 原来怎么做 / 痛点 | 怎么改 | 优化后能讲什么 |
|---|---|---|---|
| 预览状态机 | 轮询、聊天流、启动流、SSE 各自改状态；失败记录是粘性的；固定 3 秒轮询无超时；启动失败傻等约 60 秒 | 单点决策 + 用「本轮启动时间」区分新旧失败 + 指数退避轮询 + 致命错误快速失败 | 缺文件场景失败等待约 60 秒 → 约 6 秒；不再跳变/白屏/卡「启动中」。99%→18.6% 是**事故数字**，不是优化结果 |
| 部署链路 | 部署记录被覆盖、Pod IP 写死、模型自己拼 curl、只有一套环境 | 一次部署一行 + 稳定内部入口 + 受控工具 + 存储预检 + 双环境 | 现象类：失败不卡 loading、Pod 重建不改记录、可单步查状态重试；没有成功率/耗时数字 |
| Git 两条链路与性能 | 面板走后端预检；对话里模型用沙箱原生 git（凭证在仓库配置里），提交推送都能成功；每条命令一次远程往返 | 面板补齐预检与配套；AI 写入设计过短期令牌工作流（未接入界面）；同一个接口的命令合成一次下发 | 往返次数 10+/6/2/5/4/4 → 1，版本差异 7~9 → 1；安全口径要诚实，无耗时对比 |
| 会话与协作 | 输出时禁用输入框；截断只删一边；老项目打开空白；导入完成靠单机广播 | 队列（后端存、前端调度）+ 两边一起删 + 按需迁移 + 查库兜底 | 现象类：不用干等、不空白、不卡「导入中」；3507 是受影响会话估算，不是修复数 |
| 上传与身份 | 跨域调上传必 401、上限 10MB、预览用明文身份 token、部署侧注入全局密钥 | 服务端转发 + 来源校验前置 + 请求体 1G + 身份收敛到一个接口 | 10MB → 1G；401/500 消失；密钥不出平台、存量沙箱和已上线实例无需重建 |
| Skills | 只把技能名字写进提示词、沙箱里没文件；同步一次约 137 次远程写、1 分钟以上 | 预置进沙箱 + 指纹增量同步 + 渐进式加载 + 安装存储合一 | 文档给的期望：内容未变约 1 秒、冷启动 5-10 秒；不是线上实测 |
| 统一登录态 | 第三方接口要下线；预览靠 Cookie、部署靠网关头两套分叉 | 泛域名接入 + 先回滚止血 + 三级方案 + 回源 443 + 身份收敛 | 一套写法；免登录前缀两个站点生效；预览泛域名整体接入**没做** |
| 监控 | 各阶段字段不统一、正常日志也刷屏、环境全落 default、同一批调用记两份 | 统一上报字段 + 日志分级降噪 + 补环境标识 + 导出阶段去重 | 可按统一字段检索、按环境筛、不再记两份；没有量化效果 |

**一条通用讲法（8 个功能都能套）**：「原来做法是 X，在 Y 场景下会出问题（说一个具体现象）→ 根因是 Z → 改成 W → 结果是……（有数字报数字，没数字只讲现象，并主动说明没做全量对比）」。

## 1. 预览状态机与竞态（案例 3）

### 是什么

用户写完代码后，界面要决定：现在该转圈等、该启动服务、该渲染 iframe、还是该报错。这个判断就是预览状态机。

### 实现原理（按一次真实打开过程拆开）

**一句话**：预览区不自己猜。它每隔几秒问后端一次「现在该显示什么」，后端把结论和理由一起回传，前端照着做。

**两层分工**：后端负责「判断」，前端负责「执行和显示」；判断只在一个地方发生。界面一共 9 种状态：刚进入 / 沙箱启动中 / 沙箱不可用 / 没有项目 / 等对话完成 / 自动启动中 / 手动启动中 / 运行中 / 启动失败。

**先分清谁在跑（这是理解全局的前提）**：主链路是 `/api/agent/sandbox/chat` 进来后，后端把 prompt 写进沙箱临时文件，用 `sandbox.commands.run` 起 `claude-code-runner.js`；Claude Agent SDK 的 `query()` 循环**在沙箱内**执行，模型请求也从沙箱出网。后端只负责三件事：起进程、喂 prompt、读 stdout 上的逐行 JSON 事件，再转成 SSE 写给浏览器。仓库里另有一条 `claude-out-sandbox` 方案（SDK 在宿主进程、工具通过 `opensandbox` MCP 落回沙箱），但文档写明「不接入 dispatcher」，前端也不调它。不管哪条，**SSE 事件对象都在后端进程里**——这是活跃流能用内存 Map 登记、且只能在本实例看见的原因。

#### 一步步发生了什么

1. **打开项目**：预览面板是常驻挂着的（切到别的 Tab 不会销毁），挂载时先查一次状态。
   - 常驻怎么做到的：`WorkspacePanel` 里只有预览页是**一直渲染**的，非激活时加 `hidden` 类收起；而文件、历史、Git、环境、部署这些页是条件渲染，切走就卸载。右侧整个工作区收起时也是**宽度折叠**（宽度归零、`pointer-events: none`），不是从 DOM 里移除。
   - `isVisible` 只做两件事：切回预览时发一次静默状态校验（失败不把界面打成错误态）；以及非 HMR 框架或有未消费的保存时触发一次刷新。它不影响挂载。
   - 为什么：如果每次切回预览页都重新挂载、重新发一次启动请求，服务就会被重复启动；iframe 也会重建、闪一次白。
   - 代价：隐藏期间轮询不会停。但轮询只在启动类状态发生，且有 3 分钟总超时，不会变成后台一直打接口。
2. **后端并行问五件事**，全程只读缓存，不会因为「查一下」就顺手把沙箱创建出来。
   - ① 主聊天还在输出吗：扫内存里的活跃流和会话状态。**为什么**：AI 还在改代码时启动出来的服务是半成品，等它写完再起才有意义。
   - ② 启动服务的流程在跑吗：查临时流注册和会话流。**为什么**：已经有人在起了，就别再起一次。
   - ③ 沙箱在哪个阶段（没有 / 启动中 / 就绪 / 出错）：只读缓存。**为什么**：状态查询要便宜、要没副作用；否则「问一句」变成「顺便开一台机器」。
   - ④ 有没有可预览的项目：沙箱活着就直接列文件，找项目入口信号（`package.json`、`index.html`、`requirements.txt`、`go.mod`、常见前端框架配置等），并排除 `.git`、`node_modules`、`dist` 这类运行时和产物目录；沙箱不在了，就按「本地/对象存储的工作区 → 版本快照」三级回退再找一遍。**为什么**：沙箱回收后留下的常常只是空目录或内部临时文件，只看沙箱会把明明有项目的判成「没有项目」；而只判断「有任意文件」又会让用户发一句「你好」就误触发启动。所以把「有文件」和「有可预览的应用」拆成两个判断。
   - ⑤ 端口真的还活着吗：只在「记录里写着正在运行、且没有启动/导入任务在跑」时，进沙箱发一次 HTTP 探测，连探 2 次、间隔 1 秒，任一次返回正常就算健康。**为什么**：记录是上一次写的，用户可能让 AI 把服务杀了，不实测就会一直报「运行中」、页面白屏；连探两次是因为热重载那一瞬间会短暂不通，探一次容易误判。分不清「进程没了」和「进程在但报错」也没关系，两种都引导用户点重试。
     - ⚠️ 这里的「2 次」是**状态接口的探活**，和启动收尾的 30 次检查不是一回事，见下文「两个探活别混」。
3. **后端给一个明确结论**：把上面五件事汇总，按固定优先级选出一个动作，并附一句原因——能显示就显示；有明确失败就提示重试；启动中/导入中就等；主聊天在跑就等对话；沙箱在启动就等沙箱；沙箱出错、没文件、没有可预览项目各走各的空态；沙箱还没好就先启动沙箱；有项目但没跑起来就去启动服务。
   - 为什么带 reason：出问题时不用靠猜「它刚才到底为什么转圈」，日志和界面能对上。
   - 为什么固定优先级：几个条件可能同时成立（例如「沙箱没好」和「对话还在跑」），必须有个谁先谁后，不能靠代码写到的先后顺序碰运气。
4. **前端只做一次决策**：把「后端状态 + 三份本地上下文」喂给一个不带副作用的纯函数，得到唯一动作，一次性切到 9 个状态之一。
   - 为什么用纯函数：同样的输入永远得到同样的输出，好测试、好回放，也杜绝了「几处代码各自改状态、谁晚到谁覆盖谁」。
   - 三份上下文分别是：① 前端认为的主对话是否在输出；② 这次是哪个入口打开的；③ 本轮是否已经自动启动过一次。三者的作用不同，见下文「决策函数的三个本地输入」。
   - **不要说「这三件事只有前端知道」**：第①件后端也返回 `isMainChatActive`，只是数据源不同；说成「只有前端知道」会被追问打穿。
5. **对话期间压住「可延迟」的结论**：AI 还在输出时，「没文件 / 去启动 / 空态」统一改成「等待对话完成」；但「渲染、启动中、失败、沙箱相关」这些关键结论不被覆盖。**为什么**：AI 还没写完就闪一下「没有项目」，体验很差；反过来，服务真挂了却一直显示等待也不行。
6. **真要启动服务，走一条独立的临时会话**：它不占主聊天、不产生用户可见的聊天气泡、也不生成版本快照；用专用提示词让模型只做三件事——装依赖、按固定端口把服务跑起来、写一份项目清单。
   - 为什么单独一条流：启动服务是平台内部动作，不该混进用户的对话历史，也不该占掉「同一时间只能跑一个对话」的名额。
7. **启动结束后由后端收尾**：实测端口是否健康 → 判断项目是什么框架 → 记录端口和入口路径 → 生成预览地址 → 发「预览就绪」通知。
   - 为什么把拼地址、判健康交给后端：以前是让模型再调一次工具去换链接，模型可能忽略工具返回的错误、继续说「预览好了」，用户点开是空白。现在少一次模型往返，结果也可信；固定端口之后，项目清单、框架配置、数据库记录和前端状态接口读的是同一个数，不会再对不上。
8. **前端按状态渲染**：只有「运行中」才挂 iframe；支持热更新的框架不整页刷新，其他框架才加刷新参数；卡在启动类状态时按**指数退避**轮询（3 秒起、每次 ×1.5、封顶 30 秒，累计 3 分钟仍没进展就报错让用户手动重试）；已经在看的预览不被新一轮对话的遮罩盖掉。
   - 为什么还要轮询：通知事件可能在重连时丢，光靠事件会让页面永远转圈。
   - 为什么不能固定 3 秒一直问：见下面「优化前后」，这么干曾把状态接口的成功率打到 18.6%。

#### 竞态到底怎么消失的

- **根因不是时序，是决策点分散**：轮询、聊天流、启动流、沙箱状态这四个异步来源以前各自改界面状态，谁最后回来听谁的。
- **单点决策**：现在只有一处能决定状态，其他来源只提供素材；决策结果自带原因，便于审计。
- **用「本轮启动时间」区分新旧失败**：失败记录是粘性的，只有下一次启动成功才会被覆盖；而新一轮启动开始时并不清账，于是「正在重启」和「上一轮已失败」会同时为真，界面在两种样式之间来回跳。做法是：取本轮启动的开始时间（会话流和临时流两个来源里取更早的那个），拿它去比失败时间，失败发生在本轮之前就当残留丢掉。
  - 为什么不用「启动流是否还在跑」这个布尔量：本轮真的失败时，流收尾那几秒会把错误掩盖掉，用户又被卡在转圈上。取更早的时间，是「宁可多报一次错，也不吞掉真错误」。
- **失败信息整组生效**：失败相关的六个字段要么一起返回、要么一起不返回。因为前端只要看到「有失败原因」就会短路到重试态，单独改状态字段没意义，数据必须自洽。

#### 四个源具体在哪（4 月 24 日前后是两种问题）

| 源 | 历史实现 | 它写了什么 | 现在在哪 |
|---|---|---|---|
| 定时轮询 | `H5Preview.tsx` 的 `SANDBOX_BOOT_STATUS_POLL_INTERVAL_MS = 3000` + `setInterval` 拉状态（`d6d9346`，4-28） | 每 3 秒用接口结果覆盖 `status` / `url` / `port` / `error` | `H5Preview.tsx:278-318`，改指数退避，结果只喂决策函数 |
| 聊天流 | 同一个组件里 `chatStatus` / `conversations` 推出 `isChatting`、`hasCompletedConversation`（`45a786c`，4-10） | 决定「等待对话」还是「可以启动」 | `H5Preview.tsx:126-130`、`244-274`；后端对应 `isMainChatActive` |
| 启动服务流 | `useStartService` 的 `onSuccess` / `onError`（`45a786c`） | 成功写 `running`，失败写 `error` | 临时会话 + 后端 `isStartServiceActive` → `subscribe-stream` |
| 沙箱通知 | `useH5PreviewEvent` 的 `preview_starting / preview_ready / error`，后来是 `sandbox_ready / sandbox_error` | 直接写 `starting / running / error` | `H5Preview.tsx:470-477` → `sandboxMarkReady` → 重新走决策 |

**打起来的原始记录就在提交说明里：**

- `45a786c`（4-10）：「`sandbox_build_url` 成功后不发 SSE，`onSuccess` 仅清日志，`hasAutoStartedRef` 阻断后续状态检查，预览永远不更新」——于是补了一次手动拉取 + `setH5PreviewState`，启动流成了第二个写入口。
- `d6d9346`（4-28）：「sandbox_ready SSE 可能在连接重连或页面切换时丢失，启动中状态用状态接口兜底推进」——加了 3 秒轮询，轮询成了第三个。

**分期（这一条和原稿的写法有出入）：**

| 阶段 | 形态 | 问题 | 修法 |
|---|---|---|---|
| 4-24 前 | 四个源各自 `setH5PreviewState` | 谁晚到谁覆盖，界面横跳 | `86d6411` 引入 `h5Phase` + 纯函数，收成一个写入口 |
| 5-19 后 | 后端状态接口开始返回 `previewDecision`，前端只执行 | 决策输入不全、判据错（导入场景等） | 8 月八连修 |
| 6 月 | 固定 3 秒轮询 | 沙箱卡住时持续打接口，成功率塌到 18.6% | `7bd1b14` 改指数退避 |

原稿把「收敛成单点决策」放在 8 月，实际**后端从 5-19（`a5ea5054`）就开始返回 decision 了**；8 月修的是判据和输入（比如 8-10 `93aa99c7` 的旧失败过滤），不是重新收敛。

**为什么这个分期重要**：4 月前的问题是「多个写入口」，修法是收敛；5 月后的问题变成「一个写入口，但输入不对」，修法是补条件。两类的修法完全不同，混着讲会被追问「既然已经收敛了，为什么还横跳」。

#### 时间戳 vs runId：成本账要说准

先给结论：**现在的实现是次优解，不是取舍。** 当时选它，是因为 `failedAt` 一行就能拿到；不是算过 runId 的收益之后主动放弃。

| | 时间戳（现状） | runId |
|---|---|---|
| 失败记录 | `failedAt` | `failedAt` + `runId` |
| 判断时读什么 | **两处**启动时间：内存流 `startTime`、Redis `registeredAt`，取更早 | 一处 `runId`，和失败记录里的比 |
| 比较方式 | `<`（谁更早） | `!==`（是不是同一轮） |
| 受什么影响 | 同毫秒、时钟回拨、跨实例时钟偏差 | 同毫秒撞号（加个后缀即可） |
| 要改哪里 | — | 启动时生成、写失败时携带、状态接口读取；**前端不参与** |

**三个常见的说错处：**

- ❌「runId 要前端比较」——比较在 `isStalePreviewFailure`（`h5-preview-status.service.ts:127-140`），前端只消费 `previewDecision`。
- ❌「要跨刷新持久化」——`runId` 和 `failedAt` 存在同一个 `preview` 对象里，本来就在 Redis / DB，没有新增持久化问题。
- ❌「只是罕见 case」——单副本下罕见，多副本下时钟偏差是常态。

**为什么现在还是时间戳：** 主症状（重试时界面在启动中和失败之间跳）已经被时间比较消掉了；剩余风险在单实例、低频启动下没暴露。但判断侧要读两处再取 min，本质是在补「两份时间可能不一致」这个坑——这已经是方案的成本，不是零成本。

**面试口径（别说「图省事」，也别编排期）：**

> 这版用的是时间比较：失败记录写失败时刻，判断时读本轮启动时间，早于本轮就算陈旧。它解决的是主症状——重试时界面在启动中和失败之间跳。
>
> 代价是依赖时钟。而且判断侧要读两个来源（内存流和 Redis 流状态）再取更早的那个，本质是在补「两处时间可能不一致」这个坑。同毫秒、回拨、跨实例偏差都会影响；取 min 是把偏差方向压到「宁可多报错」。
>
> 更彻底的做法是每轮一个 runId，失败记录挂上去，判断比相等而不是比大小。改动只在后端，前端不参与。当时没做，是因为主症状已经被时间比较消掉，剩余风险在单实例低频下没暴露。多副本常态化之后，这是我会优先补的一处。

反向的坑也要防：**不能为了显得像取舍，编一个「当时排期紧所以砍了」的故事。** 面试官接一句「砍了什么、压力来自哪」就露馅。真实说法是当时没往这个方向想，现在知道边界在哪、重写会怎么做。

#### 决策函数的三个本地输入（别讲成「只有前端知道」）

| 输入 | 代码位置 | 含义 | 存在哪 |
|---|---|---|---|
| `isChatting` | `web/src/pages/Chat/components/preview/H5Preview.tsx:126-130` | 前端认为主对话在输出（chatStatus 为 streaming / submitted，或首轮 prompt 在跑） | 内存 |
| `source` | `web/src/stores/usePreviewStore.ts:19` | 本次触发入口：project-open / git-clone / status-check / manual | 只在这一次调用里，不持久化 |
| `autoStartAttempted` | `web/src/stores/usePreviewStore.ts:117` | 本轮是否已经自动启动过一次 | 内存 |

三者的目的各不相同：

- **`isChatting` 不是「只有前端知道」。** 后端也返回 `isMainChatActive`，只是算法不同（见下一节）。两份都要，是因为各有盲区：前端点发送就立刻为真，后端要等流注册；反过来流关闭后后端可能还短暂为真，前端已经结束。决策时取「或」（`usePreviewStore.ts:270`）。
- **`source` 决定「谁有权按启动键」。** 只有 project-open / git-clone / manual 允许自动启动，轮询带的 status-check 被白名单排除（`usePreviewStore.ts:655-659`）。目的是防止服务起不来时，轮询每几秒触发一次启动。另有一个会话级来源 `stuckRecoverySource`（`H5Preview.tsx:131-136`），表示这个会话是不是 Git 导入来的，只用于「卡在等待对话」的恢复，避免普通对话结束瞬间被误判成导入卡住。
- **`autoStartAttempted` 保证同一轮最多自动启动一次。** 否则会出现「启动 → 服务没起来 → 后端仍返回 start-service → 再启动」的循环。它在 no-files / no-sandbox / error / 切换会话时重置，因为这些状态表示「现在不能启动」，不是「已经启动过」。

三份上下文都不落任何存储。刷新页面会清零，靠后端的启动流幂等闸兜底。

#### 多实例下的盲区（追问最容易打到这里）

`isMainChatActive` 的算法是「先筛内存、再用数据库校正」（`backagent/src/services/chat-stream-activity.service.ts:21-61`）：

```ts
const activeStreams = streamManager.getAllActiveStreams()   // 进程内 Map
  .filter(s => s.sessionId === sessionId);
for (const s of activeStreams) { 查会话，要求 status === RUNNING 且 kind === 'chat' }
return null;   // 内存为空 → 直接返回，数据库一次都没查
```

数据库在这里的角色是**校验内存筛出来的候选**，不是独立数据源。所以请求落到不持有这条流的实例时，会返回「没在对话」，而数据库里明明写着 RUNNING。

**为什么不把数据库提到第一步**：`RUNNING` 是粘性的，进程崩溃或重启后不会自动变化。直接信它，用户会被永久卡在「等待对话完成」，新对话也会被会话锁拒绝。所以必须先有一个「流是否真活着」的判断——而它要么查内存（便宜，只在本实例有效），要么走 Redis 的流恢复（跨实例，但每次要建订阅者再取消，成本扛不住状态接口的高频轮询）。

漏判之后有三道兜底：

| 兜底 | 位置 | 作用 |
|---|---|---|
| 启动来源白名单 | `usePreviewStore.ts:655-659` | 轮询不能触发启动，误判只可能发生在切会话那一下，不会持续 |
| 启动流幂等 | `backagent/src/services/sandbox-chat/orchestrator.service.ts:121-137`，查 Redis | 跨实例有效，挡住重复的启动请求 |
| 会话锁 | `backagent/src/services/sandbox-chat/conversation-bootstrap.service.ts:281-315`，查 Postgres | 同一会话已有 RUNNING 就返回 423，前端提示「当前对话正在进行中」 |

所以最坏结果是一次被拒绝的启动请求加一句提示，不会出现两个执行体同时写同一个沙箱。

修法：把数据库从「校验候选」改成「入口」——先按 sessionId 查 RUNNING，再用内存或 Redis 的轻量 key 验证活性。彻底的做法是用递增 `runId` 划代次，不再依赖「谁还活着」这种瞬时判断。

#### 为什么要加探活（2026-10-28 那次修复）

**症状**：预览地址还挂在界面上，但打开是白屏，或者一直转圈，没有任何错误提示。

**根因**：状态是「读记录」读出来的，不是「测出来」的。只要 `preview.status === 'running'` 且有 URL，就直接返回 running / healthy，没有任何一步去问端口还在不在。而把服务弄死的几条路径都不写这条记录：

- dev server 起在前台（没有 `&`），启动会话一结束，进程被一起带走，端口没了，记录还是 running；
- 「强制重新生成」原来只是重新发一遍启动指令，没有真的杀旧进程；杀进程的匹配规则也认不出 `/usr/bin/npm` 这种绝对路径，旧进程活着，新进程起不来；
- 用户在聊天里让模型把服务杀了、进程被 OOM、沙箱被回收——这些都不经过平台的停止接口。

前两条在探活之前就已经出过事故，只是当时的表现是「点了重生成没反应」「预览 502」。

**修法：同一天三个提交，依次补三个洞**

| 提交 | 改了什么 | 解决哪一条 |
|---|---|---|
| `bf82f27a` | system prompt 强制 dev server 以 `&` 后台启动 | 前台进程随启动会话结束被杀 |
| `b4d56536` | 强制重生成真正杀进程；补绝对路径匹配；状态优先级改成「启动 / 导入」高于「running」 | 旧进程没死、重启期间状态倒挂 |
| `48a71597` | 状态接口加探活，并区分「连不上」和「HTTP 报错」 | 记录说 running、实际已经死了 |

**为什么是 2 次、间隔 1 秒**：`--reload` 和 vite 重启会短暂关掉端口，探一次容易把正常重载误判成失败。服务健康时第一次就命中，几乎没有额外延迟。

**为什么两种失败都只给「重试」**：连不上说明进程没了；4xx / 5xx 说明进程还在但报错。后者看起来更像「代码有问题」，但实际更常见的原因是 AI 把服务起在了前台、或者用户刚让 AI 杀过——再让 AI 去修，只会重复同一个错误。所以前端对这两个 reason 隐藏了「让 AI 修复」按钮（web `e43012d`）。

**为什么只在「running 且没有启动 / 导入」时探**：重启窗口里端口本来就是断的，这时探活会把正常重启判成失败，还会和启动流程抢结论。

#### 两个探活别混（第一次失败时不会输出任何状态）

| | 状态接口探活 | 启动收尾检查 |
|---|---|---|
| 位置 | `backagent/src/services/h5-preview-status.service.ts:255-299` | `backagent/src/services/h5-preview-start-finalizer.service.ts:241-296` |
| 参数 | **2 次**、间隔 1 秒，任一次成功即健康 | **最多 30 次**、间隔 1 秒；连续两次命中致命日志才提前结束 |
| 什么时候跑 | 记录是 running，且没有启动 / 导入在跑 | 启动服务结束之后 |
| 失败怎么输出 | 两次都结束才返回一次 error | 不逐次报错，只推进度 |

**第一次探测失败的那一刻，后端不输出任何状态。** 探测是在一个 HTTP 请求内部顺序执行的：第一次失败只记下 `lastStatusCode`，然后 `await` 1 秒再探第二次，`res.json()` 还没执行，也没有 SSE 事件。

前端这时只是在等响应：`h5RefreshStatus` 把 `h5StatusFetching` 置 true（这个字段不参与渲染），`h5Phase` 没有变化，iframe 继续显示。**用户屏幕上什么都不会变。**

1 秒后的两种结局：

| 第二次探测 | 后端返回 | 用户看到 |
|---|---|---|
| 成功 | `status: running`、`previewStatusReason: healthy` | 无变化。用户不知道刚才失败过一次 |
| 也失败 | `status: error`、`previewStatusReason: unhealthy`、`previewDecision.action: restart` | 错误面板，iframe 被卸载 |

失败时的字段：`failureStep: health`；`failureReason` 是 `preview_service_error`（HTTP 4xx/5xx）或 `preview_service_stopped`（连不上）；文案对应「预览服务异常（HTTP 502），请点击重试」或「预览服务已停止，请点击重试」。

前端在 `decideNextH5Action` 第一步就短路（`usePreviewStore.ts:259-266`），`h5Phase` 变 `error`；渲染条件是 `isRunning && h5PreviewUrl`，`isRunning` 变 false 后 **iframe 直接被卸载**，换成全屏错误面板。这两个 reason 不显示「让 AI 修复」，只有「重试预览」和「查看日志」。

一个容易被忽略的细节：`silent: true` 只抑制 `wait-chat`，不抑制 `restart`（`usePreviewStore.ts:711-713`）。所以「切回 Tab」触发的静默校验，如果两次都失败，一样会把界面切成错误态、卸载 iframe。这个探活没有「先观察一次、下次再说」的缓冲，2 次就是最终判定。

对比启动那条路径：第一次失败不报错，继续探，每次探测前还会发「正在检查端口 x，第 n/30 次」的进度。两条路径的共同点是**单次失败都不对外输出状态**，区别是一个 2 次下结论、一个 30 次下结论。

#### 八个修复里挑三个展开（面试够用）

| 现象 | 为什么会发生 | 修法为什么有效 |
|---|---|---|
| 重试时「启动中 ↔ 失败」来回跳 | 上一轮的失败是粘性记录，新一轮启动又不清账 | 用本轮启动时间做代次区分，旧的失败不参与本轮渲染 |
| 端口被占导致服务起不来 | 清理端口时把「向外发起的连接」也算成占用了 | 只查处于监听状态的端口，并且只结束能确认归属的进程 |
| 沙箱回收后判成「没有项目」 | 沙箱里只剩空目录/内部残留，真正的文件在版本快照里 | 三级回退（本地/对象存储 → 版本快照），并把运行时目录从「项目信号」里排除 |

### 优化前后（提交记录还原）

**原来怎么做**：预览区没有统一决策点——定时轮询、聊天流、启动服务流、沙箱通知各自往界面写状态；启动服务流和主聊天还共用同一个续传标识，刷新页面会再触发一次自动启动，同一沙箱并发部署直接报错退出；启动过程在界面上是一段滚动的流式文字；失败要等 30 次健康检查（约 60 秒）才告诉用户；状态轮询固定 3 秒、没有退避也没有总超时。

**为什么必须改**：
- 用户侧：状态来回跳、白屏、卡在「启动中」、等一分钟才看到失败。
- 平台侧：固定 3 秒轮询在沙箱卡住时会一直打状态接口，多用户叠加上去等于自我 DDoS——提交说明里记着一次告警，该接口 30 分钟窗口成功率从正常 99% 塌到 18.6%。
- 排障侧：谁最后回来听谁的，出了问题只能靠猜。

**怎么改**（按时间线，每条对应一类问题）：
1. 4 月：前端引入 `h5Phase` 状态机（4-24，`86d6411`），拆开「启动中」与「空态」；用「4 步检查清单」的进度卡片替掉流式文字；启动服务流改用独立续传标识，状态接口主动告诉前端「启动流已在跑」，阻止重复启动。4-28（`d6d9346`）加 3 秒轮询，兜底会丢的 `sandbox_ready` 事件。
2. 5 月：后端状态接口开始返回 `previewDecision`（5-19，`a5ea5054`），「后端判断、前端执行」的两层分工成形。
3. 6 月：轮询改指数退避（3 秒起、×1.5、封顶 30 秒）+ 3 分钟总超时，超时落到错误态由用户手动重试；健康检查加快失败——从第 2 次起定期扫开发日志，连续两次命中同类致命错误（缺文件、缺依赖、语法错误）就立刻停，端口冲突不算致命，识别不了就走原流程。
4. 8 月：竞态八连修——重点不是收敛（5 月已经收敛了），是补判据和输入：用本轮启动时间区分新旧失败（8-10，`93aa99c7`）、端口扫描只查监听状态、沙箱回收后回退到版本快照、初始化不再闪空态、生成结束能正确自动启动、导入仓库不等对话。
5. 10 月：同一天补了三个洞——system prompt 强制 dev server 后台启动（防 502）；强制重生成真正杀进程、补绝对路径匹配；状态接口主动探活，并区分「服务停了」和「服务还在但报错」，两者都只引导重试。

**效果怎么样**：
- 有量化、可讲：**「项目缺文件」这个复现场景，失败等待约 60 秒 → 约 6 秒**，配套 48/48 单测通过。只针对这一个场景，不是线上整体预览耗时。
- 有量化、但别讲反：99% → 18.6% 是**优化前那次事故**的接口成功率；改完不再持续高频轮询，没有「恢复到多少」的记录。
- 其余只讲现象：不再跳变、不再白屏、不再卡「启动中」、失败原因可读；其中「重试跳变」那次修复只改后端一处，前端一行没动。
- 没做的：全量耗时对比、线上预览成功率统计。

### 面试怎么讲

**一句洞察（开场用）：**

> 竞态的根因不是时序，是**决策点分散**——四个异步源（轮询、聊天流、启动流、沙箱阶段）各自在改状态，谁晚到谁覆盖谁。

> 补一句边界：这是 4 月前的形态。5 月后端开始返回统一决策之后，写入口只剩一个，后面再出现跳变，原因换成了「决策输入不全」，不是「多处写」。被追问「不是收敛了吗，为什么还跳」时，这一句能接住。

**修法：** 把散落各处的判断收敛成一个纯函数，单点决策 + 显式原因；再针对「旧结果覆盖新结果」用**本轮的启动时间**区分这是上一轮的失败还是这一轮的失败。

**八个修复串成的故事线（讲 3 个就够，其余备用）**：上面那张是原理版，下面这张是口述速查版，挑哪三个讲都行，不是两份不同的清单。

| 现象 | 原因 | 修法 |
|---|---|---|
| 重试时「启动中 ↔ 失败」来回跳 | 上一轮的失败和这一轮的启动混在一起 | 用本轮启动时间区分 |
| 初始化时 loading 跳变 | 多处各自改状态 | 收敛到单点决策函数 |
| 生成结束后卡住不启动 | 阶段推进条件缺失 | 补上自动启动条件 |
| 初始化项目时预览闪一下空态 | 空态渲染早于数据就绪 | 调整渲染时机 |
| 导入仓库后一直等对话完成 | 等错了条件 | 导入场景不等对话 |
| 端口被占导致服务起不来 | 把出站连接误判成端口占用 | 只查处于监听状态的端口 |
| 沙箱回收后判成「没有项目」 | 只看沙箱不看快照 | 同时读版本快照 |
| 残留文件判成 no-files | 沙箱回收后残留 | 清理残留文件再判断 |

**五个高频追问（这轮补的，答不上会被判「只会背结论」）：**

| 追问 | 答法 |
|---|---|
| 这三个状态存 Redis 吗 | 不存。Redis 只放 SSE 事件（断点续传）和启动流的 streamId；活跃判断在进程内存，会话状态在数据库。 |
| 后端也有「在对话」状态，为什么前端还要传一份 | 数据源不同，各有盲区：前端点发送立刻为真，后端要等流注册；流关闭后后端可能还短暂为真，前端已经结束。决策时取「或」。 |
| 多副本怎么办 | 认：状态接口可能漏判，靠来源白名单 + Redis 启动幂等 + 数据库会话锁兜底。修法是先查数据库 RUNNING 再验活，或用 runId。 |
| 会话不是跑在沙箱里吗 | 是。主链路 runner 在沙箱里跑，SDK 循环和模型请求都在沙箱；后端起进程、读 stdout、转 SSE。另有 `claude-out-sandbox` 新方案在宿主侧跑，但没接 dispatcher。 |
| 为什么不用「启动流还在跑」这个布尔量 | 流收尾那几秒，本轮真实失败已经落库、但流还是 active，布尔量会把它当残留吞掉。用失败时间和本轮启动时间比。 |

### 不能夸大

- 「缺文件场景 60 秒 → 约 6 秒」只针对**这一个复现场景**，不是线上整体预览耗时。
- 没有做全量耗时对比，只有往返次数和场景复现时间可以作为证据。
- **「这三件事只有前端知道」是错的说法**，第一件后端也有；照原稿讲会被追问打穿。
- 多实例盲区只在**服务多副本**时成立。单副本下内存表覆盖全进程，判断是准的。没有做过多副本下的一致性验证，别讲成「已经解决」。
- 决策函数里 `restart` 分支没有重置 `autoStartAttempted`，与字段注释不一致，属于已知瑕疵；被问到直接认。
- `qpilot-code/` 里「前端显式状态机 idle → starting → ready + inflight token」的旧描述是更早的版本，已于 2026-11-05 替换，两边口径现在一致。

## 2. 部署链路（案例 4）

### 是什么

把沙箱里的项目变成一个能通过域名访问的站点。

### 实现原理（按一次发布拆开）

**一句话**：点「发布部署」其实是在聊天里发了一条带特殊标记的消息，让一个被严格限制的小助手先体检、再打包、再上线；每一步在聊天里看得见，真正干重活的是后端固定流程，不是模型自由发挥。

> 口径提醒（代码核对）：「点部署 → 一条持续回传进度的通道（SSE）」是旧的一键入口，现在仍保留在预览弹窗等地方；主按钮已经换成「聊天工作流 + 受控工具」。面试说「两条都在，主路径已换成受控工具」最稳，别说成全量替换。

#### 一步步发生了什么

1. **点按钮，先定名字**：域名输入框为空就让小助手自己想名字；手填了就先做域名预检，返回「可用 / 这个项目已经绑过 / 可以从自己别的项目迁过来 / 被别人占了」几种结果，被占就提示并停住。
   - 为什么放最前：一次部署要几分钟，等镜像都构建完才发现名字冲突最亏；而且名字会写进部署记录，事后改容易和绑定关系对不上。
2. **存储预检（只读）**：读项目清单里的一个标记，判断「这次重新上线会不会把用户数据带走」。只有标记明确说有风险才弹确认框，并把原因用中文写出来；标记说安全、或者老项目根本没这个标记，就不弹；清单读不到时后端会返回一个「读取失败」标记，但前端当前不据此拦人（这个判断改过一轮，见「优化前后」）。
   - 为什么不每次都弹：每次都弹等于没弹，用户会形成无脑点确认的习惯。
   - 为什么读失败不拦：读不到清单不代表项目有风险，为这个把部署挡住，误伤比漏掉更多。后端仍把失败标记返回出来，方便排查。
3. **发起**：前端往主聊天发一条真实消息，带上「这是部署预检」的标记和本次参数（项目、包管理器、域名策略、用户是否已确认风险等）。
   - 为什么不新开一个隐藏后台任务：用户能在聊天里看到每一步和构建日志，出问题也能直接让 AI 接着修；部署记录、审计、进度卡都能复用聊天这条链路。
4. **后端组装这次的运行环境**：生成一个「本次操作 ID」，签发一枚短期令牌，把接口地址、令牌、参数注入进去；同时只开放 5 个部署专用工具（预检、构建并推镜像、上线并等就绪、查状态、查日志），关掉项目级的常规配置读取。
   - 为什么要限工具：不限的话模型会看到数据库、知识库、任意网页抓取等一堆无关工具，「受控」就名存实亡；关掉项目配置是为了让「聊天 / 启动服务 / 部署」三套规则不互相串味。
5. **小助手按提示词分三步走**：先体检（检查并补齐打包说明、忽略清单、构建命令、端口、环境变量）→ 再构建并推镜像 → 最后上线并等就绪。每步都能单独查状态和日志，失败可以单步重试。
   - 为什么要分步而不是一个大工具：出问题时能一眼看出卡在打包还是上线，也方便只重试失败那一步。
6. **每次工具调用都要过令牌校验**：工具必须带令牌和「本次操作 ID」；后端验签名、有效期、用户和项目是否对得上、参数有没有被改过（用参数摘要比对），任一不符就拒绝。
   - 为什么摘要只算「静态参数」：域名这类名字是小助手运行时才想出来的，令牌是在请求开始就签发的，把它算进摘要会永远对不上（这是实测踩过的坑）。所以只锁项目、包管理器、是否用沙箱这些一开始就确定的东西，运行时字段由后端自己再校验。
7. **真正的重活由后端固定流水线做**，模型插不上手：构建镜像 → 推到镜像仓库 → 生成集群里的运行声明（一个跑应用的说明 + 一个稳定的内部访问入口）→ 应用 → 等实例就绪（有超时上限）→ 写部署记录 → 清代理缓存 → 截图。
   - 为什么不让模型做：这些步骤是确定的，用确定性的代码最可靠；上线那一步只认后端自己保存的镜像，模型不能塞一个任意镜像地址或任意配置进来。
   - 为什么同时建「稳定的内部访问入口」：容器重建、换机器后地址会变，写死的地址很快失效；有了稳定入口，数据库记录就不用跟着改。
8. **静态项目走更轻的一条**：不进沙箱的项目把构建产物传到对象存储，网关按域名直接返回文件；单个 HTML 还有专门的快速入口，不创建工程、不启动 AI，直接传完给链接并留一条可审计的记录。
   - 注意一个反直觉的点：**走沙箱的纯静态站点现在也统一走容器**。原因是对象存储那条路早期只收文本文件，图片等二进制文件会在收集时被丢掉，上线后图片全裂；容器里文件是完整的，代价是多花几分钟。
9. **域名怎么定（三级优先级）**：① 用户/前端指定了名字就用指定的（先清洗格式，再做重名处理）；② 没指定就复用这个项目历史上成功部署过的自定义标识；③ 都没有就用部署 ID 做哈希兜底，保证总能出一条链接。
   - 平台自己留着用的一级子域（监控、老入口等）不允许被部署占用：前端输入时实时红字提示并禁用按钮，后端在「所有绑定路径汇聚的那一处」再做一次权威拦截。顺序是**先放行历史上已经绑过的老记录，再拦新绑定**，避免误伤存量。
10. **写部署记录**：一次部署一行，记下域名标识、部署类型、状态、访问地址、后端目标地址、截图、耗时和失败原因；每一步还单独留审计记录。
    - 为什么一次一行：部署历史要能翻、能回滚对照；网关也只认这张表来查「这个域名该转给谁」。
11. **用户访问链接时**：请求先到网关 → 从域名里取出标识 → 查部署记录 → 容器部署就转发到集群内那个稳定入口，对象存储部署就直接读文件。转发失败时会清掉缓存、重查一次记录再重试；缓存有 5 分钟有效期，后台还定期巡检已上线实例是否还活着。
    - 为什么要清缓存重试：刚重新部署完，网关手里可能还是上一版的地址。
12. **失败怎么收口**：构建或上线中途失败只记为「一次尝试失败」的告警，只有这次部署整体失败才算终态失败；错误会回到聊天里，可以让 AI 接着修。
    - 为什么：AI 本来就会边修边试，把每次尝试都算成部署失败，监控会全是噪音。

#### 三个决策的取舍（代码核对版）

**① 从「模型手写 curl」改成「受控工具」**：原来让模型自己拼一个请求调部署接口，等于把接口地址和凭证都摊给模型。现在模型只能调那 5 个工具，令牌和本次操作绑定，真实凭证始终在后端。工具挂不上时还保留原来的 curl 兜底，保证不会「升级完反而不能部署」。这和案例 2 里那套 AI 受控写入方案是同一个思路；**区别是部署这条已落地，Git 那条没从界面接进去**，讲的时候要分开。

**② 存储预检为什么让「生成代码的模型」自己声明**：
- 曾考虑过「部署时扫项目文件去猜」——不准，误报漏报多；也考虑过「每次部署跑一次模型来判断」——太重，每次都要推理一遍。
- 最终做法是：在**生成阶段**就把约束写进提示词——要求模型在宣布「做完了」之前先自检，业务数据不许写在容器本地目录、SQLite、内存数组里，要改用平台数据库或上传接口；自检完把结论写进项目清单的 `isEphemeralStorage`，为 `true` 时还要写一句中文原因。部署预检只读这个标记，不贵也准。
- 所以它既是生成阶段的**约束**，也是自检**结果**，不是部署时扫出来的。三态：`true` 弹确认、`false` 不管、`null/undefined`（老项目）不拦截；后端另返回一个「读取失败」标记仅供排查，不参与弹框判断。
- 边界要诚实：标记由模型写，模型漏标就拦不住；而且它只解决「重新上线丢数据」，不承诺数据永不丢失。

**③ 双环境（Preview / Production，2026-10 新功能）怎么落地**：
1. 以前一个项目只有一套配置文件和一套数据库，改配置会直接影响预览、甚至影响线上。
2. 最小版拆成两个标准文件：预览用 `.env.development`，正式用 `.env.production`；数据库按项目需要再分配两套（同一个实例上不同的库和账号，互不授权），也就是后面口述里说的「数据库策略可选」。
   - 为什么用这两个文件名：主流前端框架本来就按模式自动读它们，不用另造一套机制。
3. 界面上把「环境变量」从部署面板里挪出来，做成和「发布部署」平级的一个 Tab，里面再分「本地预览 / 正式发布」两栏；保存时后端直接改对应文件，保留注释和无关行、整份原子替换，并用文件内容版本号防止「人和 AI 同时改、互相覆盖」，改完刷新文件树。
   - 为什么文件是唯一事实源：模型和界面看到的是同一份，不需要再维护一张可能不同步的表。
4. 构建时正式环境只带 `.env.production`，明确排除预览那份；预览只加载 `.env.development`。**为什么**：不能把测试用的连接串和凭据带上线。
5. 老项目给一次轻量迁移：旧 `.env` 复制成预览文件；有旧变量表就生成正式文件，没有就用旧 `.env` 内容生成、保持原行为；用到平台数据库时把连接串换成新分配的正式库；迁移成功后不再用旧文件。**为什么**：老项目不能一升级就变样。
6. 让模型知道变化：系统提示词加一条双文件约定，凡涉及启动、构建、接口地址、数据库，都先读对应文件；界面在 AI 正跑着的时候改了变量，不热更新当前这轮推理，下一轮才生效。**为什么**：不打断正在进行的推理。
7. 启用后自动让 Agent 适配并重启预览（笔记原话）。**边界**：这是「最小隔离」，没有发布计划、候选版本健康检查、失败保留旧版、密钥托管这些完整能力，别讲成完整的环境管理体系。

**补充（追问用）**：子域名部署白屏——部署时强制把构建的 base 路径改成根路径，否则挂在子路径下的静态资源会全部 404。

### 优化前后（提交记录还原）

**原来怎么做**（按时间线）：
1. 早期：一个项目的部署记录是**覆盖写**的（同一条记录反复更新），没有真正的部署历史；部署失败时界面会一直卡在 loading；域名还要单独点一个绑定按钮。
2. 容器部署把实例 IP 直接写进数据库，实例一重建地址就失效；代理连不上不会重试，缓存也没有过期时间。
3. 后来改成让模型主导部署，但工具没挂上，提示词里写的几个部署工具「永远不可用」，模型每次都退回去自己拼一个 curl 请求——接口地址和凭证等于摊给模型，还不能单步查状态、单步重试。
4. 只有一套环境，改配置会直接影响预览。
5. 存储风险确认最初用一个「是否标准存储」的字段判断，后来才改成读项目清单里的易失标记并展示中文原因。

**为什么必须改**：稳定性（实例重建就访问不了、失败卡界面）、安全性（凭证暴露给模型）、可运维性（没有历史、排障靠猜）、数据与配置隔离。

**怎么改**（挑能串成故事的几次）：
1. 4 月：部署记录改成「一次部署一行」，统一错误事件格式，界面不再卡 loading；容器部署引入稳定的内部访问入口，代理加一次重试、缓存 5 分钟过期、后台定期巡检，新入口创建失败还能降级回旧方式。
2. 6 月：把部署流水线拆成可观察的阶段、做成进度卡片，再把进度桥接到聊天状态流——这是后来「主路径变成聊天工作流」的起点。
3. 8-9 月：部署前加存储预检；接入受控 MCP 工具，让模型回到「分步、可查询、可重试」的路径，curl 只留作连接失败时的兜底。
4. 10 月：双环境最小隔离落地；随后发现「只创建两个配置文件、代码还读旧文件、预览也不重启」等于没生效，于是加了一条启用后自动发给 Agent 的适配指令，让模型改读取方式并重启预览；同时补上保留子域名黑名单（前后端都拦，已绑定的老记录放行）。

> 存储预检还有一段来回：最初「读取清单失败也弹确认框」，9 月初有提交明确把它去掉了，当前只在标记明确为有风险时弹。面试讲「只在明确有风险时弹」最稳。

**效果怎么样**：
- 能讲的是**现象与能力**：失败不再卡 loading、有部署历史可回看、实例重建不用改记录、代理连不上会自动重查重试、模型不再手写 curl 且每步可查可重试、只在明确有数据丢失风险时弹确认、双环境启用后配置改动能真正生效。
- 没有的：部署规模、成功率、耗时数字一个都没有，别编「提升了百分之多少」。
- 边界：双环境是最小隔离；存储预检依赖模型自己打标记，漏标就拦不住。

### 面试怎么讲：三个最值得讲的决策（① ② 必讲，③ 备用）

**① 部署从「模型手写 curl」改成「受控 MCP 工具」**

> 原来的做法是让模型自己拼一个 curl 调部署接口，等于把接口和凭证暴露给模型。改成接入受控的 MCP 工具：令牌和**本次操作**绑定，模型只能调这个工具，不能自己发请求。

（和案例 2 的 AI 受控写入方案是同一类思路，但部署这条已落地、Git 那条没接入界面，别混成一件。）

**② 存储预检：只在数据可能丢失时才弹确认**

> 容器重建会把数据带走。但不是每次部署都会丢——只有数据真的会随容器丢失时，才弹确认框并**说明原因**，否则每次都弹等于没弹。

**判断方式（代码核对）**：读项目下 `.qpilotcode` 清单里的 `deploy.isEphemeralStorage` 标记 + `ephemeralReason`。

- 曾经考虑过的两种方案都否掉了：**扫项目文件去猜**不准（误报漏报多），**让模型判断**太重（每次部署都要跑一次推理）。
- 最终是**让生成项目的模型在收尾时自己声明**：预检只读这个标记，不贵也准。
- **标记由模型写入**（`src/config/system-prompt.ts`）：提示词强制要求模型在声明完成前做持久性自检——不允许把业务数据写到容器本地目录/SQLite/内存数组，要改用平台数据库或上传接口；自检完再把结果写进 `.qpilotcode` 的 `isEphemeralStorage`，为 `true` 时还要写一句中文的 `ephemeralReason`。所以它既是**生成阶段的约束**，也是自检结果，不是部署时扫出来的。
- 三态：`true` = 弹确认；`false` = 数据不随容器丢失，不管；`null/undefined` = 老项目，不拦截。
- **读取失败的口径（按提交记录修正）**：后端会返回 `readError=true`，早期版本前端确实也据此弹框；9 月初有一次提交明确「去掉 readError 拦截」，当前代码只在 `isEphemeralStorage === true` 时弹。面试讲「只在明确有风险时弹」，**不要讲读失败也弹**。

**③ 双环境隔离（Preview / Production，2026-10 新功能）**

> 之前项目只有一套环境，改配置会直接影响预览。新增了 Preview / Production 双环境：环境变量文件分开、数据库策略可选，老项目给轻量迁移提示，启用后自动让 Agent 适配并重启预览。

**补充（追问用）：** 子域名部署白屏——部署时强制把构建的 base 路径改成根路径。

### 不能夸大

- 部署规模、成功率数字都没有，只讲设计和修复。
- 双环境是「最小隔离」，不是完整的环境管理体系。

## 3. 沙箱 Git：两条链路与权限边界（案例 2）

> ⚠️ 2026-11-05 按两个仓库的代码和一段真实对话记录核对：本节原来写的「凭证不出后端、模型只能拿令牌调接口」**只对一条没有接入界面的工作流成立**，不是线上现状。已重写，面试别再讲旧口径。

### 先讲清楚：实际在用的是两条路

**一句话**：同一个「提交代码」，在页面上点按钮和在聊天里说一句，走的是两条完全不同的路；而且凭证其实就在沙箱里。

#### A 路：Git 面板（页面点按钮）

1. 用户点「提交并推送」→ 前端先做**只读预警**：问后端「远程有没有新提交、本地有没有没提交的改动、两边会不会撞车」。
   - 为什么要先问：以前是点了之后才报冲突，用户白等一轮；现在分叉就拦住让先拉，只是落后就提示「会自动同步」，并列出**预估**可能撞车的文件（标「预估」，不等于一定冲突）。
2. 要不要 AI 写提交信息由用户勾选；勾了才让后端读工作区 diff 生成一条，用户填过的内容作为意图提示，生成结果可预览、可改，失败有兜底文案。
   - 为什么不让前端把 diff 传上来：内容以服务端读到的为准；生成前会过滤掉依赖目录、缓存等生成物，diff 太长会截断并提示。
3. 后端执行写入前再预检一次（拉远程、判断落后/分叉）：落后就自动同步，真分叉就阻止写入并给冲突辅助数据，让 AI 帮着解。
   - 为什么预检两次：界面那次是给人看的提示，真正执行前必须再确认一次，中间远程可能又变了。
4. 提交、推送由后端用真实凭证完成；顺带清理预览产生的临时文件、修「读取时擅自改工作区忽略清单」造成的假变更，以及「停止追踪某些文件」被误显示成「删除文件」的假冲突。
   - ⚠️ 界面上「一键提交清理变更」的引导在文档里仍标为**待实施**，别讲成已上线。
5. 结果回到界面；认证失败有自动重新授权入口。

#### B 路：LLM 对话（聊天里让 AI 提交）

1. 用户发「提交代码」→ 这就是一条**普通聊天**，请求里没有任何特殊标记。
2. 后端照常准备沙箱、启动模型运行环境；模型能用的工具里有「执行命令」，而且没有被禁止跑 git。
3. 模型自己看状态、看 diff、看日志，然后 add + commit，提交信息也是它自己写的；用户再说「推一下」，它就 push。全程没调平台 Git 接口，也没有用受控工具。
4. **为什么能成功**：项目克隆进沙箱时，后端是带着用户凭证的仓库地址去克隆的，这个地址会留在沙箱仓库的 remote 配置里；后端在推送类操作前还会再补一次。所以沙箱里 push 天然带着凭证，不需要临时令牌，也不需要后端代发。
5. **这条路缺什么**：面板那套预检（冲突/分叉检查、AI 提交信息、冲突辅助）一个都没经过。约束只有提示词里一句「不要自作主张提交，版本由用户在 Git 面板管理」——用户明确开口时，模型会照做。
   - ⚠️ 代码里还留着一段「禁止模型直接跑 commit/push」的拦截（写在部署到沙箱的运行脚本里），但真实对话记录证明这次没生效；失效原因我没确证，面试里**不要**说「有硬隔离」。

### 受控令牌方案：设计实现过，但没从界面接进去

**一句话**：这是为「AI 写入」设计的一套更严格的办法，能讲设计和威胁模型，**不能**讲成线上现状。

1. 只在一个叫 `git-write` 的工作流里启用：后端签发 30 分钟、带签名和载荷哈希的令牌，把接口地址、令牌、参数一起注入运行环境。
2. 票里只有用户、会话、操作类型（提交并推送 / 仅推送）、过期时间、随机数和摘要，**没有仓库地址和分支** → 模型没法指定往哪写；改任何一个参数，摘要对不上就作废。
3. 专用提示词明确要求「不许直接跑 commit/push，只能用注入的环境变量调后端那个受控接口」；后端验签、验过期、验载荷哈希，再做冲突和分叉检查，最后才用真实凭证执行。
4. **为什么不算线上现状**：后端这套能力在（接口、令牌服务、专用提示词都有），但当前前端能发的工作流只有普通聊天 / 部署预检 / 启动服务三种，**没有 git-write 入口**，从界面走不到这条路。
5. 设计价值仍然能讲：把「模型能碰什么」从一句约定变成机制——作用域收窄、载荷不可篡改、执行前统一预检、操作可审计。局限也主动讲：没接进去就等于没真正生效；30 分钟不是主防线。

### 性能那段（换沙箱之后）

**为什么突然变慢**：换到新的沙箱方案后，git 命令不再跑在本机，而是每执行一条都要发一次网络请求到远端沙箱、在沙箱里起一个进程。原来查一次状态要问十几件事（仓库根、分支、提交号、远程、有没有未提交文件、跟踪分支、本地超前几条、远程超前几条……），就是十几趟路费。

**修法不是换回旧方案（已经不能选），而是「一次问完」**：

1. 把同一个接口要问的所有命令拼成一段脚本，一次下发；例如提交推送把 `add / status / config / commit / 取提交号 / 取分支` 合成一次，版本差异把「仓库是否初始化、两个提交是否存在、改了哪些文件、每个文件改了什么、单文件模式还要取新旧内容」合成一次。
2. 每段命令的输出先做编码，再用固定标记分段打印；后端拿到一大坨文本按标记切开。
   - 为什么要编码：代码里什么字符都可能有，直接靠换行或分隔符切会串；编码后的字符表里不会出现标记用的下划线，切得干净。
3. 顺手做短路：没有差异就别跑后面的命令，提交不存在就别算 diff；沙箱不可用或脚本异常时降级到数据库/快照里已有的结果，不把用户卡住。
4. 收益口径（提交说明逐条可查）：状态/写入预检 10+ → 1 次；提交推送 6 → 1；仅推送 2 → 1；拉取前检查 5 → 1；远程 diff 4 → 1；分支列表 4 → 1。另外新增一个轻量信息接口，替代「写完再查一次全量状态」；拉取后的文件同步改成后台异步，不再阻塞响应。
   - 这组数字来自 4/29 那条「合并沙箱命令减少 RTT 开销、优化 7 个 Git 接口性能」的提交，不是估算，见下面「优化前后」。
   - 版本差异另有一次 7~9 → 1 的合并（5/29），文档里记着约 8.3 秒 / 7 跳 ≈ 1.2 秒每跳、目标 3 秒内、单测 20/20 通过。

### 优化前后（提交记录还原）

**原来怎么做**：4 月中旬之前，Agent 在沙箱里可以直接跑 `git commit` / `git push`，凭证也在沙箱里；第一版防护是用工具回调硬拦这两条命令、再在提示词里写「不许自动提交」。换到新沙箱后，每条 git 命令都变成一次远程调用，一个状态检查要问十几个问题、一次提交推送要跑 6 条命令。

**为什么必须改**：安全上，模型被注入就能拿凭证写任意仓库，只靠约定和固定命令拦截不够；性能上，远程命令按「次」收路费，用户明显感到卡。

**怎么改**（按提交时间线）：
1. 4/13 先硬拦自动提交，止血（这段拦截至今还留在部署到沙箱的运行脚本里，但实测没拦住）。
2. 4/29 合并沙箱命令，一次优化 7 个 Git 接口（就是上面那组数字）。
3. 5/29 版本差异 7~9 次 → 1 次，编码 + 标记分段。
4. 之后做了两件不同的事：**面板链路**补齐推送前预检、AI 生成提交信息、冲突辅助、清理假冲突（已落地）；**AI 写入**设计并实现了 `git-write` 受控令牌工作流（后端能力在、没从界面接入）。两条别混成一件。

**效果怎么样**：
- 往返次数这组数字有提交记录可查，可以放心讲；版本差异那条还有实测耗时拆解，但只针对那一条接口。
- 面板链路能讲的是「提交前会检查冲突和分叉、分叉拦住、提交信息可 AI 生成」这些能力与现象，没有成功率/耗时数字。
- ⚠️ 安全侧**不能**讲「凭证不再进沙箱 / 模型不再直接 push」；能讲的是「面板做了检查收口，对话链路靠提示词约束，另外有一套设计实现过但未接入的受控方案」。

### 面试怎么讲

**主版本（先摆两条路，再讲边界）**：

> Git 这里有两条实际在用的路：页面上点提交和推送，走后端接口，会先检查远程有没有新提交、有没有分叉；聊天里让 AI 提交，是模型在沙箱里用原生 git 命令做的，因为仓库配置里带着凭证，所以也能直接推成功，这条路上没有那套预检，靠提示词约束它别自作主张。另外我设计并实现过一套短期令牌、后端代执行的受控写入方案，但当时前端没有对应入口，没接进界面。

**被追问「我用对话提交怎么也成功了」**（真被问过，别绕）：

> 对，那条是对话链路，凭证在沙箱仓库的 remote 配置里（克隆时写进去的），模型用原生 git 就能推。我们靠提示词约束它不主动提交，用户明确要求时会照做。这是我知道的边界，也是后来做那套受控方案的原因。

**性能金句（这部分完全不受影响）**：

> git 本身没变，变的是「发一条命令要付的路费」。所以修法不是换回旧方案（已经不能选），而是把同一个接口要问的这些合成一次请求。

### 不能夸大

- 不讲「凭证不进沙箱 / 模型不再直接 push / 模型拿不到仓库凭证」——真实对话记录里模型用原生 git 提交并推送成功了。
- 受控令牌是设计实现过的 `git-write` 工作流，但没从界面接入；讲设计可以，讲成线上现状不行。
- 收益是**往返次数**，没有做前后耗时对比，不说「快了百分之多少」；版本差异那条只有「优化前单次实测拆解 + 优化目标」。
- 旧沙箱方案已从源码里移除（依赖、变量、注释都清理过），不能说「还能切回去」。

## 4. 会话与协作（案例 5）

### 五个功能点，逐个按流程拆

> 按实际五项重排（原稿编号有重复）；「正在输出时」的处理顺序也按代码修正过。

#### 1）编辑后重发

1. **谁能编辑**：只有「最后一条用户消息、且当前没在输出」才给编辑/重发入口。附件和代码引用会被原样拆出来再拼回去，不丢内容。
2. **先找到这条消息属于哪一轮对话**：按「消息自身带的信息 → 紧跟其后的助手消息 → 当前会话最后一轮」三级兜底；**绝不往前翻历史消息**，那会拿到上一轮的对话 ID，把删除动作打到错误的地方。
3. **调截断接口**：后端先校验对话存在、归属对不对、状态是不是还在跑；确实在跑会先判断是不是「僵尸状态」，还在跑就直接拒绝。
4. **删的时候加锁**：在一个数据库事务里加一把锁（和新消息写入共用同一把锁），删掉最后一条用户消息及其后的所有回复。
   - 为什么加锁：截断还没删完、新消息又插进来，顺序就乱了。
5. **同时清理模型那一侧的会话上下文**。
   - 为什么两边都要删：只删界面上看得见的历史，模型下一轮还带着被删掉的内容，用户看到的历史和模型以为的历史对不上，回答会莫名其妙。
6. 界面把消息截断到目标位置，再把编辑后的内容当一条新消息发出去。

> ⚠️ 口径修正：正在输出时是**直接拒绝**编辑/重发；「停止生成」是另一条独立链路（先调取消接口把会话标成已取消，再停前端的流）。笔记原来写的「先取消 → 再截断 → 再当作新消息发出」不是当前代码的顺序，面试别这么讲。

#### 2）输出期间的消息队列

**为什么以前要禁用输入框**：后端对同一个项目是「一次只能跑一个对话」的串行模型，文件系统、沙箱、版本快照、上下文都按串行假设设计；并发发送会带来文件冲突和版本竞态，改造成本极高。所以输入框被简单粗暴地锁住，用户只能干等（一次生成可能好几分钟）。

**现在不动这个串行模型，只把「排队」加上**：

1. 输出期间输入框保持可输入、可粘贴、可传附件；点发送不再打断当前回答，而是进入队列，按钮上显示排了几条。
2. 队列数据存在后端的一张队列表里，但「什么时候发下一条」仍由前端在状态变成空闲时驱动。
   - 为什么这么分：**存在后端**，刷新页面、切走再回来、换设备都不丢，编辑/删除才有数据依据；**调度留在前端**，不用让后端主动发起对话，现有发送链路一行不动。
3. 支持编辑（把内容回填到底部输入框改完再存回去）、删除（可撤销）、置顶（插到队首、当前回答结束优先发它）。
   - 为什么编辑复用输入框：附件、粘贴、提示词增强这些能力都在输入框里，不用再做一套。
4. 当前回答结束 → 自动取队首发出；这里用**不带防抖**的发送函数，因为普通发送有个 3 秒防抖，会把自动续发吞掉。
5. 点「停止生成」会**暂停**自动续发（队列保留不清空），用户下一次主动发送时恢复。
   - 为什么：用户停下往往是想调整方向，队列却自顾自往下发会很糟。
6. 兜底：前端先乐观更新界面、再异步同步后端；后端队列挂了就降级成纯内存，绝不阻断输入；万一撞上「会话还在跑」的拒绝，这条消息退回队列稍后重试；输出失败时队列保留，给「继续发送」入口。

#### 3）重发时避免误删上一条历史

1. 消息刚发出就报错时，这条消息**可能还没落库**，界面上那条是临时生成的。
2. 此时若照样走截断，后端「删最后一条用户消息」删到的会是上一条正常历史。
3. 判定：**拿得到对话 ID（说明已落库）才截断，拿不到就不截断**（代码里是直接抛错拦住请求），只把界面恢复成可重发状态。

#### 4）历史会话按需迁移（重点讲方案设计）

**问题怎么来的**：多线程模型上线前，老项目的对话直接挂在会话下，没有「线程」这一层；后来为了治理一个 P0（只读接口不该偷偷写库），把读路径上的自动迁移关掉了。结果打开老项目时线程为空 → 查不到对话 → 页面显示空白。数据其实都在，只是没人把它们关联起来。

**为什么不做全量迁移**：受影响的会话约 3500 个，一次性跑批影响面大、要停机窗口，而且大部分老项目不会再被打开；写一次脚本全改，收益远小于风险。

**按需自愈的五步**：

1. 打开项目时，后端保持纯读，只多返回一个「需要迁移」的布尔信号——用一条「有没有没挂线程的对话」的存在性查询精确算出来，不用前端靠页面状态去猜。
2. 前端看到信号才调一次迁移接口；迁移期间把这个会话放进「迁移中」名单，专门压住空态，不让页面先闪一下「我能帮你做什么？」。
3. 迁移成功后，**直接用这次接口返回的完整数据更新界面，不再额外发一次查询**。
   - 为什么：多查一次既浪费，又可能在用户已经切到别的项目时把旧数据刷回来。
4. 幂等靠后端保证：只绑定「没挂线程」的孤儿对话，已经绑好的一律不动，重复调用没有副作用；前端再加一层「同一会话同时只迁一次」的防并发。
5. 失败兜底：迁移报错不阻塞渲染，用户看到原样页面，下次打开自然重试；迁移期间用户切走，回调直接丢弃，不把界面切回去。

**只读协作者也能看历史**：迁移接口的权限从「可写」放宽到「可读」，否则协作者会被挡在空态外；但只读成员只触发「绑定孤儿对话」，**不改所有人共享的「当前选中线程」**，避免一个人看历史把别人的视图改了。

#### 5）多实例下的导入状态

1. 原来的问题：导入完成的通知只在「干活的那一台机器」的内存里广播；用户页面连的是另一台机器，永远收不到，于是卡在「导入中」。
2. 改成：前端定时（约 3 秒）去读**数据库里的导入任务状态**——数据库是所有实例共享的事实源。
3. 通知事件到达时仍然提前刷新一次（快），查库作为兜底（稳）；确认完成后再同步一次文件树，让右侧目录立刻出现导入进来的文件。

### 优化前后（提交记录还原）

**原来怎么做**：
- 模型输出期间输入框整体禁用，只能干等（后端同一项目一次只跑一个对话，前端用「锁输入框」这个最省事的办法回避并发）。
- 编辑重发时截断只处理一边，模型侧上下文没同步；消息被「会话正在跑」拦下、还没落库时照样走截断，会报「编辑重发失败」，严重时误删上一条正常历史。
- 老项目打开是空白：多线程模型上线前的对话没挂到线程上，而治理 P0「只读接口不该偷偷写库」时把读路径的自动迁移关掉了，于是没人补这一层关联。
- 导入完成的通知只在执行任务那台机器的内存里广播；多实例下用户连到别的机器就永远收不到，卡片一直显示「正在导入」，文件树也是空的。

**为什么必须改**：都是用户能直接看见的断点——干等几分钟、历史读不出来、页面永远转圈；影响面也不小（旧会话约 3507 个）。

**怎么改**（提交时间线）：
1. 8/19：导入卡片加 3 秒查库兜底（读共享数据库里的任务状态），并校验会话 ID，防止把别的项目状态写进当前面板；文件树同步试过「有限重试 3 次」、还回退过两次，最后定成「确认完成后主动刷一次即可」，不依赖事件、不需要重试。

## 5. 上传与身份（备用）

### 是什么

用户传一个附件、以及「AI 生成的应用怎么知道当前是谁在用」，这两件事都收成一条统一入口。

### 实现原理（按一次上传拆开）

1. **选文件 / 拖入 / 粘贴**：前端先按**单文件 150MB** 过滤，超限当场提示；把长文本粘成附件也受同一限制。
   - 为什么在前端先拦：别让用户等一个大文件传完才告诉他不行。
2. **发消息时统一走一个上传接口**：文件在浏览器里读成编码文本，连同会话 ID 一起发给后端；不再让浏览器直连存储服务。
   - 为什么收成一个入口：来源校验、身份记录、存到哪里、返回什么地址，都只有一处要维护。
3. **首页还没建立会话时**先用一个占位 ID；会话真正创建后，后端把临时文件迁到真实会话名下并改写引用，迁移失败就保留原引用（宁可留着，也别让附件丢）。
4. **服务端先拦来源，再收数据**：上传请求跳过全局那个较小的请求体解析；路由上先做来源白名单校验（几个固定域名精确匹配 + 若干通配后缀；没有来源头的内网直连放行），通过了才解析请求体。
   - 为什么顺序不能反：不先拦来源，任何不被允许的站点都能先塞一个巨大请求让服务吃满内存，甚至先返回「太大」再返回「不允许」，等于白送一个低成本攻击面。
   - 身份在这里只用来记录「谁传的」，不参与放行判断。
5. **写进对象存储**：按文件内容算一个摘要当名字（同一份内容天然去重）；返回给前端的是平台自己的代理地址，不暴露存储桶；读的时候统一加缓存和跨域头。
6. **上限别讲混**：前端单文件 **150MB**；后端请求体上限 **1GB**（编码后体积膨胀约三分之一，对应二进制文件约 750MB），代码注释里明确写了「这是已知的内存风险，正解是流式上传、尚未做」。另外「快速部署单个 HTML」另有限制（30MB）。
   - ⚠️ 笔记原来写「单文件上限 1GB」不准确。面试说「前端按单文件限制拦，后端单独有一个更大的请求体上限」即可。

### 身份（这里只给一条线，细节在案例 6）

- 统一认证在入口校验登录并注入一个**加密的身份头**；平台侧用密钥解开，通过标准身份接口把账号/工号返回给业务；预览和部署共用这一套，**密钥始终不进沙箱**。
- 预览链路里的网关是透明反代、不剥离任何请求头，所以身份头能一路送到沙箱内的应用。
- 废弃旧的明文 Cookie 方案：那种 token 在沙箱里没法验签，只能明文、可信度低；预览接进统一认证后，两套方案已经没有并存的理由。
- ⚠️ 代码核对：标准身份接口当前稳定返回的是「是否登录 + 账号 + 工号」；「完整员工信息（中文名/部门/头像）」在仓库里是一份状态为「方案待确认」的设计文档，界面上确实展示了用户名和头像。面试说「拿到用户基础信息、界面展示中文名和头像」，别说成「接口一次性返回完整员工档案」。

### 优化前后（提交记录还原）

**上传，原来怎么做**：最早的设计是让 AI 生成的应用**前端直接跨域调**平台上传接口。实测撞了两个硬问题：跨域请求带不上登录 Cookie，后端把用户判成匿名直接 401；改用相对路径又会被部署代理转到用户自己的服务上。当时门禁还叠了几层「网关身份 / 沙箱来源」校验，生产浏览器直连公开网关必然 401；单文件上限 10MB，全局请求体解析也只有 10MB，稍大一点的文件直接 500。

**为什么必须改**：功能根本不可用（401 / 500），大文件传不了；来源校验放在解析请求体之后，任何站点都能先塞一个巨大请求让服务吃满内存，是现成的 DoS 口子。

**怎么改**（8 月这一串提交几乎一天一改，很适合讲「按反馈收敛」）：
1. 8/3 建立统一上传接口；
2. 8/4 上限 10MB → 1G；
3. 8/5 首页还没会话时先用占位目录存附件，会话建好再搬过去（带重试、按内容摘要保证幂等，搬失败就保留原地址，用户无感）；
4. 8/6 改成**服务端转发**：AI 生成带后端的应用，前端走同源相对路径，由应用后端转发到平台，平台按内网来源放行；
5. 8/13 门禁简化成「来源域名白名单」，去掉那几层必然 401 的鉴权；
6. 8/14 上传请求改用单独的 1GB 请求体上限（绕开全局 10MB），并把来源校验提到解析请求体**之前**。

**身份，原来怎么做**：预览域名当时不在认证网关后面、Cookie 也不跨域，用户项目拿不到登录人。平台的办法是在预览链接里拼一个**明文**身份串（沙箱里拿不到平台密钥，没法验签），再写进 Cookie；部署侧则把一把全局解密密钥注入用户容器，让用户代码自己解身份头。预览一套、部署一套，代码要写分支。

**为什么必须改**：明文串可信度低，全局密钥一旦泄露能伪造成任意员工，换密钥还要全平台同步；后来预览域名接进网关，两条链路都能拿到同一种加密身份头，两套方案就没有存在理由了。

**怎么改**：9/9 先做 Cookie 方案；9/14 试过新增一个统一身份接口，当天又收敛成「复用平台已有的 `/auth/me`」、删掉新接口；同一天删掉预览 URL 里的明文串、Cookie 注入和部署侧密钥注入。中间还试过两个临时接口，都回退了，最终选的是「不新增接口」。

**效果怎么样**：
- 上传：10MB → 1G（后端请求体），跨域 401 和大文件 500 消失；不被允许的来源不会再先占内存；附件搬迁失败对用户无感。
- 身份：预览和部署同一套写法、密钥不出平台、**存量沙箱和已上线的实例都不用重建**；身份 Skill 从 340 行精简到 97 行。
- 边界：1GB 是请求体上限（编码后约合 750MB 二进制），代码注释里明确写了内存风险、正确的流式上传方案尚未做；前端单文件限制仍是 150MB。

### 面试怎么讲

一句话版本：「把散在各处的上传收成一个入口，来源校验前置；身份统一到公司方案，密钥不进沙箱。」

## 6. Skills（备用）

### 是什么

Skills 是给模型看的「操作手册包」：一个目录里放一份说明文件，需要时再带脚本、参考文档、模板。

### 实现原理（逐步）

1. **原来的断点**：请求只把技能**名字**塞进提示词，沙箱里并没有对应文件——模型能说出「我有这个技能」，真要读手册却找不到；另外用户在界面勾选的技能，前端明明传了，后端却从一个从来没被写过的默认配置里读，等于链路是断的。
2. **先修链路**：以请求里用户实际选中的为准；每次会话开始前，把内置技能的文件写进沙箱的指定目录，市场里装的外部技能下载进去；内置技能写不进去就直接让这次请求失败，不再「有名字没文件」。
3. **改用 SDK 原生的渐进式加载（三级）**：
   - 一级：启动时只扫每份说明的头部（名字 + 什么时候该用），放进系统提示词；
   - 二级：模型判断要用某个技能了，才去读完整正文；
   - 三级：正文里引用到脚本、参考文档时，才去读那些文件。
   - 为什么：不用把所有手册一次性塞进上下文，省空间也少干扰；所以手工往提示词里拼「可用技能清单」那段代码就删掉了。
4. **同步本身也有成本**：往远端沙箱写文件是一次次网络调用，曾经 8 个内置技能约 137 次、耗时一分多钟。加了指纹：文件全写完后算一个短摘要留在沙箱里，复用沙箱时一次命令批量比对，没变就跳过，只重写变化的那几个；批量检查失败就降级成全量写，新沙箱强制全量；技能之间、文件之间并发写。
   - 为什么摘要要最后写：写一半就留下「已同步」的标记，下次会被误判成完整。
5. **市场与详情页**：内置技能不写安装表（查询时动态补出来，也不允许卸载），外部技能装了才记一行；原来两套并行的安装存储合并成一个服务；列表和详情页能标出「内置 / 已安装」。
### 优化前后（提交记录还原）

**原来怎么做**：请求里只把技能**名字**拼进提示词，沙箱里并没有对应文件，模型「知道有这个技能」却读不到内容；用户勾选的技能前端传了，后端却从一个从来没写过的默认配置里读。同步技能进沙箱也是一次次远程写文件，8 个内置技能约 137 次、耗时一分多钟；安装状态还分两套存储（内置一套、市场一套）。

**为什么必须改**：功能名义上有、实际用不了；每次会话都为一堆没变化的技能付同步成本；两套存储容易对不上。

**怎么改**：
1. 更早（1 月）先用打包方式减少技能同步的远程调用，属于「减少路费」的同一类优化。
2. 8/17：会话前把内置技能真正写进沙箱并支持校验；随后修「复用沙箱时用户新选的技能没同步」——让选中的技能始终参与指纹校验和增量写入。
3. 8/19：把「可用名单」和「沙箱里实际有没有文件」统一成一个事实源；再改用 SDK 原生的三级渐进式加载，删掉手写技能清单的提示词；安装存储也合并成一个服务。

**效果怎么样**：
- 文档给的**期望值**（不是线上实测）：技能内容未变且带校验参数时同步约 1 秒，冷启动或技能变更约 5-10 秒（原来一分多钟、137 次远程写）；复用沙箱不再逐文件覆盖。
- 能讲的现象：不再「有名字没文件」、选中即生效、内置技能不允许误卸载。
- 没做的：线上整体同步耗时对比、技能命中率统计。

6. 一句话版本：不强，备用。

## 7. 统一登录态接入（案例 6）

### 背景（这是钩子的来源）

平台原来获取登录态靠调用一个**第三方安全接口**。这个接口因为安全问题要被下线，我们提供的登录能力会直接失效。讨论后决定：**把预览和部署的域名整体迁到公司统一认证上**，顺便把身份获取方式统一。

### 先看一条请求是怎么走的（代码核对版）

1. 浏览器访问部署域名或预览域名 → 统一认证先拦下来校验登录，没登录就自动拉起登录页；登录后往这次请求里加一段**加密的身份信息**。
   - 为什么放在网关：只要「需要登录」、不读用户信息时，业务服务一行代码都不用改；也避免每个项目各写一套登录。
2. 网关按配置把请求**回源到 443（HTTPS）** → 集群外的负载均衡 → 集群内按域名分流 → 预览网关 → 沙箱入口 → 用户自己的服务。
   - 为什么强调「不剥离请求头」：身份信息就藏在这个头里，中间任何一层把它丢掉，后面就只能把用户当游客。预览网关只改目标地址和协议标记，其余原样透传。
3. 用户项目的前端**不直接解读这个加密头**，而是请求自己项目后端的一个普通接口（例如 `/api/me`）。技能里也允许前端直接调平台的标准身份接口（浏览器请求同样会经过网关注入），但推荐写法统一走自己后端——这样预览和部署的写法完全一样。
4. 项目后端把这次请求收到的请求头和 Cookie **原样转发**给平台的标准身份接口，只剔除逐跳传输用的头，其余一个不改。
   - 为什么必须原样：平台要拿身份头、时间戳、签名一起校验，少一个或改写过就验不过。
   - 为什么不让前端直接把用户名传上来：客户端提交的字段可以随便改，鉴权、数据归属、审计一律以平台解出来的结果为准。
5. 平台用**自己的密钥**解密并验签（同时看有没有过期），返回账号和工号；项目后端再决定展示什么、允许做什么。
   - 为什么密钥不进沙箱：这是一把全局、长期、能解开任意员工身份的钥匙，泄露等于能伪造成任何人；换钥匙还要全平台同步，没法像部署令牌那样随时作废。放在平台侧还有个额外好处——**存量沙箱、已经上线的容器都不用重建**就能生效。
6. 纯静态、没有后端的项目：保留一个可选的直连接口，只给中文名、部门等展示信息，**不给工号、不能用于鉴权**。
   - 为什么留这个口子：没有后端就没法转发；展示够用，但可信度不同，必须划清。

**这次迁移真正改了什么**：以前是「预览靠一个明文 Cookie、部署靠网关头」两套分叉；预览接进统一认证之后，两条链路拿到的是同一种加密身份头，于是收敛成一套写法——项目代码不用区分预览还是部署，也完全不接触密钥。

### 做了四件事

**① 部署域名的泛域名接入统一认证**

- 只需要登录、不读用户信息时，统一认证会在访问时自动拉起登录，业务服务不用改代码。
- **副作用**：切过去之后，某个业务平台（报告平台）的对外接口登录态失效。
- 处理：当天上午**先回滚**——**回滚的是刚配好的泛域名接入配置**（把接入删掉），下午确定方案再恢复接入，形成 P0 / P1 / P2 三级：
  - P0：对该业务域名单独接入 + 约定路径白名单豁免登录，**用户侧零改造**；
  - P1：重新调整 OA Skill 适配新鉴权（统一认证自带的 skill 不能直接搬，要改造）；
  - P2：等新 OA Skill 出来后业务按需改造，或维持 P0。
- 踩到的限制：泛域名**不支持**整体配置免登录路径，只能「先接子域名再接泛域名，在子域名上配免登录」；内部早期文档写「不支持泛域名接入」，实际已支持。

**② 打通前后端统一身份获取**

- 旧方案走那个被下线的第三方接口，拿不到身份。
- 升级后的方式：前后端携带凭证请求平台统一身份接口，拿到用户基础信息（账号、工号等）；界面上展示的中文名、部门、头像属于展示信息，完整员工档案的补充是后续方案（见 §5 与「关键事实」口径提醒）。
- 冲突点：**预览域名是动态分配的**，原来那套「路径白名单豁免」在预览环境不适用，必须业务改造 + 预览域名也接入统一认证。
- 后端对接时要绕开证书校验，且返回字段名有变更。

**③ 对外服务的免登录路径**

- 用户部署的项目要对外开放接口时，直接请求会被统一认证拦截返回 302。
- 平台下项目是动态的，逐个域名加白不可行。
- 落地：**约定固定免登录前缀**（形如 `/api/no-auth/xxx`），业务把要开放的接口挂到这个前缀下，平台侧统一加白。两个站点已生效。

**④ 预览环境的接入（最难的一次定位）**

- 现象：预览环境不在认证网关后面，前端调标准身份接口会打到**自己**的服务上返回 404，被识别成「游客」只读。
- 初查：预览域名和测试部署域名解析到同一个负载均衡 IP，一度怀疑是转发规则把流量送错了地方。
- **根因（我定位的）**：接入时**回源端口配错**——负载均衡上预览的转发监听器只配了 443，实际流量走 80 打到了后台服务。改成强制 HTTPS、按 443 回源后解决。
- 方案收敛：不再区分预览和部署两套鉴权——前端沿用标准身份接口，后台服务解密请求头里的身份信息。
- 稳妥处理：开发测试阶段**不整体接入预览泛域名**，先单域名接入，避免影响正式环境。

### 关键事实（代码与设计文档核对）

- **接口**：平台统一提供 `GET /api/auth/me`（Skill 里写明：前端自动带 headers/cookies，后端请求时**只剔除 hop-by-hop headers，其余原样转发**）。平台侧用令牌解密请求头里的身份信息后返回。**密钥始终在平台侧，不进沙箱**。
- **前后端都可直调**（SKILL.md 已明确）：前端请求自动携带 headers/cookies；后端请求时**只剔除 hop-by-hop headers，其余原样转发**。身份判断必须以接口返回为准，不得信任客户端提交的用户名。
- （旧的分岔方案属于未上线的尝试，面试不提。）
- **预览链路**：认证网关 → 回源 443 → 负载均衡 → 预览网关（**透明反代，不剥离任何请求头**，所以加密身份头能原样进沙箱）→ 沙箱入口 → 沙箱内服务。
- **80/443 那个坑的准确机理**：回源配成 `http:80` 时，流量落到集群里真实存在的部署网关服务（它只认三个部署域名），看到预览域名就返回「请用部署域名访问」的错误 JSON；改成回源 `https:443` 后，流量才走到预览网关进沙箱。
- **两个域名解析到同一个入口 IP**，靠域名区分走哪条链路——这是配错端口会互相串的根源。
- 纯静态、没有后端的项目保留一个可选直连接口（只返回中文名、部门等展示信息，不给工号）。
- ⚠️ **免登录前缀属于平台网关侧的配置约定**，两个仓库里没有对应代码实现。面试按经历讲「约定固定前缀 + 平台统一加白、业务把开放接口挂上去」，不要说成「我在代码里实现了免登录前缀」。
- ⚠️ 「只剔除逐跳头、其余原样转发」是身份 Skill 写给**业务项目**的用法；平台侧的解密验签是另一层（统一认证 + 身份解析）。别把两件事说成一件事。
- ⚠️ 「标准身份接口返回完整员工信息」的口径见 §5：当前稳定返回账号/工号，中文名/部门/头像的完整档案是设计文档里的方案。

### 优化前后（提交记录还原）

**原来怎么拿到登录态**：平台靠一个第三方安全接口取身份；预览域名因为不在认证网关后面，只能由平台在预览链接里拼一个明文身份串再写进 Cookie；部署域名则靠网关注入的加密身份头、用户代码自己解密。同一个功能，预览和部署是两套写法。

**为什么必须迁**：那个第三方接口因为安全问题要下线，登录能力会整体失效；顺带也该解决明文串可信度低、全局密钥扩散、两套写法维护成本高的问题。

**怎么改**（9 月这一串提交能看出方案是怎么收敛的）：
1. 先按「预览不在网关后」的前提做了 Cookie 方案，并给部署侧注入解密密钥；
2. 试过给部署域加一个同源身份接口、又试过给纯前端项目加一个展示信息接口，两个都当天回退了；
3. 随着预览域名接进网关、回源端口修正，两条链路都能拿到同一种加密身份头，于是收敛成：用户项目前端调自己后端 → 后端原样转发请求头 → 平台用已有的 `/auth/me` 解密；新增的接口、Cookie 方案、部署侧密钥注入全部删掉；
4. 过程中出了对外接口登录态失效的连带问题，先回滚止血、再拆 P0/P1/P2（见「做了四件事」）。

**效果怎么样**：
- 能讲：预览和部署同一套写法、代码不接触密钥、**存量沙箱和已上线实例都不用重建**；身份 Skill 精简到 97 行；约定免登录前缀后两个站点的对外接口恢复可用。
- 没有量化：没有迁移前后登录成功率、耗时数字。
- 别夸大（呼应下面「不能夸大」）：预览泛域名整体接入没做、AI 调用场景的内网授权没做、免登录前缀是平台侧配置约定，不是我写的代码。

**60 秒标准版：**

>
> 我负责的是对接和落地这一段。迁的过程中产生了连带问题：某个业务平台的对外接口登录态失效了，我们先回滚止血，再拆成三级方案——先给这个业务单独接入并加路径白名单，保证用户侧零改造；再改造内部的身份 Skill 适配新鉴权。

> 最难的是预览环境。它不在认证网关后面，前端调标准身份接口会打到自己的服务上返回 404，被当成游客。一开始怀疑是转发规则送错了流量，我最后定位到是**接入时回源端口配错**：负载均衡上只配了 443，流量实际走 80 打到了后台服务。改成强制 HTTPS 回源之后解决。现在预览和部署共用一套鉴权。

**追问 1：为什么先回滚再恢复？**
> 对外接口是别的业务在用，影响面不可控。先回滚止血，再拆成 P0/P1/P2，让「保证现有业务可用」和「长期方案」分开推进。

**追问 2：泛域名免登录怎么解决？**

**追问 3：如果重做？**
> 两件事：一是迁移前先把「预览域名是动态分配的」这个约束列出来，白名单方案就不会白做一次；二是接入前先确认回源端口和协议，80/443 这个坑其实配的时候就能发现。

### 概念备注：负载均衡 vs Ingress（别说串）

- **负载均衡（CLB）**：云资源，在集群**外**，把外部流量送到集群节点的某个端口（或 Ingress 入口）。四层（TCP）+ 七层（HTTP/HTTPS）都能做。
- **Ingress**：K8s 概念，在集群**内**，按域名 / 路径把 HTTP 流量路由到具体服务；需要 Ingress Controller 实现，且前面通常要有负载均衡把流量送进来。
- 两者是**串联的两层**：负载均衡送流量进门，集群内网关按域名路由。看起来像（都在转发请求），但位置和职责不同。
- 本项目的三条入口：**测试部署域名**与**预览域名**共用一个负载均衡（转发规则分监听器配：预览的规则只在 443 监听器下，测试部署的规则在 80 回源能命中的监听器下）；**正式部署域名**走集群 Ingress 入口（host 规则 → 后台服务）；预览还有一层自带的预览网关（透明反代）再进沙箱入口。
- 面试口径：**「负载均衡在集群外送流量进门，集群内网关按域名路由——两层，串联。」** 沙箱方案里那个名字带 ingress 的组件，统一说「沙箱方案的入口网关」，不要展开标准 Ingress 资源细节。

### 概念备注：K8s 是什么（被问到时怎么答）

- K8s（Kubernetes）是**容器编排系统**：管的是「容器在哪台机器上跑、跑几个、挂了怎么办、怎么被访问到」。没有它，这些都要手工做。
- 结合本项目记住几个概念就够：
  - **Pod**：最小单位，装一个或多个容器。用户部署出来的项目、沙箱，各自都是一个 Pod。**Pod 是「正在跑的那个实例」，挂了就没了**。
  - **Deployment / StatefulSet**：不是实例，是**「说明书 + 管理者」**——声明「我要跑几个什么样的 Pod」，并保证实际跑着的符合声明（少了补、挂了重建）。
    - **Deployment**：无状态，Pod 之间完全等价，随便换一个都一样 → 用户部署出来的应用用这个。
    - **StatefulSet**：有状态，每个 Pod 有固定序号、稳定名字和自己的存储卷，按顺序启停 → **沙箱用这个**（StatefulSetPlus），因为每个沙箱是某个用户的开发环境，有自己的文件、端口和身份，不能被替换成一个全新的空实例。
    - 一句话区分：**Pod 是干活的，Deployment / StatefulSet 是保证「一直有合适数量的 Pod 在干活」的。**
  - **Service**：给一组 Pod 一个稳定的访问入口。**NodePort** 是把服务暴露到节点的某个端口（预览网关的 30881 就是）。
  - **Ingress**：按域名 / 路径把 HTTP 路由到 Service（正式部署域名走这个）。
- **我在项目里实际用到的**：构建镜像 → 推到镜像仓库 → 在集群里起实例 → 等它就绪 → 通过域名访问；以及预览这条链里，沙箱也在集群内，由预览网关转发进去。
- **口径**：「我用 K8s 部署过应用，知道 Pod / Service / Ingress 的基本概念和一条完整的部署链路；集群运维不是我的范围。」**不要说精通、不要说搭过集群、不要说写过 Operator**。被追问就诚实界定边界——你的定位是 AI 应用工程，不是基础设施。

## 8. 监控（加分，不单独练）

### 伽利略：给关键链路上结构化上报

覆盖部署、Git 提交与推送、首页核心接口，按 P0 / P1 分级。

1. **以前的问题**：部署的几个阶段各打各的日志，前缀和字段不统一；用户报「部署失败」时要分别按几条链路去搜，还得猜卡在哪一环。
2. **现在统一成一个上报口径**：每条事件都带同一组字段——谁、哪个项目、哪次对话、哪次部署、走的是哪条部署路线、域名、当前阶段、状态、耗时、错误码。日志统一前缀。
3. **按阶段成对上报**：请求进来 → 读工作区文件 → 分流 → 自动域名解析 → 装依赖 → 生产构建 → 上传产物 / 构建镜像 → 起实例 → 等就绪 → 截图 → 完成，每一步都有「开始」和「结果」。
4. **最值得讲的一个取舍**：中间某一步失败只记**告警**，只有整次部署最终失败才记**终态失败**。
   - 为什么：AI 会边修边试（缺打包说明就补一份再试一次），把每次尝试都算成失败，告警会全是噪音，也看不出到底影响了谁。
5. 截图失败、缓存上传失败这类不影响发布的，单独用告警事件，不混进主流程的失败统计。

### Langfuse：AI 调用链的观测

**先分清楚两个项目**：QPilot 这边是**修质量**（原本就有接入，修两个毛病）；QQ OKR 那边是**从 0 建**（见 qq-okr 材料）。不要混。

**一次请求怎么被记下来**：

1. 应用启动时初始化观测组件；**没配密钥就自动不启用**——本地开发可以不开，某个环境不开也不影响主流程，绝不让观测把业务拖挂。
2. 一次聊天请求进来建一条根记录，带上会话、用户、模型、提示词、标签和请求摘要；在列表页就能看出这次请求大概是什么。
3. 只给少数关键阶段记耗时（准备沙箱、下发运行脚本等），**不给每个函数埋点**。
4. 模型 SDK 的内部事件走一条**只给观测用**的旁路：每一轮模型调用、每次工具调用的输入输出和用量，被整理成结构化记录；这些内部事件不转发给前端，也不写进消息表。
   - 为什么低侵入：不用为了观测改前端协议，也不用改业务存储结构，只是多了一条内部支路。
5. 请求结束时标成成功 / 失败 / 取消，补上总耗时、总轮数、token 用量，或错误信息与日志摘要。

**修的两个质量问题（这才是本案例的落点）**：

1. **环境标识没传给导出器** → 所有记录都落到 default，测试和正式混在一起筛不出来。修法：初始化时把环境同时写进资源属性和导出器。
2. **同一批调用被记两份**：手动埋点记了一份，模型 SDK 原生上报又记了一份。修法：**在导出阶段**按记录名称把手动那份（每轮模型调用、每次工具调用）丢掉，只留原生那份。
   - 为什么在导出层做：一处开关、业务埋点代码一行不动、想回退只要去掉这条过滤规则，改动面和风险都最小。

### 优化前后（提交记录还原）

**原来怎么做**：
- 部署链路各阶段各打各的日志，前缀和字段不统一，排障要分几条链路搜；代理链路连「缓存正常过期后重建」这种日常事件也打 info 日志，默认级别下持续刷屏。
- 首页几个核心接口没有统一的调用结果和耗时上报。
- 观测平台这边有两个质量问题：导出器没配环境标识，平台自建的记录一律落到 default，测试和正式混在一起；手动埋点和模型 SDK 原生上报又会把同一批模型/工具调用记两份。

**为什么必须改**：不是「没有监控」，而是「有了但不可信、不可查」——按环境筛不出来、同一份调用翻倍、日志噪音把真正的问题淹没。

**怎么改**：
1. 部署链路抽出一个统一上报服务，所有事件带同一组字段（用户/项目/会话/部署 ID/阶段/状态/耗时/错误码），并把「中间某步失败」降为告警、只把整次部署的终态失败算失败；
2. 8 月两阶段做日志降噪：域名解析成功、缓存过期重建这类正常事件降为 debug，只保留首次创建、目标变化和所有告警错误；首页核心接口补齐调用结果与耗时上报；
3. 10 月修观测质量：给两处导出器显式传环境标识；在导出阶段按名称把手动埋点那份重复记录丢掉，业务埋点代码一行不动。

**效果怎么样**：
- 能讲现象：可以按统一字段和统一前缀检索、能按环境筛选、正常流量不再产生 info 噪音（告警和错误仍保留）、同一批调用不再记两份；改动集中在导出层，去掉过滤规则就能回退。
- 没有量化：没有告警量下降百分比、排查耗时对比这类数字，别编。

**讲法：** 两个项目都碰过 AI 调用链上报——一边是从 0 建，一边是修质量。说清楚哪边是建、哪边是修，不要混。

## 9. 技术栈地图（概念理清用，面试不主动讲）

> 目的：把接触过的这些组件放到同一张图里，知道各自在哪一层、解决什么问题。面试不主动展开，但心里有底讲的时候不会慌。

### 9.1 一条请求的完整链路

```
① DNS          域名 → IP（决定流量去哪个门）
      ↓
② 认证网关      校验登录，注入身份头（横切能力）
      ↓
③ 引流层        把外部流量送进集群
   ├─ CLB       云的负载均衡，四层 + 七层都行
   ├─ IAS       内部的类 Nginx 网关，七层，带服务发现
   └─ NodePort  直接开在节点上的端口
      ↓
④ 集群内路由    按域名 / 路径找到服务
   ├─ Ingress   K8s 机制，host/path → Service
   └─ Service   集群内稳定入口，后面挂一组 Pod
      ↓
⑤ 运行层
   ├─ K8s       编排系统（调度、重启、扩缩容）
   ├─ TKE       腾讯云的 K8s 服务（公有云）
   ├─ TKEX      公司内部的 K8s 平台（原 STKE，按 BG 分：CSIG/TEG/PCG/WXG/IEG）
   └─ Pod       实际跑的容器；由 Deployment（无状态）/ StatefulSet（有状态）管着
```

### 9.2 按「解决什么问题」分类

| 类别 | 组件 | 解决什么 |
|---|---|---|
| 寻址 | DNS | 域名换 IP |
| 安全 | 认证网关 | 登录校验、身份注入 |
| 引流（进门） | CLB、IAS、NodePort | 把外部流量送进集群 |
| 路由（进门后） | Ingress、Service | 按域名找到服务 |
| 服务发现 | 北极星、K8s Service/DNS | 后端 IP 老变，怎么找到它 |
| 运行 | K8s、TKE、TKEX | 容器在哪跑、挂了怎么办 |
| 实例 | Pod、Deployment、StatefulSet | 真正干活的 |

### 9.3 三个最容易混的点

1. **CLB 和 IAS 是同类，不是上下游**：都在做引流 + 域名转发。CLB 是云产品（能做四层），IAS 是内部平台（类 Nginx，只七层，配北极星做服务发现）。不同团队/时期选了不同的，所以会同时存在。
2. **IAS 和 Ingress 也是同类，但层级不同**：Ingress 是 K8s 内部的机制（规则在集群里、跟应用走）；IAS 是独立网关平台（规则在平台上配，通过北极星寻址，可跨集群）。
3. **TKEX 和 TKE 是同一类东西的两个供应商**：都是 K8s 容器平台，TKEX 是内部的、TKE 是腾讯云的。前端从 TKEX 迁到 TKE，本质是**换了个跑容器的地方**，架构没变。

### 9.4 一句话记住每个

- **CLB**：云的门，四层七层都能转
- **IAS**：内部的类 Nginx 门，带服务发现
- **Ingress**：门里面的路由表（K8s 原生）
- **北极星**：通讯录，服务名 → 实际地址
- **Service**：集群内稳定入口，挡住 Pod IP 的变化
- **K8s**：编排系统本身
- **TKE / TKEX**：跑 K8s 的地方（云上 / 内部）
- **Pod**：真干活的容器；**Deployment / StatefulSet** 是保证它一直有的管理者
- **有状态 vs 无状态**：删掉重建会不会丢东西——会丢就是有状态（数据库、沙箱），不丢就是无状态（前后端服务大多都是）
