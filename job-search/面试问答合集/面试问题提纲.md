## 一、AI / Agent 专项（最重要，先准备这块）

### 1.0 Agent Harness（统领概念，先理解这个）

**是什么**：包在模型外面、把它从「会聊天」变成「能干活」的那层软件。行业里常用的类比（2026）：

> **模型 = CPU，上下文窗口 = 内存，Agent Harness = 操作系统**——它负责编排上下文、跑控制循环、提供标准驱动（工具）、施加权限与沙箱、并在出错时恢复。

具体包含六块：**控制循环 / 工具执行 / 上下文管理 / 权限与沙箱 / 状态与恢复 / 可观测**。

**补充 C：结构化输出的标准答法（别只靠案例迁移）**

> 四层保障：
> 1. 用模型原生的**结构化输出模式**（JSON mode / 工具 schema）固定格式
> 2. 用 **schema 描述字段**（类型、必填、枚举）
> 3. 拿到输出后**用校验库校验**（如 zod），并把「是格式错还是字段错」区分开
> 4. 校验失败**带上错误信息重试一次**；仍失败就降级（退回纯文本，不渲染结构化视图）
>
> 我能挂的实战：**失败要能解释原因**——这和预览里「把判断原因一起回传」是同一个思路（案例 3）。

| 问题 | 考察点 | 来源 |

| 你怎么设计一个 prompt？包含哪些部分？ | 系统性 | 待补 |

**框架性答案（必须背下来，AI 线第一题就问这个）**

> 一个 prompt 我会分成六块写：
>
> 1. **角色**：它是谁、在什么场景工作
> 2. **上下文**：它要知道的背景（项目结构、已有约定、约束）
> 3. **任务**：这次具体做什么，**做到什么程度算完成**
> 4. **格式**：输出长什么样（schema / 模板）
> 5. **示例**：一两个正例，必要时给反例
> 6. **兜底**：做不了怎么办、不知道怎么办、**不能做什么**
>
> **我的实战（这块你能讲，不是空话）**：平台的系统提示词就是按这个思路写的——先约束「不要把业务数据写到容器本地」，再要求它**收尾时自检并把结果写进标记**（案例 4 的存储预检，标记由模型写入）；另外把 Skills 从「手工塞进提示词」改成 SDK 原生的**渐进式加载**，避免上下文被静态列表占满。

**补充：prompt / RAG / 微调 三分叉（AI 线经典题，背下来）**

| 手段 | 什么时候用 | 代价 |
|---|---|---|
| **Prompt** | 业务规则多变、要快速迭代 | 最便宜，但受上下文长度限制 |
| **RAG** | 知识量大、需要更新、要引用来源 | 要建检索链路，有召回质量问题 |
| **微调** | **风格 / 格式要固化，且样本量大**；或者要压缩 prompt、降延迟成本 | 最贵最慢，知识更新困难 |

> 选择顺序：**先 prompt → 不够再 RAG → 最后才微调**。原因讲两点：微调迭代慢、知识更新要重训，不适合业务多变的场景。
>
> 我的情况（诚实说）：平台用的是 **prompt + 工具（MCP）+ 沙箱执行**，没做 RAG 也没做微调。如果被问「要加外部知识你会怎么做」——答「先上 RAG，不会直接考虑微调，因为知识更新频率高」。

**工具设计的要点（你有 MCP 实战，别只答流程）**

> - **描述（description）最关键**：要写清「什么时候该用、什么时候不该用」——这是模型判断用不用这个工具的唯一依据，写含糊会导致误调用或不用。
> - **粒度**：一个工具做一件完整的事。太大 → 参数复杂易填错；太小 → 调用次数爆炸、上下文被工具结果撑满。
> - **参数**：**能由后端决定的就不要交给模型填**（减少出错面，也减少注入面）；必填 / 可选 / 枚举 / 边界都要声明清楚。
> - **返回**：只回必要字段，大结果落盘给引用（呼应上下文管理）。
> - **失败**：错误信息要能让模型看懂并自我纠正，而不是只返回一句「失败」。
>
> 我能挂的实战：**「能由后端决定的不交给模型」**这条和部署 MCP 是同一个思路——令牌绑定本次操作，模型只能调它，不能自己发请求（案例 4）。

**框架答案（1.2 最后一问「怎么验证没退化」和这里是同一题，一份答案两处用）**

> 三步闭环：
>
> 1. **构造正例集（golden cases）**：覆盖典型场景 + 边界场景，每条写清期望——**必须包含什么、不能包含什么、格式要求**。两个要点：case 要能代表真实分布（不能只挑好做的），另外要有专门的 bad case 盯历史上踩过的坑。
> 2. **每次改动跑全量**：改 prompt、换模型、改工具后都跑一遍，对比输出：
>    - **格式合规** → 脚本校验（schema / 必填字段）
>    - **语义达标** → 打分，或让模型按 rubric 判分
> 3. **退化归因**：先分清是**格式退化**还是**语义退化**，再往下定位到 prompt / 上下文 / 工具 / 模型哪一层。
>
> **我能挂的实战**：在个人 Demo 里做过一套（10 条 golden cases，覆盖必须提到的类别和不能提到的内容）。
>
> ⚠️ **边界**：**业务上没有建正式的回归集**——这条要如实说。但你可以补一句为什么值得做：AI 功能「看起来能跑」和「稳定」之间差的就是这个，没有它，prompt 改完只能靠感觉。

### 4.9 手写题（前端线常考）

Promise.all / Promise.race / 并发限制 / 防抖节流 / 深拷贝 / 数组扁平化去重 / 继承 / EventEmitter / 柯里化

**两个高价值变体（优先练这两个）**

- **带重试的并发池**：限制并发数 + 失败重试 N 次 + 仍然失败要能把错误带出来
- **可取消的 Promise（AbortController）** ← **和案例 3 的 cancel 状态机串起来讲**：面试官问「用户取消怎么处理」时，你能同时答出「前端怎么取消请求」和「Agent 状态怎么收敛」，是现成的加分连接点

**⟦JD⟧ Python 变体（该岗一面现场编码，可能指定 Python）**

- 两道高价值题各备一份 Python 版：**asyncio 并发池（带重试）**、**可取消任务（asyncio.Task / TaskGroup）**

- 定位话术：「主语言 TS/Node，Python 落过 demo，能读能写，生产深度在 Node」——别装老手，一追深就穿帮

## 五、怎么用它

1. **先过 AI 专项**：标了「案例 N」的你能直接讲，是主力；标**待补**的按优先级补。⟦JD⟧ 加权后的补题顺序：**1.8 评测 → 1.9 沙箱故事 → 1.1 补充A 记忆专题 → 1.4 编排框架概念 → 1.12 Python demo → 1.5 流式**。
2. **系统设计**：⟦JD⟧ 岗先练 **1 / 4 / 5 / 6**（工作台、沙箱执行服务、评测平台、记忆系统），练到能讲 8 分钟、说出 2 个 trade-off；2 / 3 次之。
3. **工程生产**基本都有现成答案，口述过一遍即可；**3.3 的 OTel GenAI 三题是点名考点且有生产实战，练到能主动引出**。
4. **技术基础**：投 AI 线只做热手（你的卖点在 AI 工程，不在八股）；**投前端线时第四部分是主场**——4.5 前端实战题基本都能挂你的案例，4.6 的三道设计题至少练熟第一道（可配置中后台，案例 7 直接能讲）。
5. **⟦JD⟧ 面试形式应对**：部分面试**现场跑 Agent Demo**——P1 的脱敏清理提到录视频之前，目标是能现场跑；备 90 秒演示脚本 + 网络不稳时的录屏兜底。
6. **薪资锚点**：JD 25–40K·13~15薪，你的目标 28–32K 落中位，谈判空间正常；两条线时间按 7:3 分。
