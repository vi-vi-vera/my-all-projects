## 1.1 模型能力边界

### 1.1-1 上下文窗口

**口述版**

> 上下文窗口是模型一次能"看到"的 token 上限，输入、历史、工具返回和它自己的输出都算在里面，所以它更像内存，不是只算我打的那句话。超了有两种结果：要么接口直接报错，要么框架自动裁掉早期内容，模型就会"忘"前面的约定。更隐蔽的是没超但很长，中间的信息容易被忽略，还更贵更慢。所以我的做法是不指望窗口够大，而是主动管：只放必要的内容、能力按需加载、编辑重发时把旧上下文清干净。我在平台里做的就是这几件事，一个是 Skills 从手工塞进提示词改成渐进式加载，另一个是截断接口，删消息的同时清掉模型侧的上下文。

**追问备用**

- **窗口大小具体是多少？** 不同模型、不同版本不一样，我不背数字，以官方文档为准。设计上我只假设"它有上限，而且接近上限前质量就会下降"。
- **超了之前怎么知道快超了？** 靠统计每轮的 token 用量，接近阈值就触发处理，比如裁剪、摘要或拆任务。我们做的是调用链上的 token 上报，不是做阈值触发。

**边界句**

诚实说法：我做的是"截断 + 按需加载"，没有做过历史摘要压缩，也没有做阈值自动触发。

**可挂载点**

- 讲到"主动管"时挂 **Skills 渐进式加载**。
- 讲到"清干净"时挂 **会话截断接口（两边都删）**。

### 1.1-2 模型幻觉的产品兜底

**口述版**

> 幻觉没法在模型层根治，我是按产品层兜底来想的，分三层。第一层是让能验证的事交给确定性的东西验证，比如它说"部署好了"，那要以后端的真实状态为准，不以它的话为准。第二层是高风险动作不让它自己执行，收口到受控通道：需要权限的操作走后端签发的令牌和受控工具，它说错了也做不成坏事。第三层是对用户诚实：不确定的内容标出来，失败时给出能看懂的原因，而不是一句"出错了"，让用户知道该不该信、下一步怎么办。核心思路是：模型可以出错，但出错的代价要被系统挡在可控范围内。

**追问备用**

- **用户看到幻觉内容怎么办？** 给反馈入口，把这条记成 bad case，之后进评估集，别只靠修提示词。
- **能不能让模型自己检查自己？** 可以当辅助，但它不是可靠的最后一道防线。能用规则、校验或外部真实数据核对的，就不要靠它自检。

**边界句**

诚实说法：我们没有做专门的幻觉检测或事实核查链路，我做的是**收窄它能碰的范围**这一层，也就是受控通道和失败原因回传（Git 对话链路的真实边界见案例 2，不能讲成「模型做不了坏事」）。

**可挂载点**

- 讲第二层时挂 **Git 面板的预检与权限边界**（面板走后端接口先检查冲突分叉；对话里模型用沙箱原生 git，凭证在仓库配置里，靠提示词约束不主动提交）和 **部署改成受控 MCP 工具**（令牌绑定本次操作，这条已落地）。AI 写入的受控令牌方案设计实现过，但没从界面接进去，要主动说清。
- 讲第三层时挂 **预览启动失败给非开发者一句人话错误摘要**。

### 1.1-3 延迟和成本的权衡、什么场景换小模型

**口述版**

> 我先分清这个任务对什么敏感。用户在等的交互场景，延迟最重要，可以流式输出降低体感等待，也可以缩短提示词、减少无谓的工具调用。批量、后台的场景，成本更重要。至于换小模型，我的判断标准是：任务是不是简单、可验证、错了代价小。分类、抽取、改写、生成提交信息这类适合小模型。主链路里的规划和工具调用不适合省，因为一旦出错，后面要花的代价更大。所以我会按任务拆开选。先说明，我深度用的是 Claude，没做过多模型路由和多家对比，这部分是方法论，不是生产经历。

**追问备用**

- **怎么确定小模型够用？** 先在固定的一批样例上对比输出，看格式合规和语义是否达标，再决定要不要换。没有评估集就换模型，等于凭感觉。
- **还有哪些不换模型也能降成本的手段？** 缓存、缩短上下文、按需加载能力、减少不必要的工具调用，这些往往比换模型更稳。

**边界句**

诚实说法：我没有做过多模型路由或 fallback，也没有做过系统的横向评测。我讲的是选型思路，我自己的工程落地主要在 Claude 上。

**可挂载点**

- 讲到"成本"时挂 **AI 调用链可观测里的 token 与成本口径修正（含 cache token）**，说明我对成本怎么度量是做过的。
- 不要把"换小模型"挂成我的成果。

## 1.2 Prompt 设计

### 1.2-2 怎么让模型输出稳定符合格式

**口述版**

> 我会从生成前、生成后两段来看，具体四层。
>
> 第一层，选对手段。能用结构化输出或工具参数表达的，就不要让模型自由写文本。这两类都是把格式要求提前交给模型，生成时就被约束住，而不是拿到文本再解析。
>
> 第二层，把 schema 写对。字段名、类型、必填、可选值、取值范围写清楚；结构尽量扁平，别嵌套太深。schema 越复杂，模型漏字段、写错类型的概率越高。
>
> 第三层，校验分两级。先查结构：字段在不在、类型对不对；再查业务：跨字段有没有矛盾、引用的东西是否真实存在。两级要分开报错，因为处理方式不一样。
>
> 第四层，不合格怎么办。先重试一次，把具体哪个字段错、错在哪喂回去；还不行就降级——换成不依赖这个格式的路径，比如只展示纯文本、用默认值、或者让人确认。
>
> 还有一条原则：能由后端算出来的字段，不要让模型填。少一个字段就少一个出错点，也少一个被注入的面。
>
> 这一套里，项目真正落地的是前两层加第三层的结构校验：工具参数用 schema 约束，启动清单是模型自由输出的文本，后端解析后逐项校验，不合格就不采用。重试和降级这两层没有完整做。

**追问备用**

- **schema 是什么。** 一份机器能读的字段清单：有哪些字段、什么类型、哪些必填、可选值是什么。它不是示例文本——示例只能给人看，清单能让程序判断对错。
- **为什么结构错和业务错要分开。** 结构错通常是格式问题，重试有用；业务错是内容不对，得告诉它具体哪个字段、和什么冲突，否则它只会换个说法再错一次。
- **重试几次。** 一次。再多是烧成本和延迟，而且如果错误来自理解偏差，重试也不会变好。
- **什么时候不该重试。** 如果错误是模型对任务本身理解错了，重试只是重复同一个错误，这时候该降级或者补上下文。
- **怎么证明有效。** 记录失败率和失败类型，按类型改 schema 或提示词；没有数据就不要说“效果很好”。

**边界句**

> 这四层是通用做法。项目里落地的是“能用 schema 就不用自由文本 + 事后校验 + 不合格不采用”，重试和降级没有完整实现，我也没有失败率数据。

**可挂载点**

- 讲“能用 schema 就不用自由文本”时挂 **工具参数定义**。
- 讲“能由后端定的不交给模型”时挂 **部署改成受控 MCP 工具，令牌绑定本次操作**。

### 1.2-3 拒答和兜底怎么写

**口述版**

> 拒答和兜底我放在 prompt 六块里的最后一块，核心是三句话要写清楚：做不了怎么办，不知道怎么办，不能做什么。比如"信息不足时先问，不要猜"，"超出范围的请求明确说做不了并说明原因"，"不要把业务数据写到容器本地"。有两点我比较在意。一是写成具体可执行的规则，不要写"请谨慎"这种空话。二是不能只靠提示词。真正不能做的事，我会从工具和权限上直接拿掉，提示词只负责告诉它别尝试、碰到了怎么说。因为提示词会被忽略或被注入绕过，权限收口才是底线。

**追问备用**

- **拒答太多影响体验怎么办？** 拒答规则要写清边界，同时给替代方案，比如"做不了 X，但可以做 Y"。上线后看被拒答的样本，判断是不是误拒。
- **怎么验证兜底有效？** 把"该拒答的"和"不该拒答的"都写进测试样例，改完提示词就跑一遍，这和 1.2-4 是同一套做法。

**边界句**

诚实说法：我没有做过专门的拒答率统计或误拒分析，我讲的是写法和原则，实战里用到的是约束规则和权限收口。

**可挂载点**

- 讲具体规则时挂 **系统提示词先约束"不要把业务数据写到容器本地"，并要求收尾自检写标记**（存储预检）。
- 讲"权限收口才是底线"时挂 **Git 面板预检、部署受控工具、身份密钥不出平台**；Git 对话链路的真实边界要主动说清，别讲「凭证不进沙箱」。

### 1.2-4 prompt 改动后怎么验证没退化

**口述版**

> prompt 改完“看起来更好”是靠不住的。我用三步：建样例、跑对比、定退化。
>
> 第一步，建一批固定样例。覆盖典型场景、边界场景、历史上踩过的坑。每条样例要写清三件事：必须出现什么、绝对不能出现什么、格式要求是什么。这三件事合起来才是评判标准，只写“回答要好”等于没写。
>
> 第二步，把标准拆成 rubric。能写成规则的都用脚本判：格式能不能解析、该有的字段在不在、有没有危险操作——这类不要交给模型判，模型判分自己会飘。只有写不成规则的（简洁不简洁、步骤清不清楚）才让模型当裁判，而且要给 1 分、3 分、5 分三档的锚点描述，让它说出理由。裁判本身要先用人工标过的样本校准，一致率不到 80% 就不用。
>
> 第三步，定义什么叫退化。三个信号：必过用例从过变不过，直接拦；总体通过率掉 5% 以上，人工看具体哪条；质量分平均掉 0.5 以上，先确认不是裁判漂移。而且不能只看总分，要按场景分桶——总体没变但某一类全挂了，也是退化。
>
> 跑的时候控变量：同一批样例、同一个模型、同一组参数，每条跑三次——通过/不通过取多数，质量分取中位数，别让采样抖动被当成退化。

**追问备用**

- **rubric 具体是什么。** 四条：格式、必含内容、禁忌，脚本判通过/不通过；质量，模型判 1–5 分并给理由。
- **为什么不让模型判格式。** 格式是确定性的，脚本判既准又便宜；模型判会飘，还会把“看起来对”当成“真的对”。
- **样例从哪来。** 优先真实出过问题的案例，其次人工构造的边界场景，不能只挑好做的。
- **怎么防止修了 A 坏了 B。** 分桶统计 + 逐条看差异，不看汇总数字。
- **没有回归集怎么办。** 先把线上出过的问题沉淀成样例，哪怕只有十条，也比没有强。

**边界句**

诚实说法：业务上我没有建正式的回归集，只在个人 demo 里做过 10 条。没有这套东西，prompt 改完只能靠感觉，这是我清楚的短板，也是我想补的。

**可挂载点**

- 讲到“我做过”时挂 **个人 demo 里的 10 条 golden cases**，只能挂这一个，不要挂成 QPilot 的成果。

## 1.3 Tool calling / MCP

### 1.3-1 tool calling 的完整流程

**口述版**

> 完整流程是一个循环。第一步，应用把工具的名字、描述和参数 schema 连同用户消息一起交给模型。第二步，模型决定要不要用工具，要用就返回一个工具调用，里面是工具名和参数，注意此时模型只是"提出请求"，并没有执行。第三步，应用侧收到后，先校验参数和权限，再真正执行。第四步，把执行结果作为工具结果回给模型。第五步，模型据此继续，可能再调工具，也可能给出最终回答，直到不再请求工具为止。我关注第三步：执行权在应用手里，参数校验、权限、失败信息怎么回给模型都在这里，也是我做 Git 面板预检、AI 受控写入方案和部署 MCP 的出发点。

**追问备用**

- **参数不合法怎么办？** 不要静默吞掉，把清楚的错误信息当作工具结果回给模型，让它能自我纠正。反复失败要有次数上限，然后转为向用户报错。
- **一次返回多个工具调用呢？** 可以并行执行，再把结果一起回传，但要注意写操作之间的先后和冲突，必要时串行。

**边界句**

诚实说法：循环本身主要由 Agent SDK 驱动，我做的是工具这一侧，也就是受控工具、令牌和参数边界，以及围绕它的状态收敛，不是从零手写模型循环。

**可挂载点**

- 讲第三步时挂 **AI 受控写入方案**（后端签发 30 分钟有效、带签名和载荷哈希，模型只能拿令牌调后端；这套 `git-write` 工作流设计实现过，但没从界面接入）。
- 讲"为什么执行权要收口"时挂 **部署从模型手写 curl 改成受控 MCP 工具**。

## 1.5 流式与结构化输出

### 1.5-4 边生成边解析（partial JSON）怎么做

**口述版**

> 先说清楚它是什么：partial JSON 不是一种格式，是“JSON 还没写完”这个中间状态。只要三个条件同时成立就会遇到——模型是流式吐的、内容是 JSON、你又想在写完之前用它。少一个都没有这个问题。
>
> 处理方式有四种，从轻到重。第一种不解析，只显示“生成中”，等完整了再渲染。第二种单字段扫描，不解析整体，只在文本里找某个键后面那对引号中间的内容。第三种修复后解析，补括号、补引号、去尾逗号，再解析。第四种流式词法解析，边收边按 token 发事件。
>
> 我们现在用的是第二种，而且只用在一个地方：文件变更卡片。模型吐工具参数时，后端收到一块就原样转给前端，不解析；前端把块拼成一段文本，用“找键名、找冒号、找开引号、扫到闭合引号”的办法，把文件路径和文件内容抠出来先显示。命令卡片和其他工具不抠，等参数完整再渲染，因为半截命令显示出来没有意义。
>
> 为什么不用“修复后解析”：补出来的值可能是错的，尤其是数字，收到 12 可能是 123 的前缀；转义字符也容易让“找结束引号”找错位置。所以选了最笨但最稳的做法：只抠一个字符串字段，别的都等写完。
>
> 一条原则：中间态只能用来显示，不能落库、不能拿去执行工具。最终一定以完整解析加校验为准。

**一个例子（帮助理解，不用背）**

模型要改一个文件，参数是这样分块吐出来的：

```
第 1 块：{"file_path": "/home/user/workspace/src/App
第 2 块：.tsx", "content": "import React
第 3 块： from 'react'"}
```

第 3 块到之前，这段文本不闭合，`JSON.parse` 一定报错。但可以这样找：

1. 找 `"file_path"`；
2. 找它后面的冒号；
3. 找冒号后面的第一个引号；
4. 从这个引号往后扫，处理 `\"` 转义，遇到下一个引号就停——中间就是路径。

第 1 块时扫到文本末尾还没遇到闭合引号，说明没写完，先不显示；第 2 块到了，路径闭合，就能显示完整的 `App.tsx`。内容区同理，边收边追加。

**四种做法对照**

| 做法 | 怎么干 | 代价 | 适用 |
|---|---|---|---|
| 不解析 | 只显示“生成中”，等完整再渲染 | 用户等得久，但不会错 | 参数小、不急着看 |
| 单字段扫描 | 在原文里找键名，取它那对引号中间的内容 | 只能取字符串字段 | 想实时显示路径、命令、代码片段 |
| 修复后解析 | 补引号补括号去尾逗号，再解析 | 数字、布尔不可信；转义容易出错 | 结构简单、字段少 |
| 流式词法解析 | 边收边按 token 发事件 | 实现最重 | 嵌套深、要实时渲染整棵结构 |

**流式词法解析具体是什么（追问会用到）**

修复后解析每次都要重看整段文本；流式词法解析只处理新来的字符。它内部维护两样东西：

- 一个状态：等键名 / 读键名 / 等冒号 / 读值 / 在字符串里 / 在数字里；
- 一个栈：当前套在第几层对象或数组里。

每进来一个字符，按当前状态走一步。关键规则：**字符串遇到闭合引号、数字遇到分隔符，才算一个值完整**，这时候才发事件；没完整之前只能算“正在输入”。

四个坑：

1. 数字不能提前用，收到 `12` 可能是 `123` 的前缀；
2. 转义要处理，`\"` 不是字符串结束；
3. UTF-8 可能被切断，要按流式解码；
4. 解析可以逐字符，渲染要节流（比如 50 毫秒一次），否则界面会抖。

现成的库分三类：

| 类型 | 常见包 | 适用 |
|---|---|---|
| 要一个尽量完整的对象 | `partial-json`、`best-effort-json-parser`、`jsonrepair` | 每块重扫全文，字段少时最省事 |
| 要边解析边发事件 | `jsonparse`、`@streamparser/json`、`clarinet`、`stream-json` | 按字段逐个渲染，文本长时更划算 |
| 浏览器里直接拉流 | `oboe.js` | 对 HTTP 流做增量解析 |

选型：只要一两个字符串字段，手写扫描就够；要整个对象，用容错解析；要结构化实时渲染（边生成边长表格、长表单），用事件式。

项目里不引库的原因：只需要 `file_path` 和 `content` 两个字符串字段，手写几十行就够；多一个依赖多一层不确定性；而且这些中间态只用于展示，不参与决策，出错的影响面小。

**追问备用**

- **partial JSON 只在文件卡片和命令卡片里才有吗？** 不是。所有工具调用的参数都是流式 JSON，所以这个状态每个工具都有。但“存在”不等于“需要处理”：只有文件变更这种“越早看到越有用”的参数才去解析，命令、查询条件、Task 参数都等完整再渲染。
- **怎么决定处不处理？** 看一个问题：这个参数写完之前显示，有用吗？有用就抠，没用就等。
- **宽松解析会不会拿出错的值？** 会。数字只收到一半、布尔还没收完，都可能读错。所以中间态只用来显示，不做判断，不触发动作。
- **不用 JSON 行不行？** 可以。逐行输出、或用分隔符分块，每块自带完整含义，解析简单很多，代价是表达力弱，嵌套结构不好表达。
- **怎么避免界面抖？** 字段闭合了才更新，没闭合不显示；不要每个字符都刷新一次。

**边界句**

诚实说法：我做过的是“从半截 JSON 里抠单个字段做预览”（文件路径、文件内容），没做过“通用的部分解析 + 半截对象渲染 + 结构校验”。前者够用，后者成本高，这个场景不需要。

**可挂载点**

- 讲“单字段扫描”时挂 **文件变更卡片的实时路径与内容预览**（确实在线上跑）。
- 不要挂成“做过通用 partial JSON 解析”。被问到复杂结构怎么处理，就如实说没做，并说明为什么这个场景不需要。

### 1.5-5 流式在网关/代理层会不会被缓冲，怎么处理

**口述版**

> 会，这是流式很常见的坑，现象是后端明明在流式输出，用户那边却一直没动静，最后一下子全出来。原因是链路上的代理或网关默认可能把响应先缓冲再转发，或者开了压缩，也要等攒够一块才发。处理分几个层面。响应层：设置正确的事件流类型，并且通过响应头告诉代理不要缓冲。代理层：对流式接口关掉响应缓冲，也别在这类接口上开压缩。超时层：放宽读超时，并且定期发心跳，避免长时间没数据被当成空闲连接断掉。排查时，我会先绕过代理直接请求后端，对比是不是只有经过某一层才变慢，这样就能定位是哪一层在缓冲。

**追问备用**

- **怎么确认是哪一层缓冲？** 逐层绕过：直连服务、再过内部代理、再过网关，看流式在哪一层开始失效。
- **心跳有什么用？** 一是防止中间层把长时间没数据的连接当成死连接断掉，二是前端能据此区分"还在生成"和"已经断了"。

**边界句**

诚实说法：我实际踩过的代理层问题是部署代理丢 POST body。流式缓冲这条我讲的是通用处理办法和排查思路，没有拿它当自己的线上故障。（事实卡里没有这件事，如果你踩过，请自行改成真实经历。）

**可挂载点**

- 讲到"排查时逐层绕过"时挂 **部署代理丢 POST body**（FastAPI 422 / Express body=null）这次排查，用来说明"代理层会悄悄改变行为，要逐层确认"。必须说清这是另一类问题，不是流式缓冲。

## 1.6 成本与延迟

### 1.6-3 怎么降低长对话的成本

**口述版**

> 长对话的成本大头，不是回答太长，是每一轮都把系统提示、工具定义和历史重新发一遍。十轮下来，那 8k 的固定内容会被发十次；工具结果更贵，因为它量大，而且会一直留在历史里。
>
> 所以我从三个方向想：减量、省轮次、算准。缓存我不列进来，因为那是 SDK 自己打断点的，开发同学只能保证前缀稳定，不能靠它减少总量。
>
> 减量按收益排三件。第一，改工具返回值：读文件只回前几百行、搜索只回匹配行、命令输出截断。第二，清理已经用过的工具结果，把大块内容换成一句摘要。第三，按任务切会话，别让一个会话无限增长。
>
> 省轮次两件：能并行的工具调用一次发出去；确定性步骤交给代码，别让模型反复试错——错误信息给得越准，模型返工越少。
>
> 算准是指成本要分项统计：普通输入、缓存写入、缓存读取、输出，四类价格都不一样。混在一起会得出错误结论，甚至把优化做成负收益。
>
> 这里有个冲突要主动说：缓存要求前缀不变，清理历史会改变前缀。所以不能每轮清，那样缓存永远不命中，反而更贵。做法是粗粒度——攒到阈值清一次，清完保持稳定；或者干脆切会话，旧的不动、新建一个带摘要的。

**先算一笔账（帮助理解，不用背）**

假设系统提示加工具定义是 8k token，每轮新增对话 1k：

| 轮次 | 这一轮要发的输入 |
|---|---|
| 第 1 轮 | 9k |
| 第 5 轮 | 13k |
| 第 10 轮 | 18k |

十轮累计约 135k，其中 **80k 是那 8k 固定内容重复发了十次**。

如果模型每轮还读文件、跑命令，工具结果也会进历史，下一轮再发一遍——一次读大文件，后面每轮都在为它付钱。

**五个手段和优先级**

| 手段 | 做什么 | 收益 | 改动成本 | 风险 |
|---|---|---|---|---|
| 工具返回值瘦身 | 读文件限行数、搜索只回匹配行、命令输出截断 | 高 | 低 | 模型可能要再读一次 |
| 清理旧工具结果 | 大块内容换成一句摘要 | 高 | 中 | 丢细节，要保留结论和错误 |
| 按任务切会话 | 一个任务一个会话，新任务只带摘要 | 高 | 低 | 用户翻旧账要跨会话 |
| 减少往返轮次 | 并行工具调用；确定性步骤用脚本 | 中 | 中 | 需要工具支持并行 |
| 输出约束 / 小模型 | 不复述代码；分类摘要类任务换小模型 | 中 | 低 | 质量可能下降 |

**缓存和清理为什么会打架**

缓存是按前缀算的：从开头到某个断点，整段一模一样才算命中。

- 在中间删内容，从删的位置往后都失效；
- 但删的位置之前——系统提示、工具定义那一大段——缓存还在。所以不是全废，是消息段失效。

三种做法的账（假设历史 100k，命中价是普通价的一折）：

| 做法 | 每轮等效成本 | 结论 |
|---|---|---|
| 不清理 | 100k × 0.1 = 10k | 稳定 |
| 每轮清理 | 前缀每轮变，全价 = 100k | **比不清理贵十倍** |
| 攒到阈值清一次（清到 40k） | 清理那轮付 40k 全价，之后每轮 4k | 约五轮回本 |

所以规则是：**粗粒度、一次性、清完保持稳定**。另外两个好时机：缓存本来就过期的时候清、任务切换的时候清。

更干净的做法是切会话：旧会话不动，缓存不受影响；新会话只带几行摘要，历史从零开始。

**追问备用**

- **缓存不是 SDK 做的吗？** 是。所以我把“保证前缀稳定”当成一条约束，不当成优化手段：别把时间戳、用户 ID 放提示词开头，变化的内容放最后。真正能控的是减量。
- **清理工具结果会不会让缓存失效？** 会，失效的是消息段，不是系统提示那段。所以不能每轮清；每轮清等于永远不命中。
- **多久清一次？** 不按轮次，按阈值或任务边界。历史到一个水位清一次，或者换任务时清。
- **切会话和压缩怎么选？** 任务切换用切会话；同一个任务太长、又不能切，用压缩。压缩时保留关键约束和结论，只压过程。
- **怎么知道省了多少？** 分项看：每轮输入多少、缓存命中多少、工具结果占多少。只看总 token 会判断错——用了缓存总量没降，但实际花费降了。

**边界句**

诚实说法：项目里做的是工具输出限量、技能按需加载（只放名单、正文按需读）、成本统计里把缓存 token 单列。没做工具结果的自动清理，没做按任务自动切会话，也没做历史摘要压缩。截断是为了会话一致性，不是为了降成本。

**可挂载点**

- 讲“能力按需加载”时挂 **Skills 渐进式加载**。
- 讲“缓存与清理冲突”时，可以挂 **预览里“保留旧画面”和“重启必须换进程”的冲突**：都是两个正确目标互相打架，只能选时机和粒度，不能两个都要满。
- 讲“成本分项统计”时挂 **AI 调用链可观测里修正 cache token 与成本口径**（只做上报这一块）。

## 1.7 RAG（链路我清楚，生产上没做过）

### 1.7-1 RAG 的基本链路

**口述版**

> 先说明一下，RAG 我没有在生产上做过，但链路我是清楚的。分离线和在线两段。离线：把文档解析、清洗，切成块，用嵌入模型转成向量，连同原文和元数据存进向量库，这是建索引。在线：用户提问后，先把问题也转成向量，到库里召回最相关的若干块，必要时再做一次重排；然后把这些块放进提示词里，连同问题一起交给模型，让它基于给定材料回答，并要求它标明引用；最后把答案和来源一起展示。我会特别关注两件事：一是召回质量决定上限，召回不对，模型再强也答不对；二是知识更新时索引怎么增量更新。

**追问备用**

- **什么时候用 RAG，而不是微调？** 知识量大、更新频繁、需要引用来源时用 RAG。微调适合固化风格和格式，知识更新要重训，成本高。选择顺序是先提示词，不够再 RAG，最后才微调。
- **文档更新了怎么办？** 按文档做增量更新，用文档标识和版本号找到旧的块，删除后重新入库，不要整库重建。

**边界句**

主动话术：这块我没有生产落地，没做过 RAG，也没做过微调。我的平台是提示词加工具加沙箱执行。我清楚这条链路，如果要加外部知识，我会先上 RAG，不会先考虑微调。

**可挂载点**

- 不挂成我的经历。如果需要类比，只能说"按需注入相关部分、不全量塞进上下文"和我做过的 **Skills 渐进式加载** 是同一个思路，并明确说这是类比。

### 1.7-2 chunk 怎么切、切多大

**口述版**

> 这块我没有生产经验，我讲的是原则。切块要在"语义完整"和"检索精度"之间取舍：切太大，一块里混了多个主题，召回的噪声多，还浪费上下文；切太小，意思被拆散，召回的片段缺少上下文，答不完整。所以我不会背一个固定数字，而是先看文档类型，按结构切，比如按标题、段落、函数这类自然边界，再设一个大小上限，相邻块留一点重叠，避免关键句被切断。每块还要带上标题路径、来源这些元数据，方便过滤和引用。具体多大，要拿真实问题和一批评测样例去试，比较召回的效果后再定，不是拍脑袋定。

**追问备用**

- **重叠要留多少？** 没有通用答案，目的是避免边界处信息被切断，通常是一小部分。具体比例要靠评测样例去调，我不报固定数字。
- **表格和代码怎么切？** 不适合按字数硬切。表格尽量整表或按行带表头，代码按函数或类这样的结构边界切。

**边界句**

主动话术：切块大小我没有在真实业务里调过，我清楚原则和取舍，但具体数值我会拿评测样例去试，不会随口报一个数字。

**可挂载点**

- 不挂。不要把任何一个具体的 chunk 大小说成经验值。

### 1.7-3 召回不准怎么办、rerank 是什么

**口述版**

> 先说明，我没有在生产上调过召回，我讲的是排查思路。召回不准我会先分清问题出在哪一环：是文档没切好，是问题和文档表述差得远，还是检索方式本身不合适。对应的办法：切块方式调整；对用户问题做改写或扩展；把向量检索和关键词检索混合使用，因为专有名词、编号这类内容关键词更准；加上元数据过滤缩小范围。rerank 是在初步召回之后的一步：先多召回一批候选，比如几十条，再用更精细的模型对"问题和每个候选"重新打分排序，只取前几条给模型。它比向量检索更准但更慢更贵，所以放在召回之后，只处理少量候选。

**追问备用**

- **怎么判断召回好不好？** 准备一批问题和对应的正确文档，看正确文档有没有被召回、排在第几位。这是先把召回和生成分开评估。
- **为什么不全用 rerank 模型？** 它要对每个候选逐一计算，成本和延迟高，不适合对整个库做，所以只用来精排小范围的候选。

**边界句**

主动话术：召回调优和 rerank 我没有生产经验，我了解的是思路和这一层的作用。如果让我做，我会先建一批检索评测样例，把召回和生成分开度量，再决定改哪一环。

**可挂载点**

- 不挂。只能在"先分清出问题的是哪一环再动手"这个排查习惯上，说和我排查预览问题时的习惯一致，并明确是类比。

### 1.7-4 引用来源和答案可信度怎么展示

**口述版**

> 这块我没有做过，我从产品角度说一下想法。引用来源的原则是：让用户能快速核对。每个结论后面带来源标记，点开能看到原文片段和出处，并且能跳到原文位置。可信度我不会直接给一个很准的百分比，因为模型给出的置信度并不可靠，容易误导用户。更好的做法是给用户能判断的信号：这句话是有来源支持的，还是模型自己补充的；没检索到相关资料时，要明确告诉用户"没找到依据"，而不是编一个答案。再就是提供反馈入口，用户觉得不对可以一键反馈，这些反馈也能回流成评估样例。

**追问备用**

- **引用会不会也是编的？** 会，模型可能引用不存在或不相关的内容。所以引用要由系统根据真实召回的块生成，并且校验引用的编号确实存在，不让模型自己写出处。
- **没检索到相关内容时怎么处理？** 设一个相关度的阈值，低于阈值就明确提示没有找到，而不是让模型硬答。这条要写进兜底规则里。

**边界句**

主动话术：引用展示我没有做过，我讲的是产品上的做法。我的立场是：来源要让用户能核对，不确定时要明说"没找到依据"，不用假精确的置信度。

**可挂载点**

- 不挂成我的经历。要类比的话，只能说"失败时把原因说清楚"和我做的 **预览启动失败给人话错误摘要** 是同一种"对用户诚实"的取向。

## 1.8 评估（链路我清楚，业务上没建正式回归集）

### 1.8-1 怎么判断一个 AI 功能变好还是变坏

**口述版**

> 我的想法是不靠感觉，靠对比。先定义什么叫"好"，按功能拆成几个可检查的维度：格式是否合规，内容是否包含必须有的、没有不该有的，任务是否真的完成，另外还有延迟和成本。然后用一批固定的样例，在改动前后跑同样的输入，对比这几个维度。线上还要看真实信号，比如用户重试、反馈、失败率，这些能发现样例没覆盖到的问题。先说明我的实际情况：业务上我没有建正式的评估体系，只在个人 demo 里做过一小套十条样例。但我清楚这件事的价值：AI 功能"看起来能跑"和"稳定"之间，差的就是这套度量。

**追问备用**

- **指标之间冲突怎么办？** 比如质量涨了但成本翻倍。要先和业务确认优先级，再决定取舍，不能只看单一指标。
- **线上信号靠什么拿？** 靠调用链和日志上报，我做过的是 AI 调用链的上报，能看到 token、成本和工具调用，但没有做过质量评估的指标。

**边界句**

主动话术：这块我没有生产落地，业务上没有建过正式的评估或回归体系。我清楚怎么做，也在个人 demo 里练过十条样例，但我不会把它说成线上做过的。

**可挂载点**

- 讲到"我做过"时挂 **个人 demo 的 10 条 golden cases**。
- 讲到"线上信号"时挂 **AI 调用链可观测**（只做上报这一块，说清楚是过程数据，不是质量评估）。

### 1.8-2 golden cases 与回归集怎么做

**口述版**

> golden cases 就是一批固定的、带期望结果的测试样例，作用是每次改动之后都能跑一遍，防止改一处坏一处。我会这样做：样例要覆盖典型场景和边界场景，并且要代表真实的分布，不能只挑好做的；另外专门收集历史上出过问题的 bad case，防止同一个坑再踩。每条样例写清期望，包括必须包含什么、不能包含什么、格式要求。格式用脚本检查，语义用打分或者按 rubric 让模型判分，再抽样人工复核。线上发现的新问题要回流进来。我自己只在个人 demo 里做过十条，业务上没建正式回归集，这点我会明说。

**追问备用**

- **样例要多少条？** 没有固定数字，起步先有一批覆盖主要场景的就行，重要的是持续补充。我不会编一个"标准数量"。
- **输出每次都不一样，怎么比？** 不比整段文字，比可检查的东西：格式是否合规、关键信息是否出现、禁止内容是否没出现。语义部分用 rubric 打分。

**边界句**

主动话术：回归集我只在个人 demo 里做过十条，业务上没有建。我没有大规模维护过样例集，也没有跑过大批量的模型判分，我讲的是方法，不是规模经验。

**可挂载点**

- 挂 **个人 demo 的 10 条 golden cases**（覆盖必须提到的类别和不能提到的内容）。
- 不要挂到 QPilot 业务上。

### 1.8-3 bad case 怎么归因

**口述版**

> 我的归因思路是先分层、再定位。第一步，先分清是格式问题还是语义问题：格式问题用脚本就能看出来，语义问题要看内容。第二步，往下按层排查：提示词，是不是指令含糊或者互相冲突；上下文，是不是该给的信息没给，或者太长被淹没了；工具，是不是工具描述写得含糊、参数填错，或者返回的内容有问题；最后才怀疑模型本身的能力。顺序上先排除前几层，因为它们是我能改的。还要能还原现场：当时的输入、上下文、工具调用过程，没有这些就没法归因。这块我讲的是方法，业务上没做过系统的归因流程。

**追问备用**

- **怎么还原现场？** 靠调用链的记录：每一轮的输入、工具调用和返回、token 用量。我做过 AI 调用链的上报，所以知道这些数据对排查有多重要。
- **怎么确认是不是改动导致的？** 用同一批样例，在改动前后各跑一遍对比。如果改动前也有问题，就是旧问题，不是这次引入的。

**边界句**

主动话术：这是排查方法，业务上我没有建过系统的 bad case 归因流程，也没有做过量化的归因统计。我清楚怎么分层排查，但不会说成线上跑过的流程。

**可挂载点**

- 讲"还原现场"时挂 **AI 调用链可观测**（只做上报这一块）。
- 讲"区分旧问题和新问题"时，可以类比 **预览里用本轮启动时间区分旧失败与新失败**，并说明这是类比。
