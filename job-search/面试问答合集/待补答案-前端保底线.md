## 4.5 前端实战题

### 4.5-1 你做过最复杂的组件 / 模块是什么？

- **口述版**：
  我做过最复杂的是 AI 编程平台的**预览状态机**，以及技术债后台的**可配置通用表格**。
  在预览模块里，用户写完代码后界面要实时决定是等待、启动、渲染还是报错。难点在于轮询、聊天流、启动流、沙箱阶段四个异步源都在通知前端，早期各自改状态导致界面反复横跳。
  我把它改造成两层：后端综合沙箱存活、文件与版本快照、启动流和“探两次间隔一秒”的 LISTEN 端口健康检查，算出九态之一并把判断原因一起回传；前端把后端状态和本地上下文喂给一个**纯函数做单点决策**，再用**本轮启动时间**过滤掉上一轮迟到的失败结果。
  另外在技术债后台，我从空仓库独立做到上线，把多个专项抽成一张通用表格，只传查询条件、列、行内按钮三份配置就能复用。

- **可挂载点**：
  - 在“四个异步源打架 → 两层九态单点决策”处，挂 **案例 3：QPilot 预览九态状态机**。
  - 在“多专项配置化复用”处，挂 **案例 7：技术债治理后台可配置表格**。

- **追问备用**：
  - **追问 1：为什么预览状态机要分前后端两层，而不是全放前端？**
    因为底层事实在后端（容器活没活、文件/快照在不在、LISTEN 端口通不通），而交互上下文在前端（对话流停没停、用户有没有点重试）。后端返回“状态 + 判断原因”让排障不用猜，前端用纯函数合并本地上下文算出最终动作，职责单一也好测。
  - **追问 2：那九个状态是一开始就设计好的吗？**
    不是，是随着踩坑逐步长出来的——比如沙箱回收后要读版本快照、把出站连接误判成端口占用后改成只查 LISTEN 状态。正因为每加一个异步源就多一处判断，最后我才回头把分散的决策点收敛成单点纯函数。

- **边界句**：
  QPilot 是我和另一位同事平级分工，预览模块由我负责落地，不能说我一个人主导了整个平台；九个状态也是迭代收敛出来的，不是第一天就设计好的。

### 4.5-2 多个页面形态一样，怎么避免重复写？

- **口述版**：
  核心思路是**“不复制页面，抽通用表格容器 + 传三项声明式配置 + 动态菜单兜底”**。
  我从空仓库独立做到上线的**技术债治理后台**就是典型场景。后台里有多个治理专项，业务字段不同，但页面形态完全一致：筛选区、数据表格、导入导出、行内操作按钮。
  我基于 React 18、Vite、TDesign 和 Redux Toolkit 做了一张通用表格组件，每个专项不建新页面，只传三样配置：**查询条件、要展示的列、行内按钮**。新增专项时加一份配置就行。
  同时，左侧菜单也不是写死在前端的，而是**由后端接口返回专项类型动态生成**：已知类型渲染通用表格，未知类型进兜底页，接口失败进错误页；Excel 导入前还会按当前列配置先校验表头，这样不管后端怎么加类型，都不会出现空菜单、白屏或脏数据入库。

- **可挂载点**：
  - 全程挂 **案例 7：技术债治理后台（动态菜单 + 兜底页 + 三样配置复用通用表格 + Excel 导入前校验表头）**。

- **追问备用**：
  - **追问 1：为什么菜单要由接口生成？如果后端加了新类型但前端还没配列信息怎么办？**
    专项类型会持续增加，写死在前端意味着每次加类型都要发版。由接口决定后，对未知类型专门做了兜底页、接口失败做了错误页，保证绝不白屏；常规字段可直接映射，特殊按钮支持传自定义渲染函数。
  - **追问 2：这个后台里的权限和登录异常是怎么统一处理的？**
    在请求拦截层把 `100001`（登录过期）和 `100002`（缺少权限）两个返回码严格分开处理，分别给用户重新登录引导和无权限提示，不会一报错就粗暴踢出。

- **边界句**：
  这是针对内部治理后台同构 CRUD 页面的配置化复用，不是对外通用的低代码拖拽平台；另外这个项目 2026 年的移动端适配不是我做的，不算我的成果。

### 4.5-3 复杂交互状态怎么保证不打架？

- **口述版**：
  复杂交互状态打架，根因往往不是时序本身，而是**决策点分散**和**新旧轮次混淆**。
  我在接手 AI 编程平台预览模块时，最常见的问题是重试时界面在“启动中”和“失败”之间反复横跳。原因是轮询、聊天流、启动流、沙箱阶段四个异步源都在各自改状态，谁晚到谁覆盖前面的结果。
  我的解法是三件事：第一，**收回修改权做单点决策**，只允许一个纯函数根据汇总输入计算九态，其他异步源只能提供输入；第二，用**本轮启动时间**区分新旧失败，早于本轮启动时间的旧报错直接丢弃；第三，在会话“编辑后重发”这种多步操作里**强制串行收敛**——模型还在输出时拒绝直接截断，必须先取消当前轮、等状态不再是输出中，再调截断接口同时删数据库和模型侧上下文，最后发新消息。

- **可挂载点**：
  - 主挂 **案例 3：预览状态机（四个异步源收敛成纯函数单点决策 + 本轮启动时间区分新旧失败）**。
  - 辅挂 **案例 5：会话截断与编辑重发（输出中拒绝截断，先取消再删数据库与模型上下文）**。

- **追问备用**：
  - **追问 1：为什么不用加锁来处理这四个异步源？**
    因为问题不是并发写冲突，而是多个异步来源在不同时间点各自得出结论——加锁挡不住晚到的旧请求排完队后依然覆盖新状态。只有“单点纯函数 + 本轮启动时间过滤旧事件”才能根治。
  - **追问 2：发送失败的消息点重发时，怎么防止把上一条正常历史消息误删掉？**
    消息发出去报错时可能还没落库，如果这时候无脑走截断，就会把上一条已存在的历史消息当成“最后一条用户消息”删掉。所以重发前我先判断有没有会话标识：有说明已落库可以截断，没有就跳过截断直接当新消息发。

- **边界句**：
  我用的是 TypeScript 联合类型配合纯函数做状态收敛，没有引入重型第三方状态机库；会话模块也是前后端配合完成的，不说成纯后端一人完成。

### 4.5-4 长列表 / 长消息卡顿怎么优化？

- **口述版**：
  长列表和长消息卡顿主要是 **DOM 节点过多** 或 **高频流式更新阻塞主线程**，我按三个层次处理：
  第一是**控制挂载节点与按需加载**：在固定结构长列表里用虚拟滚动（只渲染视口及缓冲区）；在 AI 编程平台里，我们把内置 Skills 从“手工全量塞进提示词”改成了 SDK 原生的**渐进式按需加载**，历史约 3507 个老会话也做成查询返回信号、前端按需触发迁移加载，避免一次性拉取和渲染大块数据。
  第二是**流式渲染与输入状态隔离**：模型流式输出时，历史已完成的消息块保持稳定不重渲，只增量更新最后一条消息；同时把底部输入框与消息列表解耦。
  第三是**交互不阻塞**：早期模型输出时直接禁用输入框，用户只能干等；我做了前后端持久化的**输出期间输入队列**，输出时用户照样能丝滑打字、排队、编辑、删除或置顶，前一轮结束自动发下一条。

- **可挂载点**：
  - 挂 **案例 5：会话模块（输出期间输入队列前后端持久化 + 历史会话按需迁移）**。
  - 挂 **Skills 重构（同步进沙箱 + SDK 原生渐进式加载）**。

- **追问备用**：
  - **追问 1：历史老会话按需迁移为什么要做成“查询只返回信号，前端再单独发请求迁移”？**
    因为后台有一条硬约束：“查询接口不做数据库变动”。所以查询接口读到老数据时一个字都不写，只返回需要迁移的信号；前端收到信号后再单独调迁移写接口，既守住了读写分离，只读协作者也能正常看历史，迁移本身也是幂等的。
  - **追问 2：如果做不等高消息的虚拟列表，展开代码块时怎么防抖动？**
    先用预估高度占位，节点挂载和代码块展开时通过 `ResizeObserver` 实测真实高度写回缓存，并重算后续偏移量；同时在用户主动上滚看历史时暂停自动滚底，避免视角乱跳。

- **边界句**：
  3507 个老会话是方案文档里的受影响估算值，不是我手工逐个修的数量；线上长对话主要靠流式增量隔离与截断控制，没有夸大成单页几万条 DOM 的极限压测。

### 4.5-5 多端（H5 / 小程序 / Hybrid）适配踩过什么坑？

- **口述版**：
  我在做 **QQ 频道多端前端** 时，负责过 Vue 3 多页 H5、Nuxt 3 Web、微信小程序多分包和 Next.js 15 Hybrid，在小程序作者资料卡和跨端迁移上踩过五个很具体的坑：
  第一是**多入口状态串号**：小程序最初全局只有一份资料卡状态，用户扫码进不同作者主页时，会闪出上一个人的头像和资料；我改成**按用户拆状态**，按用户标识隔离数据槽位才解决。
  第二是**跨分包引用限制**：小程序多分包下，跨分包引用不到私有组件，需要下沉公共层或走分包异步化。
  第三是**原生按钮遮挡**：自定义标题被小程序右上角原生胶囊按钮遮挡，得动态读取胶囊位置留出安全区。
  第四是**手势绕过确认**：iOS 侧滑返回会直接绕过页面内的屏蔽确认弹窗，必须拦截路由返回。
  第五是**分享卡片缺头像**：异步数据未就绪就触发分享会导致缺图，需做好数据就绪守卫与兜底。

- **可挂载点**：
  - 全程挂 **QQ 频道多端前端（`guild_mp` 小程序作者资料卡五个坑：全局状态导致扫码头像串号→按用户拆状态、分享卡片缺头像、标题被原生按钮遮挡、跨分包引用不到组件、侧滑返回绕过屏蔽确认；以及 `guild_web` Nuxt 3、`next-guild` Next.js 15 Hybrid）**。

- **追问备用**：
  - **追问 1：为什么全局一份状态在普通 H5 没暴雷，在小程序扫码时特别容易串号？**
    多页 H5 每次跳转往往重新初始化页面，而小程序是常驻内存的页面栈模型，全局 store 在冷启动周期内一直存在；从扫码等不同入口跳入同一个资料卡组件时，如果复用同一个全局字段，网络请求回来前就会直接渲染上一个人的残留状态。
  - **追问 2：做 `guild_web`（Nuxt 3）页面迁移适配时踩过什么 SSR 的坑？**
    主要是水合不一致（Hydration Mismatch）和服务端直接访问浏览器 API（如 `window` / `document`）报错。迁移作者主页和帖子恢复页时，需要把客户端专有逻辑放到挂载生命周期之后或用客户端专属容器包裹，保证服务端与客户端首帧结构一致。

- **边界句**：
  我在 QQ 频道多端中负责的是具体业务页面与组件（如作者资料卡、作者主页、帖子恢复页）的开发、迁移与问题修复，多端仓库底座是团队既有的，不包装成我从零搭建。

### 4.5-6 前端出错怎么不影响用户？

- **口述版**：
  我做前端容错的核心原则是：**局部报错绝不清空全局上下文、底层错误翻译成人话、异常分支全部有兜底页**。
  第一，在 AI 编程平台工作台里，我改造了 React **Error Boundary**：当某个局部模块渲染抛错触发错误边界时，**不再清空全局会话状态**，用户正在进行的对话上下文和输入队列都完好保留，只降级出错区块。
  第二，**给非开发者一句人话错误摘要**：平台用户很多是产品同学，预览启动失败时如果只抛容器日志他们看不懂；我在预览状态机里除了让后端回传判断原因供研发排障，还专门提取了**一句人话错误摘要**告诉用户为什么没起来；并且在日志出现致命错误时提前终止健康检查、清理占用的 3000 端口，把缺文件复现场景从约 60 秒缩到约 6 秒。
  第三，在技术债后台里，动态菜单遇到未知专项类型进兜底页、接口失败进错误页，`100001` 登录过期与 `100002` 缺权限分开提示，Excel 导入前先校验表头，把错误拦在前面。

- **可挂载点**：
  - 挂 **QPilot Error Boundary 触发时不清空全局会话状态**。
  - 挂 **案例 3：预览启动失败给非开发者一句人话错误摘要 + 缺文件场景 60 秒→6 秒**。
  - 挂 **案例 7：技术债后台（未知类型进兜底页、100001/100002 分开处理、Excel 表头前置校验）**。

- **追问备用**：
  - **追问 1：除了预览失败，部署的时候怎么防止用户因为不知道风险而丢数据？**
    我做了**部署存储预检**（案例 4）：提示词先约束模型不要把业务数据写到容器本地，并在收尾自检时把“是否使用易失存储”写进配置标记；部署前预检读这个三态标记，只有为 `true`（数据易失）或读取失败时才弹确认框提醒用户，老项目无标记不误拦。
  - **追问 2：线上报错怎么跟监控告警结合，避免告警误报？**
    在 QPilot 里我把部署、Git 提交推送和首页核心接口接入了伽利略结构化上报（分 P0/P1）；在 QQ OKR 调用链上报里，把业务规则主动拦截导致的 `ERROR+Abandoned` 改成了 `UNSET + WARNING` 加 `business-intercept` 标记，避免业务正常拦截污染真故障大盘。

- **边界句**：
  60 秒降到 6 秒只针对“缺文件”这一个复现场景，不是整体预览耗时；QQ OKR 里我也只负责调用链上报这一块，OKR 业务建模和前端不是我做的。

### 4.5-7 上传 / 文件处理怎么设计？

- **口述版**：
  设计上传和文件处理，我重点抓三条：**统一收口与对象存储转存、安全门禁前置到解析请求体之前、业务前置校验**。
  在 AI 编程平台里，我负责了**上传与身份模块**，把分散的上传收口成**统一上传 API**，支持单文件最大 **1GB**，聊天里的附件统一转存到腾讯云 COS，不在应用容器本地堆大文件。
  最关键的一个设计细节是：**上传门禁按 Origin 白名单校验，并且严格放在解析请求体（body parser）之前**。如果等收完高达 1GB 的文件流再去验来源，非法请求光靠发大包就能把带宽和内存打爆；把门禁前置后，不在白名单内的请求在读请求头阶段就直接拒绝，一个字节的 body 都不收。
  而在技术债治理后台做 Excel 导入导出时，我把防线前置到浏览器端：**导入前先解析并校验表头**，表头不对当场拒绝，绝不让脏数据进库后再排查。

- **可挂载点**：
  - 主挂 **QPilot 上传与身份模块（统一上传 API、单文件 1GB、聊天附件转存 COS、上传门禁按 Origin 白名单且放在解析请求体之前）**。
  - 辅挂 **案例 7：技术债后台 Excel 导入导出前校验表头**。

- **追问备用**：
  - **追问 1：为什么在部署代理转发时也会遇到请求体（POST body）的问题？你踩过什么坑？**
    在部署模块里我修过一个反向代理丢 POST body 的坑（案例 4）：网关层的 `express.json()` 先把请求体消费解析掉了，转发给用户沙箱里的应用时没把流重新写回去，导致里面的 FastAPI 报 422、Express 拿到 `body=null`。这和上传门禁放解析请求体之前一样，核心都是对请求流生命周期的把控。
  - **追问 2：上传和预览、部署里的身份鉴权是怎么统一的？**
    我们接入了太湖 TOF 统一认证，由平台统一提供 `/auth/me` 返回员工完整信息，预览与部署共用同一套身份机制，平台侧解密请求头，密钥始终不进沙箱。

- **边界句**：
  我们在 QPilot 里落地的是统一上传 API（1GB 上限）、转存 COS 和 Origin 门禁前置，没有做前端自定义切片断点续传协议，这点如实说明。

### 4.5-8 发布流程怎么分环境？

- **口述版**：
  分环境发布的核心是**测试求快、正式求稳且受控、环境配置隔离**，我有三段真实经历：
  第一是**前后端项目的分支发布分级**：在我独立负责的技术债治理后台里，测试分支推送后自动构建并更新测试环境；正式分支只构建镜像，必须通知**人工确认**后才上线。
  第二是**存量多服务交付链路迁移**：在多服务资源整合迁移中，9 个服务跨 4 条业务线，我负责交付链路（代码仓库迁移、流水线迁移、七彩石配置与环境变量关联）。我严格按“先仓库、再流水线、最后配置”的顺序推进，每个服务先在测试环境跑通再动正式，并把这批服务从“构建完直接更镜像”改成了**走审批流**。
  第三是**平台内预览与正式双环境最小隔离**：在 AI 编程平台部署模块里，我把一个项目的预览环境和正式环境拆开——环境变量文件分开、数据库策略可选，并记录每次部署成功的 `sourceVersionId` 在版本历史里标识已发布版本。

- **可挂载点**：
  - 挂 **案例 7：技术债后台（测试分支自动发布 / 正式分支人工确认）**。
  - 挂 **案例 8：多服务资源整合迁移（9 个服务跨 4 条业务线，仓库→流水线→配置顺序，改走审批流）**。
  - 挂 **案例 4：QPilot 部署（双环境最小隔离 + 部署成功记录 `sourceVersionId` + 子域名白屏强制 Vite `base` 为 `/`）**。

- **追问备用**：
  - **追问 1：迁移那 9 个服务时踩过什么环境或存储上的坑？**
    踩过两个：一是 Langfuse 迁过去后依赖的 ClickHouse 跨环境被网络 ACL 拦了，权衡白名单耗时后决定在原机器自建 ClickHouse；二是上线后历史数据把磁盘写满导致上报失效，我通过清历史数据、给 trace 表加 1 天 TTL、挂载 100G 专用盘彻底解决。
  - **追问 2：测试部署、正式部署和预览域名在网关转发上有什么踩坑经历？**
    接入统一认证后预览域名报 404（案例 6）。我定位出根因是：测试部署和正式部署的回源走 80 端口都能命中各自规则，但预览域名的转发规则只配在负载均衡的 **443 监听器**下；回源配成 80 就落到了部署默认后端，改成 443 回源才恢复。

- **边界句**：
  多服务迁移是我和另一位同事分工（DNS/CLB 是同事做的），**不能说“我主导了这次迁移”**；而且 QPilot Code 走的是自己的 stream CI，**不能说“9 个服务全部接入了审批流”**；平台双环境也只是环境变量和数据库策略的“最小隔离”。

## 4.9 手写题两个高价值变体

### 4.9-1 带重试的并发池（Concurrency Pool with Retry）

- **完整可运行代码**：
```javascript
/**
 * 带重试的并发池：限制最大并发数 + 失败重试 N 次 + 仍失败保留上下文抛出
 * @param {Array<() => Promise<any>>} tasks 任务工厂数组（调用时才真正发起请求）
 * @param {number} concurrency 最大并发数
 * @param {number} retries 单任务失败后的最大重试次数
 * @param {number} retryDelay 重试等待毫秒数
 * @returns {Promise<Array<any>>} 按原任务顺序排列的结果
 */
async function runPoolWithRetry(tasks, concurrency = 3, retries = 2, retryDelay = 200) {
  if (!Array.isArray(tasks) || tasks.length === 0) return [];
  const results = new Array(tasks.length);
  let nextIndex = 0;

  async function runTaskWithRetry(taskFn, index) {
    let lastError;
    for (let attempt = 0; attempt <= retries; attempt++) {
      try {
        return await taskFn(attempt);
      } catch (err) {
        lastError = err;
        if (attempt < retries && retryDelay > 0) {
          await new Promise((r) => setTimeout(r, retryDelay));
        }
      }
    }
    const error = new Error(
      `Task[${index}] failed after ${retries + 1} attempts: ${lastError?.message ?? lastError}`
    );
    error.cause = lastError;
    error.taskIndex = index;
    throw error;
  }

  async function worker() {
    while (nextIndex < tasks.length) {
      const current = nextIndex++;
      results[current] = await runTaskWithRetry(tasks[current], current);
    }
  }

  const workerCount = Math.min(Math.max(1, concurrency), tasks.length);
  await Promise.all(Array.from({ length: workerCount }, () => worker()));
  return results;
}
```

- **20 秒讲法（口述版）**：
  “分两层写：内层 `runTaskWithRetry` 用 `for (attempt = 0..retries)` 包住单次任务，失败就延迟重试，重试耗尽仍失败时把原始错误挂在 `error.cause` 并带上 `taskIndex` 抛出来；外层启动 `Math.min(concurrency, tasks.length)` 个 `worker` 协程，共用同步游标 `nextIndex++` 抢任务，结果按原下标 `results[current]` 写入，既控死并发数又保证结果顺序。”

- **怎么和「Agent 取消与状态收敛」串起来讲**：
  写完代码顺势接一句：“在我的 **预览状态机（案例 3）** 里，重试有两条铁律：第一，**区分偶发抖动和致命错误**——热重载端口抖动我们会探两次、间隔一秒重试；但一旦容器日志已经报了缺文件这类致命错误，就立即短路终止，不傻等重试超时（缺文件场景从约 60 秒降到约 6 秒）。第二，**重试必须带本轮启动时间**，防止上一轮失败的慢响应回来覆盖新一轮重试的状态。”

- **追问备用**：
  - **追问 1：为什么入参必须是函数数组 `() => Promise`，不能直接传 `Promise[]`？**
    因为 `new Promise` 创建瞬间请求就已经发出了，传 `Promise[]` 无法控制并发；必须传懒执行函数，等 `worker` 领到任务调 `taskFn()` 时才真正发起请求。
  - **追问 2：如果希望单个任务彻底失败时不中断其他任务，怎么改？**
    在 `worker` 里用 `try/catch` 包住 `runTaskWithRetry`，成功存 `{ status: 'fulfilled', value }`，彻底失败存 `{ status: 'rejected', reason: error }`，对齐 `Promise.allSettled` 即可。

- **边界句**：
  这是前端并发池的标准实现；在 QPilot 换 OpenSandbox 后的 Git 性能优化里，我们解决十多次请求慢靠的是**把 7 个接口的多条命令合并成单次脚本往返（状态检查十多次→1，提交推送 6→1）**，而不是靠前端并发硬刷。

### 4.9-2 可取消的 Promise（AbortController）

- **完整可运行代码**：
```javascript
/**
 * 基于 AbortController 的可取消异步包装器（支持透传 signal 与外部级联取消）
 * @param {(signal: AbortSignal) => Promise<any>} taskFn 接收 signal 的任务函数（可传给 fetch）
 * @param {AbortSignal} [externalSignal] 可选的外部取消信号
 */
function createCancellablePromise(taskFn, externalSignal) {
  const controller = new AbortController();
  const { signal } = controller;

  const onExternalAbort = () => controller.abort(externalSignal.reason);
  if (externalSignal) {
    if (externalSignal.aborted) {
      controller.abort(externalSignal.reason);
    } else {
      externalSignal.addEventListener('abort', onExternalAbort, { once: true });
    }
  }

  const promise = new Promise((resolve, reject) => {
    if (signal.aborted) {
      return reject(signal.reason ?? new DOMException('Aborted', 'AbortError'));
    }

    const onAbort = () => {
      reject(signal.reason ?? new DOMException('Aborted', 'AbortError'));
    };
    signal.addEventListener('abort', onAbort, { once: true });

    Promise.resolve()
      .then(() => taskFn(signal))
      .then(
        (val) => {
          signal.removeEventListener('abort', onAbort);
          resolve(val);
        },
        (err) => {
          signal.removeEventListener('abort', onAbort);
          reject(err);
        }
      );
  }).finally(() => {
    if (externalSignal) {
      externalSignal.removeEventListener('abort', onExternalAbort);
    }
  });

  return {
    promise,
    abort: (reason) => controller.abort(reason),
    signal,
  };
}
```

- **20 秒讲法（口述版）**：
  “我基于原生 `AbortController` 实现，核心抓三点：一是进入前先判 `signal.aborted` 做同步短路；二是把 `signal` 作为参数透传进 `taskFn` 里的 `fetch` 或流读取器，确保调 `abort()` 时不仅外层 Promise 立刻 `reject`，底层网络请求也真实断开；三是在任务结束的 `then` 和 `finally` 里清理 `abort` 监听器，防止长生命周期 `signal` 引起内存泄漏。”

- **怎么和「Agent 取消与状态收敛」串起来讲（核心加分连接点）**：
  这道题写完，直接把话题拉到 **案例 3（预览状态机）+ 案例 5（会话截断与编辑重发）**：
  > “在 AI Agent 工作台里，前端调 `abort()` 掐断请求只是第一步，真正的难点是**取消后的前后端状态收敛**：
  > 1. **会话‘编辑后重发’的顺序收敛（案例 5）**：当模型还在流式输出时，用户改了一句话点重发，绝对不能一边流式往页面上写字、一边直接调截断接口删库。我定的顺序是：**先发 cancel 取消当前这轮 → 等运行状态收敛、不再是‘输出中’ → 再调截断接口，同时删掉数据库里的消息和模型侧的会话上下文与指针 → 最后把改过的句子当新消息发出去**。而且如果上一条消息刚发出去就报错、还没落库（没有会话标识），重发时要跳过截断，防止误删更早的历史消息。
  > 2. **预览重试的竞态收敛（案例 3）**：用户取消或重试后，上一轮残留在途的检查结果可能晚到，所以除了主动 abort，我们还用**本轮启动时间**兜底过滤，早于本轮启动时间的旧失败一律忽略，保证取消后状态绝不乱跳。”

- **追问备用**：
  - **追问 1：为什么截断时一定要数据库和模型侧两边都删？只取消前端流、删数据库行不行？**
    不行。因为页面消息编号和数据库不是同一套，更重要的是模型侧自己维护了一份会话上下文和指针，下次发消息它会顺着旧指针接着写。只删数据库的话，模型还在按被删掉的旧内容续写，两边看到的历史就彻底劈叉了。
  - **追问 2：只用 `Promise.race` 包一个取消信号，不把 `signal` 传进 `taskFn` 有什么问题？**
    只用 `Promise.race` 属于“假取消”——外层调用方虽然提前拿到了报错，但内层的 `fetch` 或流还在后台继续跑，等它跑完回来如果没有时间戳或状态拦截，依然会触发副作用把旧结果写进页面状态。

- **边界句**：
  前端 `AbortController` 只能断开浏览器到服务端的连接，不能自动清理服务端状态；AI 会话的取消与截断必须靠前后端配合（输出中拒绝直接截断 + 同步清理数据库与模型侧上下文）才能真正闭环。

## 4.6 前端线系统设计（三道，按 8 分钟结构）

### 4.6-1 设计一个可配置的中后台表格 / 表单系统

**需求澄清（先问 3 个）**：专项有几类、后续还会不会加？字段差异是「列不同」还是「交互不同」？要不要行内编辑 / 审批 / 权限粒度？导出量级多大？

**数据模型**：配置驱动，三份声明式配置——查询条件、列定义、行内按钮。列定义里带 key / 标题 / 渲染方式 / 宽度 / 是否可导出。菜单不写死在前端，由接口返回专项类型生成；统一分页与排序参数。

**状态机**：查询参数放 URL（可分享、刷新不丢）；表格状态（分页、排序、筛选）由一个受控对象驱动，组件本身无状态。

**渲染策略**：一张通用表格组件承载所有专项；已知类型渲染通用表格，未知类型进兜底页，接口失败进错误页。复杂交互允许传自定义渲染函数，不做拖拽式低代码。

**错误与安全**：登录过期（100001）与缺权限（100002）分开处理；导入前先按当前列配置校验表头；导出走服务端，不在浏览器拼大文件。

**性能与监控**：分页而非全量拉取；导出异步化；关键操作打点上报。

**取舍（2 个）**：
- 配置化 vs 灵活性：选配置化，代价是遇到非标准交互仍要写自定义渲染，所以必须留渲染函数这个口子；不做通用低代码，因为维护成本会超过收益。
- 接口驱动菜单 vs 前端静态路由：选接口驱动，换来「加专项不用发版」，代价是未知类型和接口失败必须有兜底，否则会白屏。

### 4.6-2 设计一个多端页面适配方案

**需求澄清**：哪几端（QQ 内 H5 / 微信小程序 / Hybrid / Web）？是否同一套业务与同一份数据？各端发布节奏是否独立？

**数据模型**：业务模型与请求层共享，视图层分端；组件分三层——基础组件、业务组件、端适配层（差异只允许出现在适配层）。

**状态机**：小程序是常驻内存的页面栈模型，状态必须按「用户 / 实例」隔离，不能全局一份；跨入口进入时先按标识取自己的数据槽位。

**渲染策略**：小程序走多分包 + 分包异步化；Nuxt/Next 的 SSR 页面注意首帧一致，浏览器专有 API 放到挂载之后；Hybrid 处理键盘遮挡与安全区，原生导航栏要按胶囊位置留白。

**错误与安全**：分享前做数据就绪守卫（否则卡片缺图）；屏蔽/确认类交互要拦路由返回，不能只靠页面内弹窗。

**性能与监控**：分包预加载、图片按需、控制单次 setData 的数据量；各端统一错误上报。

**取舍（2 个）**：
- 一套代码 vs 多套：选「共享业务逻辑 + 分端视图」，代价是适配层要长期维护，收益是业务逻辑只改一次。
- SSR vs CSR：列表页用 SSR 换首屏，交互重的页面退回 CSR，代价是要处理水合不一致。

### 4.6-3 设计一个前端错误与监控上报体系

**需求澄清**：要发现什么（白屏、接口错、资源错、性能）？告警发给谁？能否接受采样？要不要 sourcemap 还原？

**数据模型**：事件模型包含类型、级别、release 版本、trace_id、用户标识（脱敏）、堆栈、上下文快照；按 P0/P1 分级。

**状态机**：错误边界分级——局部边界只降级出错区块，不清空全局会话状态；未捕获错误走白屏兜底页。

**渲染策略**：兜底页给人话错误摘要 + 重试入口，不把原始堆栈丢给非技术用户。

**错误与安全**：上报前脱敏，不带令牌和内网地址；同类错误去重 + 限流，避免一次故障把上报通道打爆。

**性能与监控**：批量聚合上报、页面卸载用 sendBeacon；上报本身不能阻塞主线程。

**取舍（2 个）**：
- 全量 vs 采样：默认全量抓错误类，性能类采样，代价是可能漏掉低频问题。
- 实时 vs 批量：错误实时上报（宁可多一点请求），性能数据批量（省带宽）。
