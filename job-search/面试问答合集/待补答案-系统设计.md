## 二、系统设计

### 2-1 设计一个 AI Agent 工作台

**需求澄清（我会先问 3 个问题）**

1. 用户是谁:开发者,还是不懂代码的业务同学?这决定错误信息怎么写、哪些细节要藏起来。
2. Agent 能碰什么:写文件、跑命令、提交代码、部署,哪些动作不可逆、需要外部权限?
3. 一次任务有多长,用户能不能中途插话或取消?

非目标:多 Agent 编排、跨会话长期记忆,第一版不做。

**数据模型**

项目、会话、消息、一次 run、工具调用、文件版本快照、预览状态、部署记录。关键点是文件要有版本快照:沙箱会被回收,状态不能只活在沙箱里,否则回收后界面就会判断成"没有项目"。部署记录要关联它发布的是哪个版本,版本历史才能显示"已发布的是哪一版"。

**状态机**

run 分排队、输出中、取消中、完成、失败。预览是另一台独立的状态机,我做的是九态,由一个纯函数根据后端算出的状态加前端本地上下文,算出"现在该做什么"。后端每次返回"该做什么 + 为什么",排障不用猜。

**渲染策略**

左边对话流式输出,右边是文件树、diff 和预览。工具执行中、失败都要有独立的展示态,不让用户对着转圈猜。模型输出不直接渲染成 HTML,预览放在隔离的 iframe 里。

**错误与安全**

核心问题是"模型能碰什么"。Git 面板走后端接口、先做冲突和分叉检查；对话里模型用沙箱原生 git 命令，凭证在仓库配置里，靠提示词约束不主动提交；另外为 AI 写入设计过短期令牌加后端代执行的受控方案，但没从界面接进去。部署走受控工具，身份密钥不出平台，上传的来源校验放在解析请求体之前。失败时给非开发者一句人话摘要,而不是原始报错。

**性能与监控**

性能上做的是减少往返:把一个接口里的多条命令合并成一次调用。监控上,关键链路(部署、提交推送、首页核心接口)做结构化上报并分级。我没有用户量或调用量数据,这里只讲设计,不报数字。

**取舍**

1. **AI 写入的受控令牌方案（设计实现过、未接入界面）。** 放弃的是灵活性和实现的简单:每个能力都要在后端开接口,模型也不能随手拼命令。换来的是作用域收窄、载荷不可篡改、执行前统一预检、操作可审计。令牌 30 分钟有效,带签名和载荷哈希。但要主动说清:当前线上 Git 是「面板预检 + 对话原生 git」两条路,凭证在沙箱仓库配置里,不是「凭证不进沙箱」。
2. **预览九态用单点纯函数决策,不让各个异步源各自改状态。** 放弃的是"哪里发现问题就地处理"的方便。原因是轮询、聊天流、启动流、沙箱阶段四个来源各改各的,谁晚到谁覆盖,状态乱跳。代价是每加一个状态,都得回到这一个函数里改。

**边界**:我是两名主力开发之一,不是平台创建者;这是单 Agent 加 Skills,没做多 Agent 编排。九态是逐步长出来的,不是一开始设计好的。

### 2-2 设计一个 Chat + tool call + file diff + preview 系统

**需求澄清（我会先问 3 个问题）**

1. diff 是给谁看的:开发者要逐行审,还是业务同学只要知道"改了什么"?
2. 预览是实时跟随,还是等本轮对话结束再启动?
3. 运行环境会不会被回收,回收后还要不要能看到之前的结果?

**数据模型**

message 里挂 tool_call(名字、参数、状态、结果);一轮对话关联 file_change(文件、前后版本);再关联 preview_state。预览要能读版本快照,而不是只依赖运行中的沙箱。每个失败要带"属于哪一轮启动"的时间标记,后面做状态判断要用。

**状态机**

tool_call 分执行中、成功、失败。聊天分输出中、完成、取消。预览的关键规则是:对话还在输出时,预览先等待,不抢着启动,结束后再判断是启动、渲染还是报错。失败之后重试,要保证界面不在"启动中"和"失败"之间来回跳。

**渲染策略**

工具调用在对话流里按状态渲染,文件变更汇总成 diff 视图,预览在 iframe 里加载。启动失败时,给一句人话的错误摘要,让不懂代码的人也知道下一步该做什么。

**错误与安全**

日志里已经出现致命错误,就提前结束健康检查,不干等超时。失败和启动时都清理目标端口,避免失败进程一直占着,导致下一轮端口漂移。探活有两套,别混:启动收尾那套最多三十次、间隔一秒,靠日志里的致命错误提前退出;状态接口那套只探两次、间隔一秒,任一次成功就算健康,两次都失败才返回错误态——第一次失败不对外输出任何状态,请求还挂在一个 HTTP 调用里,界面保持原样。

**性能与监控**

缺文件这个场景的恢复时间,从约 60 秒降到约 6 秒。要说明:这只是这一个复现场景,不是整体预览耗时,我没有做全量对比。

**取舍**

1. **端口检查只查 LISTEN 状态。** 放弃的是"端口只要出现就算占用"的保守判断。原因是本机往外连模型网关时,系统会分配临时本地端口,原来的检查把它也算成占用,预览服务就不启动了。代价是:如果遇到非监听状态的冲突,这个检查看不到。
2. **用本轮启动时间区分旧失败和新失败,不加锁。** 放弃的是"用锁挡住并发"的直觉方案。问题不是并发写冲突,而是多个来源各自得出结论,加锁挡不住谁晚到。代价是每个失败都要带时间标记,判断里多一个条件。这个判别式有已知局限:同毫秒、时钟回拨、跨实例时钟偏差都会影响;更稳的做法是每轮生成一个 runId、失败记录挂上去、判断改成比相等——改动只在后端(启动生成、写失败携带、状态接口读取),前端不参与。

**边界**:进程内预热池是空实现,功能白名单和沙箱代理服务已删除,这三项不当成果讲。

### 2-3 设计一个长对话消息流与虚拟列表

**需求澄清（我会先问 3 个问题）**

1. 一个会话大概有多长:几十条,还是几千条?这决定要不要上虚拟列表,不要一上来就做。
2. 流式输出时,用户能不能同时发新消息?
3. 能不能编辑历史后重发,重发后后面的回复怎么处理?

**数据模型**

消息有稳定 id、角色、内容、状态(输出中、完成、失败)。排队中的消息单独存,和已落库的消息分开,支持编辑、删除、置顶。要注意:页面上的消息编号、数据库里的编号、模型侧自己的会话记录,不是同一套,截断时三者要对得上。

**状态机**

输出中、取消中、空闲三态。编辑重发要按顺序走:先取消当前这一轮,等状态不再是输出中,再截断,最后把改过的句子当作新消息发出。输出期间不允许直接截断,因为一边删记录、一边还有字往页面写。

**渲染策略**

消息高度不固定,流式输出时最后一条还在持续变高,所以虚拟列表要用动态高度:先估算,渲染后再校正。流式时只更新最后一条,其他消息保持稳定引用,避免整个列表重渲染。用户向上翻看历史时,不要强行滚到底部。

**错误与安全**

发送失败的消息还没落库,重发前先判断有没有会话标识:有就说明已落库,可以截断;没有就跳过截断,直接当新消息发,否则会把上一条已有的历史误当成"最后一条用户消息"删掉。模型输出不直接当 HTML 渲染。

**性能与监控**

长列表卡顿和输入卡顿要分开查:前者看渲染节点数和重渲染范围,后者看输入时有没有触发了大范围更新。我没有规模数据,不报数字。

**取舍**

1. **输出期间允许继续输入,消息进队列。** 放弃的是"输出时禁用输入框"的简单实现。原来的做法让用户只能干等;做成队列后,前一条结束会自动发送第一条,前后端都做并持久化。代价是多了一套队列状态要维护,还要处理刷新后的恢复。
2. **截断时数据库和模型侧上下文两边都删。** 放弃的是"只删页面和数据库"的省事做法。只删一边,模型仍然按旧上下文续写,用户会问"我明明删了,它怎么还接着说"。代价是两处要保持一致,一边失败时要有补救。

**边界**:虚拟列表我讲的是设计思路,没有在 QPilot 里做过;真实做过的是输出期间输入队列、截断(两边都删)和历史会话按需迁移。
