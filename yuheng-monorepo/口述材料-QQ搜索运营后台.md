## 零、开口前先讲这个：这个系统是什么

**不要一上来讲 monorepo 和微前端**。第一次听的人需要先有一个画面。

### 30 秒版

> 这是 QQ 搜索的**运营后台**，不是用户看到的搜索页。
> 用户在 QQ 里搜一个词，看到的结果长什么样，是运营人员在这个后台里配置出来的。比如用户搜"奥运"，结果顶部出现一张"热议话题"卡片，卡片标题是什么、点进去跳去哪里、里面放哪几条帖子，都是运营在后台填的。
> 运营在后台创建一条"**任务**"，任务有生效时间；到了时间，任务才会改变线上用户看到的搜索结果。
> 我在这个后台里负责前端，主要做了几块配置功能：官方频道定向召回、异型卡片的频道 tab、干预配置里的垂搜迁移和 Doc 维度屏蔽，以及一批列表搜索和导出的优化。

### 先建立四个词（后面反复出现）

| 词 | 白话解释 |
|---|---|
| **任务** | 运营的一次配置。有名称、负责人、状态、生效时间，有的还带"测试白名单"（测试阶段只有指定账号能看到效果） |
| **干预** | 改变默认的搜索结果。比如：把某条内容插到第 3 位、把某条内容屏蔽掉、调整某个频道 tab 里业务的排序 |
| **召回** | 用户搜某个词时，让某类内容出现在结果里。"官方频道定向召回"就是搜到某些词时，把指定频道的头卡拉出来 |
| **异型卡片** | 搜索结果页里一张由多个"模板"拼起来的卡片，运营在后台选模板、填素材，右边实时预览手机里的样子 |

### 后台页面的整体结构（一句话讲清楚代码怎么组织）

所有"任务类"页面共用一个**通用任务壳**：上面是查询条件，中间是表格，点"创建"弹出右侧抽屉。每个业务只需要提供：查询字段怎么配、表格列怎么配、创建表单怎么配、提交时把表单数据转成后端协议。

```
通用任务壳 components/task-manage      ← 表格 + 抽屉 + 创建/编辑/改状态，所有页面共用
  ├─ 干预配置 pages/meddle-config       ← 屏蔽、插入、排序等"干预"类任务
  ├─ 卡片配置 pages/template            ← 异型卡片：选模板、填素材、右边预览
  ├─ 官方频道召回 pages/recall-guild-config  ← 这个是我从 0 新建的，结构自成一套
  ├─ 推荐词 pages/recommend-word        ← 推荐词 / 底纹词干预
  └─ 热点 pages/hotspot
```

> 这一页的作用是：**后面每条需求讲到"改了哪个页面"，听的人不会迷路**。

## 一、官方频道定向召回页（从 0 到 1）

**什么时候讲：** 面试官问"你独立做过什么 / 从零做过什么功能"。
**证据：** `442b2a8e`（2024-11-13）起，到 12-02 共 13 个提交，同期 `recall-guild-config` 目录**全部是你的**。首个提交 14 个文件、1277 行。

### 背景：这是什么需求

用户在 QQ 搜"某个词"时，希望能直接看到某些官方频道。运营需要一个页面，**配置"搜索词 → 频道"的对应关系**：运营配置一个搜索词，用户搜这个词时，结果里会把指定频道的头卡召回出来。这是一块**全新的业务，之前没有页面**。

群里的排期是：前端开发 2 天，联调 1 天。中途因为"小世界转发配置被下架、自有中转站还没就绪"，一度 hold，等新中转站完成后 11-25 联调完推到测试环境。

### 代码逻辑：页面由哪几块组成

这个页面我没有用通用任务壳，而是自己写了一套（`task-manage.tsx`），因为它的交互和别的任务不一样：**没有生效时间，只有关键词、备注、修改人；而且需要批量导入导出**。

拆成几块配置文件，各管一件事：

| 文件 | 管什么 |
|---|---|
| `query-form-config` | 顶部查询条件：关键词（支持模糊匹配）、更新时间、修改人（可一次搜多个，换行输入） |
| `table-config` | 表格有哪几列 |
| `create-form-config` | 创建抽屉里要填哪些字段 |
| `detail-config` / `custom-detail` | 查看详情抽屉 |
| `task-manage` | 把以上配置串起来：查询、创建、删除、导出、Excel 导入 |
| `services/recall-config` | 四个接口：创建、删除、查询、导出 |

**一个值得讲的细节：为什么拆成配置文件**。查询条件、表格列、表单字段都是"描述性"的，页面逻辑一变（比如后端加一个字段），只改配置，不碰交互代码。这套思路和"通用任务壳"是一致的。

### 方案：联调阶段的几次变化

初版是按"频道名称、频道简介、频道主 QQ 号"设计的（导出表头里还留着这个痕迹）。联调后后端协议变成"关键词、更新时间、备注、修改人"，所以 `21ca403c`（11-25）把表格列、导出字段、总数字段（`taskSum`）都换了一遍，同时补上了**删除调用**——初版里"确认删除"点了只是关弹窗，并没有真的调接口。

### 一条链

1. 运营点"创建"，抽屉里填关键词（一行一个）和备注。
2. 点确定，前端调创建接口，成功后刷新表格。
3. 也可以下载 Excel 模板，填好后上传。前端用 `xlsx` 库在浏览器里直接解析，不经过后端；解析后一次调创建接口。
4. 如果有创建失败的行，后端会返回失败列表和原因，前端把它**写成一个 Excel 自动下载**，运营可以直接对着修改后重传。
5. 表格支持勾选后导出、勾选后删除。

### 最终结果

页面从 11-13 开始写，11-25 联调完成。上线后又经历了几轮优化（见第二章"全选与导出"、第三章"批量创建提示"）。

### 60 秒版

> 官方频道召回是一块新业务：用户搜某些词时，把指定频道的头卡召回出来。之前没有后台页面，运营没法配。我从零写了这个页面：查询、创建、详情、删除、导出，还有 Excel 批量导入。
> 结构上我把查询条件、表格列、创建表单拆成配置文件，交互逻辑集中在一个文件里，后端协议一变只改配置。联调时后端把字段从频道名称改成了关键词和备注，我一次性换了表格列和导出字段，也补上了初版没接的删除调用。
> 批量导入这块有个细节：失败的行不是弹个错误就完，而是把失败原因写成 Excel 直接下载给运营，他们能照着改了再传。

### 边界

- 页面是我写的，但**接口和召回逻辑是后端的**，我不讲"召回怎么实现"。
- "转发配置被下架、中转站没就绪"在转发层，前端只有 `d3f79af7`（接通转发服务）一个痕迹。
- 没有"创建多少任务、节省多少人力"的数字，不要编。

## 二、全选、翻页与导出（一个听起来简单、实际有坑的问题）

**什么时候讲：** 问"你遇到过什么有意思的 bug / 表格交互怎么处理"。
**证据：** `89da113d`（11-27，全选优化）、`2480d64f`（12-02，修改下载内容）、`b49992b0`（11-28）。

### 背景：运营反馈了三个现象

1. 没勾选任何行，点导出，只导出了一条。
2. 点了全选，再导出，只导出了第一页。
3. 先按条件筛选，再导出，导出的还是全部数据，不是筛选结果。

还有一条同类的：**全选后点删除，只删了当前页**。

### 原因：表格的"全选"只管当前页

这是表格组件（TDesign 的 `BaseTable`）的默认行为：表头那个"全选"复选框，**只选当前页的行**。翻到下一页，选中状态要么丢，要么只保留已选 id，没选的新页不会自动并入。

对运营来说"全选"的直觉是"我筛出来的全部"，而不是"这一页"。直觉和实现不一致，就产生了上面三个现象。

### 代码逻辑：怎么解决

**第一步，记住"当前是不是全选状态"。**

```ts
const [isCheckedAll, setIsCheckedAll] = useState(false);
// 表格选择变化时
onSelectChange(selectedRowKeys, options) {
  if (options.currentRowKey === 'CHECK_ALL_BOX') {
    setIsCheckedAll(options.type === 'check');   // 点的是表头全选框，才算全选
  } else {
    setIsCheckedAll(false);                      // 点的是某一行，退出全选状态
  }
  ...
}
```

关键判断是 `currentRowKey === 'CHECK_ALL_BOX'`：区分"点了表头全选"和"点了某一行"。

**第二步，翻页时，如果还处于全选状态，把新页的行自动并入选中。**

```ts
const queryTaskList = async (params) => {
  const result = await 查询接口(...);
  if (isCheckedAll) {
    const selected = [...selectedRow];
    result.tasks.forEach((item) => {
      if (!selected.includes(item.id)) selected.push(item.id);   // 新页的行补进来
    });
    setSelectedRow(selected);
  }
  setQueriesRecord(params);   // 同时记住这次的查询条件
  ...
};
```

**第三步，记录查询条件，导出时带上。**

```ts
const { current, pageSize, queries } = queriesRecord;
const downloadConditions = {
  export_ids: isCheckedAll ? [] : selectedRow.map(Number),   // 全选时传空数组
  page_number: current,
  page_size: pageSize,
  ...queries,                                                // 把筛选条件一起带上
};
```

这里的设计是：**全选时不传具体 id，传空数组 + 筛选条件，由后端按条件导出全部**。前端不需要把几千条 id 都拼出来。

**第四步，导出文件的首列从"任务 id"改成"序号"。**

```ts
id: item.taskId            →     id: index + 1
```

运营拿到 Excel 是给人看的，任务 id 是一串很长的数字，序号 1、2、3 才符合直觉。

### 另一个小问题：全选删除后再创建

`b49992b0`：全选状态下把所有词条都删光，再创建新的，列表却还处于"全选"状态。原因是 `isCheckedAll` 没复位。修复是**查询结果为空时把 `isCheckedAll` 置回 false**。

### 最终结果

三个导出现象都消失；全选导出走后端、按筛选条件出全量；序号替代了任务 id。

### 一条链

1. 运营筛选出一批词条，点表头全选。
2. 前端记下"这是全选"，翻页时自动补选新页的行，导出时把筛选条件和空 id 数组一起发给后端。
3. 后端按条件导出全部，前端把返回的数据写成 Excel 下载。

### 60 秒版

> 运营反馈导出有三种不对：没勾选只导出一条，全选只导出第一页，筛选后还是导全量。原因是表格的全选只管当前页，运营想的是"我筛出来的全部"。
> 我做了三件事：记住当前是不是全选状态，翻页时把新页的行并入选中；把每次的查询条件存起来；导出时全选就传空 id 加筛选条件，让后端按条件导全量，不在前端拼几千个 id。顺手把导出首列从任务 id 改成序号，因为这份 Excel 是给运营看的。

### 边界

- "全选导全量"是**前后端约定**：前端传空数组，后端理解为"按条件导全部"。这个约定是联调时定的，不是前端单方面实现。
- 全选后单击某一行取消勾选，会退出全选状态（`isCheckedAll` 置 false），这是**有意设计**，也是一个交互上的取舍。
- 没有性能数据，不报"支持多大数据量导出"。

## 三、批量创建：多关键词拆分与结果提示

**什么时候讲：** 问"批量操作怎么设计 / 部分失败怎么处理"。
**证据：** `89da113d`（11-27）、`b49992b0`（11-28）、`8d775d89`（12-30）。

### 背景

运营一次想创建很多词条，比如一个创建框里粘贴 50 个关键词。如果一次性提交，**只要有一个词不合法，后端可能整批拒绝**，运营只知道"创建失败"，不知道哪个词的问题。

### 方案：逐个创建，汇总结果

召回页里创建框的关键词是"一行一个"。我把提交改成：**按换行拆成数组，一个词一个词地调创建接口，最后汇总成功数和失败数。**

```ts
const queryWordsList = value.query_words.split('\n');
let successCount = 0, failCount = 0;
for (const element of queryWordsList) {
  const res = await createRecallGuildConfigApi({ task: { queryWords: [element], ... } });
  if (res?.msg) failCount += 1; else successCount += 1;
}
message.success(`任务执行成功，成功${successCount}个，失败${failCount}个`);
```

`b49992b0` 再补一步：**创建结束后显示失败的任务名**，运营能直接知道哪几个词没成功。

### 取舍：为什么逐个而不是并发

用 `for ... await` 是**串行**的。这样做的原因是：后端对同一批词可能有冲突校验和顺序依赖；并发会让失败原因对不上词。代价是词越多越慢。这是一个有意的取舍，**没有做并发控制或进度条**。

### Doc 插入的批量创建（垂搜迁移里，12-16 ~ 12-30）

另一处批量是干预配置里的"批量创建 Doc 插入任务"，用 Excel 上传：

1. 运营下载模板（`fb6ed77f`），表头：任务名称、干预页面、干预 tab、干预模块、干预搜索词、插入位置、doc_id、生效时间、备注、白名单账号。
2. 上传后，**前端用 `xlsx` 在浏览器里解析**，把每一行转换成一个完整的任务对象（页面、模块、搜索词、起止时间、doc 列表、tab、白名单……）。
3. 点确认，**一次性**把所有任务提交给后端的批量接口。
4. 后端返回 `code === 0` 才算成功，提示用返回的 `msg`（`8d775d89`），成功后刷新列表（`7f9d988e`）。

### 边界：这里有一个没做的校验

前端解析时**没有逐行校验字段是否缺失**，页面上只提示"请严格按照导入模板填写内容，如有内容缺失，则会直接影响对应任务的创建"。也就是**依赖运营按模板填、后端兜底校验**。如果被追问"为什么不在前端校验"，要如实说：当时是把校验交给后端返回错误，**没有做前端逐行校验和错误定位**，这是可以改进的点。

### 60 秒版

> 批量创建我做了两种。召回页是粘贴多行关键词，我按换行拆开，逐个调创建接口，最后汇总"成功几个、失败几个"，并且把失败的词名展示出来，这样运营不用猜哪个词有问题。我选串行是因为后端有冲突校验，并发的话失败原因对不上词。
> 干预配置里的批量创建是 Excel 上传：前端在浏览器里用 xlsx 解析，转换成任务数组一次提交，后端返回统一的结果码。这里我没有做前端逐行校验，是依赖模板说明加后端校验，这个是可以改进的地方。

### 边界

- 串行逐个提交，**词多时慢**，没做进度条和并发。
- Excel 导入**没有前端逐行校验**。
- 冲突校验由后端完成。

## 四、异型卡片支持"频道 tab"配置

**什么时候讲：** 问"配置化页面 / 多选 / 联动怎么做"。
**证据：** `2fec42d0`（2024-11-18）；前身 `79c97119`（2024-09-23）；配套 `d4eaf61f`（11-22）、`2fb8fb19`（12-10）。分支 `feature/lau-guild-tab`，12-12 合并。

### 背景

搜索结果页顶部有一排 tab：全部、频道、群聊、帖子……

**异型卡片**（运营拼出来的那张卡）此前只能配在"全部"这个 tab 下。新需求（2024-11-12 提出）：**让异型卡片也能出现在"频道" tab 里**，并且支持**同时选多个 tab**。

后台这边的工作量是 15 号启动 2 天，大搜后台 19 号启动 1 天，前端和后台暂定 20 号联调。

### 代码逻辑：改了什么

**1. 把"频道 tab"这个选项放开，并改成多选。**

之前（`79c97119`，9 月）的写法：选"网络搜索结果页"时，**专门把频道 tab 从选项里过滤掉**——因为当时还不支持。

```ts
options: propOptions.filter(item => item.value !== Tab.TAB_CHANNEL)   // 以前：隐藏频道 tab
↓
options: propOptions, multiple: true                                  // 现在：全部放开，可多选
```

**2. 数据结构从"单个 tab"改成"tab 数组"。**

这是改动里**最容易漏的一环**：下游所有读写 tab 的地方都要一起改。

| 位置 | 以前 | 现在 |
|---|---|---|
| 提交时 | `tabs: [params.tabs]`（把单值包成数组） | `tabs: params.tabs`（本来就是数组） |
| 编辑回填 | `tabs: parseInt(data.tabs.join())`（把数组拍扁成一个数字） | `tabs: data.tabs`（直接用数组） |
| 详情展示 | 只取 `tabs[0]` 的名字 | 遍历所有 tab，名字用「、」拼接 |

**3. 干预配置里的"频道 tab + 排序干预"，限制可选的业务 id。**

频道 tab 下的排序干预，运营要指定"某一批业务 id 的顺序"。可选的业务 id 不是随便填的，我新建了 `constants/meddle.ts`，把允许的业务 id 列成白名单：

```ts
// 干预页面 = 网络搜索结果页，干预 Tab = 频道 tab，干预模块 = 排序干预
export const BIZ_ID_ARR = [20, 21, 94, 75, 76, 77, 81, 82, 83, 84, 85, 79, 80, 96];
```

排序的内容配置里还有几个交互细节：

- **已选过的业务 id 在下拉里置灰**，避免同一个业务重复添加。
- **如果所有业务 id 都选完了，"添加"按钮不再生效**（`unSelectedIndexs` 为空直接 return）。
- **业务 id 不是 20 或 21 的，插入条数默认固定为 1**，只有 20、21 允许配置多条。

**4. 查询项同步升级（`d4eaf61f`）。** 干预配置和卡片配置的查询区增加了"干预 tab""干预页面"的多选，以及"生效时间""任务状态"，方便运营筛选。

### 关于"tab 维度冲突校验"

群里还讨论了一个规则：**同一个搜索词，不能在"全部 tab"和"频道 tab"配不同的卡片**。这个校验是**后端做的**，前端没有提交涉及它（我在仓库里检索"冲突"，零命中）。前端只负责把多选的 tab 传给后端，并展示后端返回的冲突提示。

### 最终结果

异型卡片可以在"频道"等多个 tab 下配置，创建、编辑、详情、查询四处都支持多选；频道 tab 的排序干预有业务 id 白名单和重复限制。

### 60 秒版

> 异型卡片原来只能配在"全部"这个 tab 下，需求是让它也能出现在"频道"tab，并且一张卡可以同时选多个 tab。
> 看起来只是把下拉框放开成多选，但数据结构从单值变成数组，提交、回填、详情展示三处都要一起改，漏一处就会出现回填成一个数字或者详情只显示第一个 tab。
> 频道 tab 下的排序干预我加了业务 id 白名单，已选的 id 在下拉里置灰，避免重复添加。
> 同一个搜索词在不同 tab 配不同卡片的冲突校验是后端做的，前端只负责传数组和展示提示。

### 边界

- **冲突校验是后端的**，不要说成自己做的。
- 业务 id 白名单是常量写死的，**加新业务要改代码发版**，没有做成后端下发。
- 没有"支持多少 tab"的数据。

## 五、热议话题：会"变形"的动态表单，和一个 memo 比较函数引出的 bug

> 这是你**最值得讲深度**的一条：有业务背景、有自己的提交、有完整的演变链，还能用真实代码复现。
> 通用原理（memo、useMemo、引用稳定性）见 [`../job-search/面试问答合集/React-memo与useMemo踩坑复盘.md`](../job-search/面试问答合集/React-memo与useMemo踩坑复盘.md)，本章只讲这个案例本身。

**什么时候讲：** 面试官问"你做过的最复杂的表单 / 配置化页面"、"遇到过什么渲染问题"、"memo 用过吗，踩过什么坑"。
**证据：** `2ac43594`（2024-10-21，动态配置）→ `374bb553`（10-22）→ `bb2f3fd9`（10-23）→ `35044e42`（10-30，修复）。分支 `feature/lau-hot-topic`，MR !4（11-04 合并），分支内你有 14 个提交。

### 先讲业务：热议话题卡片是什么

用户在 QQ 搜"奥运"这类词，结果页顶部可以出现一张"**热议话题**"卡片：左边一个图标，中间是标题，下面列几条相关帖子。运营要在后台决定三件事：

1. **标题点进去跳到哪**：要么是一个固定链接，要么是"网络搜索话题承接页"（一个按话题聚合的页面）。
2. **卡片里的帖子从哪来**：运营自己指定几条帖子，或者取这个话题下"最热"的、"最新"的，或者用承接页的。
3. 图标、标题这些外观。

### 为什么表单必须是"动态"的

三件事里，第 1、2 件的**选项决定了还要填什么**：

| 运营的选择 | 还需要多填的字段 |
|---|---|
| 标题跳转 = 固定链接 | android 链接、ios 链接 |
| 标题跳转 = 话题承接页 | 话题名称 |
| 内容来源 = 运营配置 | 3 个帖子 id |
| 内容来源 = 热门 tab / 最新 tab | 话题 id |
| 内容来源 = 网络承接页 | 话题名称（来源） |

如果把所有字段**一次性全摆出来**，会有两个问题：没选中的字段会以空值被提交；运营也分不清当前选项到底该填哪几项。所以需求是：**两个下拉框一变，下面的输入框随之增减。**

### 代码逻辑一：schema 从"对象"变成"函数"

项目里所有模板的表单，都是用一份 `schema` 描述出来的，里面有两样东西：

- `editData`：**字段清单**，画几个输入框、什么类型、必不必填。
- `defaultData`：**字段的初始值**，每个输入框里默认填什么。

其他 8 个模板的 schema 是一个**固定对象**。热议话题改成了一个**函数**，参数就是两个下拉框当前选的值：

```ts
hotTopicSchema(dumpMethod, indexType, topicName)  // 返回 { editData, defaultData }
```

函数内部先放"永远有"的五项（图标链接、图标 token、标题、标题跳转方式、内容来源），再按参数往里**插入**对应字段：

```ts
if (dumpMethod === 固定链接) {
  result.editData.splice(4, 0, 安卓链接字段, iOS链接字段);   // 字段清单里多两项
  result.defaultData.androidTarget = '';                       // 初始值里多两个键
  result.defaultData.iosTarget = '';
}
if (indexType === 运营配置) {
  result.editData.splice(末尾, 0, 帖子id字段);
  result.defaultData.feedIds = ['', '', ''];
}
```

**注意：字段清单和初始值是同步变化的**——多一个输入框，初始值里就多一个键。这一点后面很关键。

另外，这个模板在注册表里标了 `isDynamic: true`，**9 个模板里只有它有这个标记**。父组件看到这个标记，就知道"要用函数的方式去取 schema"，而不是直接读对象。

### 代码逻辑二：数据怎么流动

整个页面是四层：

```
任务壳（抽屉）→ TemplateConfig（左表单右预览）→ FormRender（按 schema 画表单）
```

运营改一个下拉框之后，发生的事：

1. `FormRender` 里的表单触发"值变化"，把全部表单值通过 `onChange` 交给 `TemplateConfig`。
2. `TemplateConfig` 把 `dumpMethod`、`indexType`、`topicName` 这三个值**存进自己的 state**（这三个值是"决定表单长什么样"的"开关"）。
3. `TemplateConfig` 重新渲染，**用新的开关值重新调用 `hotTopicSchema(...)`**，得到新的字段清单和初始值，再传给 `FormRender`。
4. `FormRender` 应当据此**多画或少画几个输入框**。

第 4 步就是出问题的地方。

### 代码逻辑三：FormRender 为什么加了 memo

`FormRender` 外面包了一层 `React.memo`，并带了一个**自定义比较函数**：

```ts
export default React.memo(FormRenderComponent, (prevProps, nextProps) => {
  return isEqual(prevProps.defaultData, nextProps.defaultData);   // 返回 true = 不用重新渲染
});
```

**这个 memo 不是你加的**：它最早是 `bc9f2e3e`（2024-07-29，jackqqxu）为了压住一个"渲染死循环"加的（当时的写法是 `===`）。你在 `374bb553`（10-22）把 `===` 改成了 `isEqual` 深比较。这两件事是先后发生的，**不是同一个人、同一个目的**。

### 问题：编辑已有任务时，切换下拉框，新字段出不来

**现象：** 新建任务时一切正常；但**打开一个已保存的任务进入编辑，切换"内容来源"，下面的输入框不变。**

**原因（这一段我用真实代码跑过，不是推断）：**

传给 `FormRender` 的 `defaultData` 是这样拼的：

```ts
defaultData = { ...schema的默认值, ...已保存的数据 }     // 后面的覆盖前面的
```

- **新建态**：已保存的数据是空的，`defaultData` 完全来自 schema。运营切换"内容来源"，schema 默认值里多出 `feedIds` 之类的键，`defaultData` 变了，比较函数判断"不一样"，放行重渲染。✅
- **编辑态**：已保存的数据是**后端回填的完整数据**，字段齐全，会把 schema 默认值**整个盖住**。运营切换"内容来源"，schema 变了，但覆盖之后的 `defaultData` **内容完全一样**。比较函数判断"一样"，**拦下重渲染**，新输入框画不出来。❌

我用修复时点的**真实 schema 代码**做了实验（把 TS 源码剥掉类型，用 node 跑）：

| 场景 | 字段清单变化 | `defaultData` 深度相等？ | 修复前 memo 是否拦下 |
|---|---|---|---|
| 新建态，内容来源 未选 → 运营配置 | 多出 `feedIds` | 否 | 不拦（正常） |
| 编辑态，内容来源 运营配置 → 热门 tab | `feedIds` → `topicId` | **是** | **拦下（bug）** |

**一句话原因：比较函数只比了"值"（`defaultData`），没比"字段清单"（`editData`），而这个表单变的恰恰是字段清单。**

这也解释了三个现象：

- **只有热议话题出问题**：只有它的字段清单会变，其他 8 个模板的清单是固定的。
- **只有编辑态出问题**：已保存的数据盖住了默认值，掩盖了变化。
- **没有任何报错**：memo 返回 `true` 是"正常的跳过渲染"，React 不会警告。

### 方案：新增 `templateDefault`

`35044e42`（10-30）的做法：父组件**多传一个 prop**，内容是"**纯 schema 的默认值，不掺已保存的数据**"，比较函数优先比它。

```tsx
<FormRender
  editData={editData}
  defaultData={{ ...defaultData, ...data }}   // 给表单当初始值
  templateDefault={defaultData}               // 新增：只给 memo 比较用
/>

React.memo(FormRenderComponent, (prev, next) =>
  prev.templateDefault
    ? isEqual(prev.templateDefault, next.templateDefault)
    : isEqual(prev.defaultData, next.defaultData)
);
```

之所以有效，是前面提到的那个性质：**字段清单变，初始值里的键也同步变**。`templateDefault` 没有被已保存的数据覆盖，所以字段清单一变它必变，memo 放行。

同一个提交还补了几处配套改动，防止切换时数据错乱：

- `value.data?.dumpMethod && setDumpMethod(...)`：**只有新值存在才更新"开关"状态**，避免别的模板的表单触发 `onChange` 时，把热议话题的开关刷成 `undefined`。
- `topicNameSource = topicName || topicName(旧值)`：兜底，避免话题名称被清空。
- 同时清理了预览组件里已经不用的"标题跳转类型"展示。

### 这个方案够不够好：我跑了穷举

之前我只是读代码，**怀疑** `templateDefault` 是"间接信号"，可能漏掉某些情形。这次我把两个下拉框的所有取值组合（3 × 5）全部跑了一遍：

> 字段清单不同的组合共 **102 对**，其中 `templateDefault` 相同、会被漏掉的 **0 对**。

所以结论要这样讲才准确：

- **对当前的 schema，`templateDefault` 是够用的**，没有漏网。
- 它之所以够用，靠的是一个**隐含的约定**："每多一个输入框，`defaultData` 里就多一个键"。这个约定**没有写在任何地方，也没有测试保护**。将来如果有人加了一个"只改字段清单、不改初始值"的选项，这个方案就会静默失效，而且和这次一样不会有任何报错。
- 更直接的做法是在比较函数里**把字段清单本身也比上**（`isEqual(prev.editData, next.editData)`），或者**给组件加 `key`**，下拉框一变整张表单直接重建。后者最简单，代价是会丢掉运营已经输入但还没同步的内容，需要权衡。

### 最终结果

编辑态下切换下拉框，输入框能正确增减；热议话题 11-04 合并上线。后续你又在 `9cadf9ec`（11-20）里让**非动态的模板**在编辑态不再被 schema 默认值覆盖（`each?.data === null || isDynamic ? { ...defaultData, ...data } : { ...data }`），把"动态 / 非动态"的处理分开。

### 一条链（给听的人）

1. 运营在热议话题里，切换"内容来源"。
2. 前端用新的选项重新生成表单描述：字段清单变了。
3. 但左边表单组件有一个"值没变就不重渲染"的优化，而编辑态下已保存的数据把默认值盖住了，值确实没变，于是优化把更新拦下，新输入框画不出来。
4. 我多传了一个"纯 schema 默认值"给这个优化比较，它不会被已保存的数据盖住，选项一变它就变，更新就放行了。

### 60 秒版

> 热议话题是搜索结果里的一张卡片，运营要配标题跳去哪、里面的帖子从哪来。这两个选项决定还要多填什么：选固定链接要填安卓和 iOS 链接，选运营配置要填三个帖子 id。所以我把这个模板的表单做成动态的：描述表单的 schema 从一个对象改成函数，参数就是两个下拉框的值。
> 上线后发现编辑已有任务时，切换下拉框新输入框不出来，新建却正常。原因是左边表单组件早先为了压一个渲染死循环加了 memo 的自定义比较，它只比较"初始值"。编辑态下后端回填的已保存数据会把 schema 默认值整个盖住，所以字段清单变了、初始值却没变，比较函数判断"不用更新"，把渲染拦了。而且这种拦截不会报任何错。
> 我的做法是多传一个不掺已保存数据的 schema 默认值，让比较函数优先比它。我事后用真实 schema 把所有选项组合跑了一遍，当前没有漏网，但它依赖"多一个输入框初始值里就多一个键"这个没写下来的约定。更稳的做法是把字段清单也纳入比较，或者直接给组件加 key。

### 常见追问

| 追问 | 答法 |
|---|---|
| 为什么不直接去掉 memo？ | 这个 memo 和父组件的 `isEqual` 守卫一起压着一个渲染死循环。守卫才是真正切断循环的点，memo 只是辅助。去掉前要先确认循环确实被守卫挡住，当时没有测试，所以选择了补比较条件而不是删除 |
| 为什么用 `templateDefault`，不直接比 `editData`？ | 坦白讲：当时是找到一个"碰巧会随选项变化"的值，改动最小。现在回头看，直接比字段清单或加 `key` 更稳。我跑过穷举，当前不会漏，但它依赖一个隐含约定 |
| 浅比较和深比较怎么选？ | 浅比较快但依赖引用稳定；深比较慢，对大对象有开销，但这里表单数据很小。我从 `===` 改成 `isEqual` 是因为父组件每次都会拼出新对象，`===` 永远不相等，memo 等于白加 |
| 你是怎么定位的？ | 先发现"新建正常、编辑才不行"，对比两种状态下传给表单的 `defaultData`，发现编辑态被已保存数据盖住了 |
| 死循环是怎么回事？ | 表单值变化触发 `onChange`，父组件 `setState` 重渲染，又把值传回表单，形成回路。切断点是父组件里"新旧内容一样就不再 `setState`"的守卫。**这个机制是我读代码推断的，没有运行复现**，要说"我分析认为" |

### 边界

- **`bc9f2e3e` 的 memo 比较函数是 jackqqxu 加的，不是你。** 你做的是 `2ac43594`（动态 schema）、`374bb553`（`===` 改 `isEqual`）、`35044e42`（`templateDefault`）。
- `374bb553` **早于** `bb2f3fd9`（10-22 对 10-23，已用 `merge-base` 核对）。所以**不能说**"我把 `===` 改成 `isEqual` 是为了配合新的传参方式"。改深比较的真实动机仓库里没有记录，**不要编**。
- **编辑态下"值被盖住、清单变化、memo 拦下"这条因果链**，我用真实 schema 代码复现过，可以讲得确定；**但没有在浏览器里复现过完整页面**，所以"运营看到的现象"是根据你当时的提交说明和群里描述，不是我亲眼看到的。

## 六、干预搜索词的英文大小写兼容

**什么时候讲：** 问"你怎么做小而独立的改动 / 怎么拆分发布"。
**证据：** `1559c48a`、`9518c577`、`9928618b`（均 2024-11-19）。分支 `feature/lau-case-compatibility`，MR !11。

### 背景

用户搜 `QQ` 和搜 `qq`，应不应该命中同一条干预？之前没有这个开关。运营要求**可选：忽略大小写 / 不忽略大小写**。

这个能力**早就开发完了**，但和另一个需求"联想直达页的审批流"的代码**混在同一批改动里**。审批流还没准备好发布，连带这个小功能也被压着。2024-11-19 群里讨论"能不能单独拆出来发"。

### 方案：把它单独拆成一个分支

我把大小写相关的改动**单独摘出来**，开了独立分支 `feature/lau-case-compatibility`，合并时只有 1 个提交。被注释掉的审批流相关代码（`getApprovalReasons` 等）留在文件里没有删，原因是**只拆分，不顺手改别的**。

### 代码逻辑

前端只增加了**一个配置项**：

```ts
export const UPPER_LOWER_OPTIONS = [
  { label: '不忽略大小写', value: 1 },
  { label: '忽略大小写',   value: 0 },
];
```

贯穿四个环节：

| 环节 | 做法 |
|---|---|
| 创建表单 | 增加"是否忽略大小写"下拉 |
| 提交 | 写入任务的 `extends` 字段：`{ is_upper_lower: 1 或 0 }` |
| 编辑回填 | 从 `extends` 读出来，用 `camelizeKeys` 转成驼峰给表单用 |
| 详情展示 | 用 `UPPER_LOWER_OPTIONS` 把 0/1 换成文字 |

**默认值设为"忽略大小写"**（`9518c577`）：创建、编辑、复制三个入口都统一成 0。为什么要专门处理编辑和复制？因为**老任务的 `extends` 里没有这个字段**，回填出来是 `undefined`，表单会是空的，所以要补默认：

```ts
isUpperLower: editData.isUpperLower !== undefined ? editData.isUpperLower : 0
```

另一个同日小改动 `9928618b`：任务列表里"发布任务"按钮之前被注释掉了，这次放出来。

### 最终结果

大小写开关独立拆出发布；老数据不会因为缺字段而回填成空；群里说"前端只需加配置项"，和代码一致。

### 60 秒版

## 七、垂搜干预迁移：Doc 插入、批量上传、模板下载

**证据：** `9a22aecf`（2024-12-09）起，到 `8d775d89`（12-30）。这段时间在 `meddle-config`、常量、类型、任务壳几个位置，你有 12 个提交（按标题去重），再加 `af820353` / `c2a2f2c9`（2025-01-10）两个预览修复。分支 `feature/lau-vertical-search-fix`，MR !22（01-14 合并）。

### 背景

"垂搜"是 QQ 搜索里按内容类型划分的垂直搜索：**帖子搜索、群聊搜索、频道搜索**。这些垂搜以前的干预配置在**另一套后台**里，需求是**迁移到这个统一后台**，并新增一种干预：**Doc 插入**（把指定的内容 id 插到搜索结果指定位置）。

### 代码逻辑

**1. 扩展枚举。** 新增三个 tab：`TAB_FEED_SEARCH`（帖子搜索）、`TAB_CHAT_SEARCH`（群聊搜索）、`TAB_CHANNEL_SEARCH`（频道搜索），新增干预模块 `UNIT_DOC_INSERT = 12`。

垂搜迁移时又增加了"帖子 / 群聊 / 频道搜索 tab 下 Doc 插入用 `doc-content-config`"的分支。

```ts
options: Object.values(PAGE_OPTIONS).filter(item => item?.module && item.value !== Page.PAGE_DIRECT)
```

**5. 批量创建**：见第三章。

**6. 预览的两个小修复（2025-01-10）：**

- `af820353`：异型卡片预览里原来会渲染**所有 tab**，现在新增 `templateTab` 只保留"全部"。因为异型卡片预览的目的是看卡片本身，不需要展示一排真实的 tab。
- `c2a2f2c9`：预览 tab 栏内容太多会**溢出**，加 `max-width: 375px; overflow: auto; white-space: nowrap`（375 是手机宽度）。

### 一个踩过的坑：`pos` 为 0 被当成"没填"

`394b6c27`（12-23）。群里反馈：**复制一个插入位置为 0 的干预任务，提示"位置和 doc_id 必填"**。

原因是校验写成了：

```ts
val.every(item => !!item.pos && !!item.docId)
```

JavaScript 里 `!!0` 是 `false`——**数字 0 被当成了"没填"**。而位置本来就是**从 0 开始**，0 是最常见的合法值，也就是"插到第一位"。

修复：

```ts
val.every(item => (!!item.pos || item.pos === 0) && !!item.docId)
```

同一个提交里还把组件默认值的字段名从 `index/word` 改成 `pos/docId`，因为字段名和后端协议不一致。

### 最终结果

## 八、Doc 维度屏蔽（以及我自己写错的两处）

**什么时候讲：** 问"你写过什么 bug / 怎么复盘"。这条**最适合讲诚实的细节**。
**证据：** `f8831b5d`（2025-01-14）、`4e51e4fc`、`7c592689`、`f8d2ba95`（01-15）、`e3ac7676`（02-08）、`a37a092e`（02-12）。分支 `feature/lau-doc-dimension-0114`，MR !23（02-25 合并）。

### 背景

在垂搜新增"Doc 插入"后，紧接着有一个相反的需求：**把某些 doc 从搜索结果里屏蔽掉**，按 doc_id 维度。群里 2025-01-09 提出，02-24 完成并安排发布。

### 代码逻辑

比 Doc 插入简单：屏蔽不需要位置，只要一串 doc_id。

```tsx
[Unit.UNIT_DOC_SHIELD]: {
  label: 'Doc ID', name: 'docIds',
  formBlockComponent: () => <Textarea placeholder="输入需要屏蔽的Doc_ID, 一行一个" />,
}
```

提交时按换行拆开：

```ts
doc_shield_infos: stringWithLineToArray(params.docIds).map(doc_id => ({ doc_id }))
```

02-08 后台同事 kevinezeng 补了一个要求：**`detail` 里要透传 `query_words`**（干预搜索词）。我给 Doc 插入和 Doc 屏蔽的创建参数都补上了 `query_words`（`e3ac7676`）。02-12 又补了 `tabs`（`a37a092e`）：单个创建取表单的 tab，批量创建则从 Excel 的"干预 tab"列映射成枚举值。

### 我自己写错的第一处：回填用错了字段（`f8831b5d` → `4e51e4fc`）

首版的**编辑回填**写成了：

```ts
docIds: arrayToStringWithLine(detail?.docInterposes.map(item => item.docId))
```

`docInterposes` 是 **Doc 插入**的数据字段，屏蔽的数据字段是 `docShieldInfos`。我把屏蔽当成插入来读，复制粘贴漏改。表现是**编辑或看详情时，doc_id 回填是空的**。第二天（01-15）`4e51e4fc` 改成 `docShieldInfos`，同一天又补了可选链 `?.`，防止 `docShieldInfos` 缺失时直接报错（`f8d2ba95`）。

### 我自己写错的第二处：三元表达式的优先级（`99171bd2` → `f8d2ba95`）

这是群里"**任务详情的干预模块显示不对**"反馈的原因。12-20 我为了让详情里显示"Doc 插入"，写了：

```ts
units: PAGE_OPTIONS[...]?.label || units[0] === Unit.UNIT_DOC_INSERT ? 'Doc插入' : '-'
```

**`||` 的优先级比 `? :` 高**，所以它被解析成：

```ts
(label || units[0] === DOC_INSERT) ? 'Doc插入' : '-'
```

我验证过行为：

| 情况 | 实际显示 | 应该显示 |
|---|---|---|
| 有 label（比如"排序干预"） | **Doc插入**（错） | 排序干预 |
| 没 label 且不是 Doc 插入 | `-` | `-` |
| 没 label 且是 Doc 插入 | Doc插入 | Doc 插入 |

也就是：**所有有名字的干预类型，在详情里都被显示成了"Doc插入"**。

修复（`f8d2ba95`）用括号把条件包起来，并顺手加上了 Doc 维度屏蔽的名字：

```ts
label || (units[0] === DOC_INSERT ? 'Doc 插入' : units[0] === DOC_SHIELD ? 'Doc 维度屏蔽' : '-')
```

### 最终结果

Doc 维度屏蔽 2025-02-25 合并上线；创建、编辑、详情、批量创建都带上了 `query_words` 和 `tabs`；两处自己引入的 bug 在一到两天内修掉。

### 60 秒版

> Doc 维度屏蔽是和 Doc 插入相反的需求：按 doc_id 把某些内容从结果里屏蔽掉。我复用了干预配置的框架，加了一个 Textarea，一行一个 doc_id，提交时拆成数组。后台同事后来要求 detail 里透传搜索词和 tab，我也补上了。
> 这个过程里我自己写错过两处。一处是编辑回填时读错了字段，把屏蔽当成插入去读，导致回填为空，第二天发现就改了。另一处是详情里的三元表达式，我写了 `a || b ? x : y`，没注意 `||` 优先级高于三元，结果所有有名字的干预类型在详情里都显示成了"Doc 插入"。我用括号改好了。这之后我写带 `||` 的三元一定加括号。

### 边界

## 十一、两个"组合卡"问题（和第五章同一个 memo，另一半）

**什么时候讲：** 讲完第五章后，面试官继续追问"这个 memo 还引出过别的问题吗"。**这一章是第五章的续集，不要单独先讲。**
通用原理和替代方案见 [`../job-search/面试问答合集/React-memo与useMemo踩坑复盘.md`](../job-search/面试问答合集/React-memo与useMemo踩坑复盘.md)。

### 和第五章的关系：同一个比较函数，漏掉了两样东西

第五章里的 `FormRender` 比较函数，是**白名单**：它只比较了你写进去的属性。漏掉的属性，变了也不会触发更新。

| | 比较函数漏掉了什么 | 造成的现象 |
|---|---|---|
| 第五章 | **字段清单**（`editData`） | 编辑态下，切换下拉框，新输入框不出现 |
| 本章 | **回调函数**（`onChange`） | 一次选多个模板时，编辑其中一个，另一个之前填的内容会丢 |

两者都是"该更新的没更新"，所以放在一起讲能给面试官一个完整印象：**自定义比较函数不是性能优化的小事，漏一个属性就是一个业务 bug。**

### 背景（业务版）

运营在异型卡片里**一次选多个模板**，比如"通用头部 + 热议话题 + 纵向列表"拼成一张卡。每个模板有一块自己的表单，右边是合成后的预览。

两个现象：

- 编辑其中一个模板的内容，**另一个模板之前填的内容丢了**。
- 新建一个任务，**预览里带着上一个任务的内容**或预览闪一下。

### 为什么会丢：回调里的"当前数据"是旧的

父组件给每个表单传了一个回调：

```tsx
onChange={(value) => handleOnChange({ templateId, data: value }, index)}
```

这是**每次渲染都新建的函数**，而且它"记住"了创建那一刻的 `editData`（整张卡所有模板的数据）。

因为比较函数没把这个回调算进去，表单被拦下重渲染之后，**手里一直拿着旧的那一个回调**，里面记着的 `editData` 就是旧快照。于是：

```
选了 A、B 两个模板
 编辑 A → 父组件的 editData 更新为 [A', B]
 但 B 的表单被 memo 拦住，手里的回调里还是旧的 editData = [A, B]
 编辑 B → 回调拿旧的 [A, B]，替换第二项，得到 [A, B'] → A 的修改被盖掉
```

### 方案与它留下的新问题

`5db7d836`（11-21）：用一个全局变量 `window.renderData` 当作"实时副本"，回调里改读它，绕开旧快照。要求**每次进入编辑时手动置空**。

新问题：**新建任务的入口漏了置空**，残留了上一个任务的数据，预览跳变或串卡。`fc3f656f`（2025-04-15）补了一行 `window.renderData = null`。

### 60 秒版

> 接着刚才那个 memo：它的比较函数除了漏掉字段清单，还漏掉了回调函数。异型卡片可以一次选多个模板，每个模板一块表单。我发现编辑一个模板时，另一个模板之前填的内容会丢。原因是表单被 memo 拦住后，手里一直拿着旧的回调，回调里记着旧的整体数据，编辑第二个模板就把第一个的修改盖掉了。
> 当时我用一个全局变量绕过，但全局变量要靠人记得清理，新建入口漏了，所以又串了数据。后来补了一行置空，运营回归后不再复现。事后我觉得更稳的做法是用组件内的 ref 保存最新值，再给组件加 key，这样任务一换整个组件重建，不需要人去清理。

### 边界

- 这条的**根因**（回调过期）是我读代码得出的，**没有运行复现**。第五章的因果链我用真实 schema 跑过，这一条没有。
- `bc9f2e3e`（最早加 memo 比较函数的提交）是 jackqqxu 做的，**不是你**。
- 全局变量方案是权宜之计，面试里不要把它讲成"最佳实践"，要讲成"当时的绕行，以及事后怎么改更好"。
