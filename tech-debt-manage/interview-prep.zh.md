## 🏗️ 架构（architecture）— 2 题

### Q1. 菜单为什么不写死，专项列表是在什么时候变成路由的？

> 来源：`tp-01` · scope: fullstack · tech-debt-manage · 难度: 中级

#### 知识点

| 名称 | 等级 | 为什么会问 |
|---|---|---|
| 动态路由 | 必须掌握 | 菜单必须和后台专项列表一致。 |
| React.lazy | 必须掌握 | 专项页面按访问再加载。 |
| 顶层 await | 加分项 | 它决定菜单何时就绪，也决定失败时页面能否渲染。 |

#### 三档回答

**🟢 一句话**：菜单来自专项接口。路由模块加载时请求列表，再按 moduleId 懒加载页面。

**🔵 标准**（默认）：

专项是后台配置的，前端写死菜单会漏掉新专项。projects.ts 在模块顶层请求 getProjectListNew。返回的 projectInfos 进入 createRouter。moduleId 1 到 5 对应扫描、管理、认证、算力和容灾页面，99 走通用模板。通用模板除了首页，还有导入页和配置页。没有权限的项不会放进菜单。页面组件用 React.lazy，避免把所有专项打进首屏。列表请求失败不会生成空菜单，而是切到加载失败页。

<details><summary>🔴 深挖（点击展开）</summary>

我接到的需求是一个后台管很多专项，而且专项还会增加。如果每个专项写一条静态路由，发布菜单就要改前端。所以路由表改成接口结果。文件顶部用 await 取列表，是为了菜单和路由在应用渲染前就定下来。createRouter 按分类数组决定是一级菜单还是子菜单。只有一层名字时，直接生成 home 路由。通用模板再追加 importing 和 setting 两条隐藏路由，导入和配置不出现在侧栏。componentMap 找不到类型时落到 More 页面，避免未知 moduleId 直接白屏。isAuthed 为假的专项不生成可访问路由。列表为空或请求抛错时，我改成错误路由，并把地址切到 /project/error。这样使用者看到的是加载失败，而不是一个空壳菜单。懒加载放在路由对象上，用户点开某个专项才下载对应页面。分类数组决定菜单层级。一层名字生成叶子路由，多层名字生成可展开的父级。子菜单的 value 必须唯一，我修过重复 value 让两项同时展开的问题。未知 moduleId 进 More 页面，这样后台先加类型时前端不会直接崩溃。这一点我能在仓库里指到具体文件，不会把同事后来的移动端适配算进自己的范围。

</details>

#### 补齐方案

- 📚 必读
  - [ ] React Router 嵌套路由
  - [ ] React.lazy 与 Suspense
- 🛠️ 动手
  - [ ] 用一份 JSON 菜单生成两级路由，并给未知类型一个兜底页
- ⚠️ 常见踩坑
  - 接口失败时路由模块抛错，整站没有菜单
  - 隐藏路由忘记标记，导入页出现在侧栏
- 🤔 自测题（合上文档自答）
  - [ ] 如果专项从 10 个变成 100 个，这段路由还要改什么？
- ⏱️ 预估学习时长：**1 天**

  > isAuthed 为假时不生成可访问菜单。鉴权失败还会在请求层拿到单独的授权地址。

### Q2. 多个专项的列表为什么可以共用一张表？

> 来源：`tp-02` · scope: fullstack · tech-debt-manage · 难度: 中级

#### 知识点

| 名称 | 等级 | 为什么会问 |
|---|---|---|
| 配置驱动界面 | 必须掌握 | 新专项复用交互，只替换列和接口。 |
| 受控分页 | 必须掌握 | 页码和筛选必须一起进入请求。 |
| Redux Toolkit | 加分项 | 查询条件跨页面保留。 |

#### 三档回答

**🟢 一句话**：差异放在配置里。CommonTable 统一管查询、分页、排序和行操作。

**🔵 标准**（默认）：

每个专项的列和筛选项不一样，但列表交互差不多。我把查询项、列和按钮收成 querySet、tableSet、operationSet。页面传入 getListApi。表格内部维护页码、页大小、排序和选中行，请求时带上 page、page_size 和筛选条件。handleQuery 可以在发出请求前改参数。行点击、双击和按钮都有自定义回调，专项自己的弹窗不用复制表格状态。查询条件还会进搜索 store，从详情返回时可以恢复。

<details><summary>🔴 深挖（点击展开）</summary>

一开始每个专项都有自己的表格，分页和重置逻辑很快重复。我把稳定的交互收进 SelectTable，把业务留在配置和回调里。查询区用 SearchForm 渲染配置，不在表格里写死字段。getListData 组装分页参数。页面如果传入 handleQuery，就用它处理筛选项，否则直接展开 filter。排序走表格自己的 sort 状态，翻页时带上当前排序。多选由 isMultiple 打开，checkValid 让页面拒绝不合法的行。fetchAllAtOnce 留给需要一次拿完整结果再在前端处理的统计场景，普通列表仍按页请求。选中行通过 onSelectChange 交出去，父页面做批量操作。这样新增一个专项时，主要工作是写列配置和接口函数，而不是再做一套分页。代价是配置对象变大，字段含义必须在 types 里说清楚。重置按钮会清空 SearchForm，并把页码放回第一页，否则旧筛选会留在下一次请求里。列宽变化通过 handleResizable 交回页面，页面可以记住运营同学拖过的宽度。rowKey 由调用方指定，避免不同专项的主键名字不一样时选中状态串行。这一点我能在仓库里指到具体文件，不会把同事后来的移动端适配算进自己的范围。搜索条件存在 store 里，详情页返回后还要用同一份条件重新请求。

</details>

#### 补齐方案

- 📚 必读
  - [ ] TDesign Table 分页与排序
  - [ ] 受控组件和状态提升
- 🛠️ 动手
  - [ ] 做一个三列配置表，支持服务端分页和返回详情后恢复筛选
- ⚠️ 常见踩坑
  - 页码和筛选各存一份，重置后请求仍带旧条件
  - 把业务判断写进通用表格，下一个专项无法复用
- 🤔 自测题（合上文档自答）
  - [ ] 配置化表格和每个页面各写一张表，你怎么选？
- ⏱️ 预估学习时长：**1 天**

#### 追问（面试官深挖向）

- ⚖️ **如果某个专项的操作不能用配置表达呢？**（trade-off）
  > 保留 customBtnCallback 和 customOptCallback。配置覆盖共性，回调处理弹窗、导入这种专项逻辑。

## 🧩 功能（feature）— 1 题

### Q1. 批量导入导出是怎么接进通用专项的？

> 来源：`tp-03` · scope: fullstack · tech-debt-manage · 难度: 中级

#### 知识点

| 名称 | 等级 | 为什么会问 |
|---|---|---|
| SheetJS | 必须掌握 | 导入和导出都经过工作簿，而不是手写 csv。 |
| 文件校验 | 必须掌握 | 错误文件不应进入提交接口。 |
| 上传体积 | 加分项 | 网关上限和接口超时不是一回事。 |

#### 三档回答

**🟢 一句话**：导出用 SheetJS 生成 xlsx。导入把文件读成 JSON，通用专项再校验后提交。

**🔵 标准**（默认）：

通用专项的 moduleId 是 99，路由里单独有 importing 页面。导出调用 downloadJsonToXlsx 或 downloadArrayToXlsx，把当前数据写进工作簿，再转成 Blob 下载。导入用 transformXlSXFileToJson 读取第一个工作表。validateFileFormat 先看扩展名和表头，不通过就不发请求。Nginx 把 client_max_body_size 放到 5000m，避免较大的表格在网关被直接拒绝。导入页是隐藏路由，从列表按钮进入。导入页带专项 id，同一个页面可以服务不同的通用专项。

<details><summary>🔴 深挖（点击展开）</summary>

运营同学要批量改工单，逐行编辑太慢。我把 Excel 收成两个方向。导出时 XLSX.utils 把 JSON 或二维数组转成 sheet，bookSST 关闭，优先生成速度。workbook2blob 用 binary 写出，再包一层 Blob。openDownloadDialog 创建对象 URL，用 a 标签触发下载。导入时 FileReader 读成二进制，XLSX.read 解析，sheet_to_json 得到行数组，回调交给页面。校验放在上传之后、提交之前。格式不对就停在前端，并提示缺少哪些列。通用模板的导入路由带 idInfo，这样同一个导入页可以服务不同专项。列表页只负责跳转，不把解析逻辑写进 CommonTable。大文件还有两个边界。接口超时现在是 5 秒，超大表可能在浏览器解析完、请求还没返回时被 Axios 取消。另外 5000m 是网关上限，不代表后端和浏览器都适合传这么大的文件。真正的批量导入仍要限制行数。downloadMultiArrayToXlsx 可以一次写多个 sheet，统计和明细不用分成两次下载。导入只读第一个表，避免使用者把说明页也提交进去。解析在浏览器完成，大文件会卡住主线程。所以导入页单独存在，不把这个耗时放进列表页的第一次渲染。这一点我能在仓库里指到具体文件，不会把同事后来的移动端适配算进自己的范围。

</details>

#### 补齐方案

- 📚 必读
  - [ ] SheetJS 读取与写出
  - [ ] Blob 下载
- 🛠️ 动手
  - [ ] 上传一个三列表格，校验缺列并导出当前页
- ⚠️ 常见踩坑
  - 只校验扩展名，不校验表头
  - 对象 URL 创建后从不释放
- 🤔 自测题（合上文档自答）
  - [ ] 为什么不把解析函数放进 CommonTable？
- ⏱️ 预估学习时长：**1 天**

#### 追问（面试官深挖向）

- ⚖️ **导入到一半失败，已写入的数据怎么办？**（reliability）
  > 前端先整表校验，通过后一次提交。接口失败就整批提示重试，不做浏览器里的半成功状态。

## ⚡ 性能（performance）— 1 题

### Q1. 列表为什么有的按页请求，有的一次拉完？

> 来源：`tp-07` · scope: fullstack · tech-debt-manage · 难度: 中级

#### 知识点

| 名称 | 等级 | 为什么会问 |
|---|---|---|
| 服务端分页 | 必须掌握 | 列表规模不受前端内存限制。 |
| 一次拉全量 | 加分项 | 只用于有边界的统计和校验。 |

#### 三档回答

**🟢 一句话**：普通列表按页请求。需要前端统计或自定义校验的场景才一次拉全量。

**🔵 标准**（默认）：

CommonTable 默认带 page 和 page_size。筛选和排序变化时回到服务端查询，浏览器只渲染当前页。fetchAllAtOnce 打开后，一次拿回更大的结果，再在前端做统计或批量校验。统计弹窗需要一组完整数据时用这条路径。普通工单列表不用。一次拉全量会让首屏等待变长，也会让表格排序失去服务端顺序。超时仍是全局 5 秒，所以全量接口必须本身足够小。默认每页 10 条，页面可以用 pageSizeOPtions 调整。

<details><summary>🔴 深挖（点击展开）</summary>

我没有把所有表格都一次拉完。工单列表会随专项增长，一次返回全部行，首屏和内存都没有必要。服务端分页还能让筛选条件生效，避免前端再过滤一遍旧数据。全量拉取只放在结果集有边界的地方。比如统计需要同一批数据计算占比，分页会把计算拆散。checkValid 也需要看到当前可选集合，而不是只看到这一页。实现上这是表格的一个开关，不是另一个组件。请求参数仍从 getListData 出去，页面决定接口是否忽略页码。这里的取舍是组件少一个、调用方多一个明确参数。如果以后统计数据变大，应该把聚合放到后端，前端只拿结果。不要把 fetchAllAtOnce 当成默认优化。它减少的是请求次数，增加的是单次响应体积。pageSizeOPtions 允许页面把每页条数改成更适合扫描结果的值，但默认仍是 10。服务端排序和前端排序不能混用。打开 fetchAllAtOnce 后，表格排序只代表当前这次返回的顺序，我不会再声称它是全库顺序。这一点我能在仓库里指到具体文件，不会把同事后来的移动端适配算进自己的范围。统计弹窗需要完整一批数据，所以只有这种场景打开一次拉全量。

</details>

#### 补齐方案

- 📚 必读
  - [ ] 分页参数设计
  - [ ] 前端聚合与后端聚合
- 🛠️ 动手
  - [ ] 同一张表分别按页和全量请求，比较返回体积
- ⚠️ 常见踩坑
  - 统计接口也按页求和，结果随翻页变化
  - 默认打开全量开关
- 🤔 自测题（合上文档自答）
  - [ ] 减少请求次数就等于更快吗？
- ⏱️ 预估学习时长：**半天**

#### 追问（面试官深挖向）

- ⚖️ **全量数据超过超时时间怎么办？**（reliability）
  > 不加大全局超时。统计改成后端聚合，或者给这个接口单独的超时和行数上限。

## 🛡️ 可靠性（reliability）— 2 题

### Q1. 接口没有走 HTTP 错误码时，你怎么判断登录过期和业务失败？

> 来源：`tp-04` · scope: fullstack · tech-debt-manage · 难度: 中级

#### 知识点

| 名称 | 等级 | 为什么会问 |
|---|---|---|
| Axios 拦截器 | 必须掌握 | 业务码不在 HTTP body 的固定位置。 |
| 登录态失效 | 必须掌握 | 过期后要终止旧页面，而不是只弹一句错误。 |
| 错误码映射 | 加分项 | 使用者只看能行动的文案。 |

#### 三档回答

**🟢 一句话**：看响应头 trpc-func-ret。100001 刷新登录，100002 取出鉴权地址，其他码映射成提示。

**🔵 标准**（默认）：

后端用 tRPC，业务码放在响应头，HTTP 仍可能是 200。拦截器先取 trpc-func-ret。100001 表示登录态过期，我遍历 document.cookie，把每条设成过期，然后刷新页面，让网关重新走登录。100002 表示鉴权失败，我用正则从 trpc-error-msg 里取 https 地址，连同 data 返回给路由层。其他码进 errorMap。能识别的给固定文案，例如记录已存在、记录未找到。识别不了的统一说系统繁忙。网络错误走第二个回调，同样尽量映射成可读消息。

<details><summary>🔴 深挖（点击展开）</summary>

如果只看 HTTP 状态，登录过期会被当成普通成功或普通失败。使用者停在旧页面上继续点，请求会连续失败。所以成功拦截器里先处理两个特殊码。清 Cookie 时只改 expires 和 path，不把 Cookie 值打进上报。刷新后页面重新加载，路由会再次请求专项列表。鉴权失败不能直接刷新，因为使用者可能只是缺某个专项的权限。我把授权地址传出去，由路由模块记到 window.authUrl，无权限页再用它引导申请。errorMap 故意把大量内部码收成系统繁忙。这些码对使用者没有操作意义，原样展示只会暴露内部编号。记录冲突和记录不存在是使用者能处理的，所以保留具体文案。超时设成 5 秒。管理端查询通常够用，但导出或大批量提交可能偏短。这个问题我知道，批量接口如果继续加，应该单独放宽超时，而不是把全局超时调大。成功回调里如果 data 为空，我会按错误处理，而不是把空响应交给页面渲染。网络错误回调要先判断 err.response 是否存在。超时没有 response，直接读 headers 会再抛一次异常。映射文案用 MessagePlugin 之外的 Promise.reject 传出，由页面决定是否弹出。这一点我能在仓库里指到具体文件，不会把同事后来的移动端适配算进自己的范围。

</details>

#### 补齐方案

- 📚 必读
  - [ ] Axios interceptors
  - [ ] tRPC HTTP 映射
- 🛠️ 动手
  - [ ] 模拟 100001 和 100002 两个响应头，确认页面行为不同
- ⚠️ 常见踩坑
  - 鉴权失败也整页刷新，使用者不知道去哪里申请
  - 把内部错误码直接展示出来
- 🤔 自测题（合上文档自答）

## 🔒 安全（security）— 1 题

### Q1. 登录态放在哪里，过期和没权限为什么不是同一种处理？

> 来源：`tp-06` · scope: fullstack · tech-debt-manage · 难度: 中级

#### 知识点

| 名称 | 等级 | 为什么会问 |
|---|---|---|
| Cookie 会话 | 必须掌握 | 身份在网关，不在前端存储。 |
| 开放重定向 | 必须掌握 | 鉴权地址必须限制协议。 |
| 权限与登录分离 | 加分项 | 两种失败对使用者的下一步不同。 |

#### 三档回答

**🟢 一句话**：请求带 Cookie。登录过期就清掉并刷新。没权限则保留页面，只拿出申请地址。

**🔵 标准**（默认）：

Axios 设置 withCredentials，会话由网关写在 Cookie 里，前端不保存 token。过期码是 100001。旧 Cookie 继续带上只会重复失败，所以先过期本地 Cookie，再刷新。没权限是 100002。这时人已经登录，只是缺专项权限。我从 trpc-error-msg 提取 https 地址，交给无权限页。两种情况如果都刷新，使用者看不到申请入口。正则只接受 https，避免错误头里的任意字符串变成跳转地址。

<details><summary>🔴 深挖（点击展开）</summary>

管理端位于内网网关后面，我没有自己做账号密码登录。浏览器只负责带上 Cookie。这样前端不接触长期凭证，也不把身份放进 localStorage。过期时的风险是死循环。如果清得不干净，刷新后仍带旧 Cookie，页面会再次收到 100001。所以删除时指定 path=/，并使用过去的 expires。我没有在日志里打印 Cookie 值。没权限的处理要保守。错误头是服务端拼出来的，理论上可能包含意外文本。正则限定 https URL，取第一个匹配。匹配不到就不跳转，只保留数据和无权限状态。window.authUrl 是路由模块和请求层之间的一个简单交接。它不是权限系统本身。真正的授权仍然在网关和后台。前端只决定展示菜单、失败页还是申请入口。Cookie 清理不能只删已知名字。网关可能追加会话字段，所以按当前 document.cookie 逐条过期更稳。刷新使用 location.reload，让路由模块重新执行顶层请求。无权限地址只保存，不在拦截器里直接跳转，避免一次列表请求把使用者突然带离当前页。这一点我能在仓库里指到具体文件，不会把同事后来的移动端适配算进自己的范围。鉴权地址来自响应头，页面用它引导申请，拦截器本身不负责跳转。

</details>

#### 补齐方案

- 📚 必读
  - [ ] Cookie 与 withCredentials
  - [ ] 开放重定向
- 🛠️ 动手
  - [ ] 构造一条非 https 的错误头，确认页面不会跳走
- ⚠️ 常见踩坑
  - 把鉴权地址直接赋给 location.href
  - 登录过期后只弹提示，不清理 Cookie
- 🤔 自测题（合上文档自答）
  - [ ] 为什么没权限不能和登录过期一样刷新？
- ⏱️ 预估学习时长：**半天**

- ⚖️ **前端能不能靠隐藏菜单实现权限？**（security）
  > 不能。隐藏菜单只改善界面。接口仍要由网关和后台拒绝，前端只处理 100002 的展示。

## ⚖️ 取舍（trade-off）— 1 题

### Q1. 为什么在路由模块顶层等待接口，而不是先渲染再补菜单？

> 来源：`tp-08` · scope: fullstack · tech-debt-manage · 难度: 中级

#### 知识点

| 名称 | 等级 | 为什么会问 |
|---|---|---|
| 顶层 await | 必须掌握 | 它把接口耗时放进应用启动。 |
| 路由稳定性 | 必须掌握 | 菜单未返回时不能误判 404。 |
| 渐进渲染 | 加分项 | 接口变慢后再把等待从整站缩小到菜单区。 |

#### 三档回答

**🟢 一句话**：先等到菜单，是为了避免先闪出空菜单。代价是接口慢时整次进入都被堵住。

**🔵 标准**（默认）：

另一种做法是先用静态骨架渲染，再请求专项列表并更新路由。那样首屏快，但菜单会从空变满，深链也可能先落到 404。我选顶层 await，让路由表在 BrowserRouter 使用前准备好。失败则立刻进入 /project/error，不渲染半套菜单。坏处是 getProjectListNew 的耗时直接加到可交互时间上，而且模块失败会影响整站路由。这个后台的首个动作就是选专项，空菜单没有价值，所以我接受这次等待。

<details><summary>🔴 深挖（点击展开）</summary>

这个选择发生在项目早期。专项数量不大，接口通常很快，顶层等待最容易保证菜单和地址匹配。如果先渲染，我还要处理三件事。第一，初始路由不能把未知地址判成 404。第二，列表返回后要替换路由且不打断当前地址。第三，请求失败时要把已经渲染的骨架改成失败页。这些都能做，但当时没有必要。现在的代价我可以明确说。网络慢时，使用者看到的是浏览器加载，而不是应用内的骨架屏。模块级错误也不容易被 React 错误边界单独接住。如果以后专项接口变慢，我会改成壳子先渲染，菜单区单独进入加载态，深链先保留路径，列表返回后再校验。现在不改，是因为还没有这个耗时问题，而空菜单闪动已经能避免。面试里我会把这个决定说成阶段性取舍，不说成永远正确的结构。顶层 await 还依赖构建目标。Vite 的 build.target 设成 esnext，旧目标可能直接不支持这种模块语法。失败跳转写了 pathname 判断，已经在 /project/error 时不再跳，避免无限刷新。这个保护是实际踩过加载失败后补上的。这一点我能在仓库里指到具体文件，不会把同事后来的移动端适配算进自己的范围。

</details>

- 📚 必读
  - [ ] ES modules 顶层 await
  - [ ] React Router 动态路由
- 🛠️ 动手
  - [ ] 把等待改到组件内，比较空菜单闪动和首屏时间
- ⚠️ 常见踩坑
  - 接口未返回就注册通配 404
  - 失败后没有任何错误页
- 🤔 自测题（合上文档自答）
